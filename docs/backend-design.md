# わりかん生活：バックエンド設計メモ

- 更新日：2026-11-21
- 状態：設計方針まとめ／実装前レビュー用
- バックエンド候補：Cloudflare Workers + D1（SQLite）
- 仕様の正本は企画メモ（[plan.md](plan.md)）。このメモは、それをD1とWorkerでどう実現するかをまとめる。食い違ったときは企画メモに合わせる
- 認証：Singfolioの実装（`singfolio/worker`）をこのリポジトリの `worker/` にコピーして使う。アカウントはSingfolioと共通にせず、アプリごとに分ける

## 1. 方針

### アプリの前提

- 2人での利用を中心に、3人以上のグループにも対応する。
- 家計の共通支出を記録・集計するアプリ。旅行の異通貨割り勘アプリではない。
- 1グループにつき1通貨。グループ内で複数通貨を混在させない。通貨換算・為替レート取得は対象外。
- 月単位で集計する（1日〜末日が基本）。月は、月の途中でも締められる（途中で精算して解散したい、月末を待たずに締めたい、など）。
- 支出の日付と、どの月に登録するかは独立させる。締めた後に出た支出（入力漏れや、早めに締めた月の残り）は、登録できる月に登録する（8章）。
- 月締め後、その月の支出は追加・編集・削除できない。締めの取り消し・再オープン機能は設けない。
- 前の月の締めと、その月のすべての送金の精算または繰越が済んでいないと、次の月は締められない。
- 締めた月の送金ごとに、「精算する」か「次月に繰り越す」を選ぶ。月やグループ全体をモードで固定しない。
- 繰り越した送金は、翌月を締めるときに、メンバーごとの差額に足してから送金を作り直す（4章）。翌月の支出・負担額には加算しない。もう一度繰り越せば、さらに翌月に合算されるだけなので、「再繰越」という操作は無い。
- 費目による負担は、月の費目ごとの合計に負担割合をかけて計算する。月の途中で割合を変えたら、その月全体に反映する。締めた時点で確定する。
- 固定費はテンプレートとして登録し、毎月の支出レコードは通常の支出として作成する。
- 招待URLはワンタイム・発行から3日で失効。URLを開いただけでは参加させず、グループ名と招待元を表示して「参加する」を押した後に参加処理を行う。
- 新規メンバーが閲覧できる履歴は参加月以降。脱退は月単位（「今月で脱退する」のみ）で、脱退する月を締めた時点か、翌月1日の早いほうで確定する。
- ローカル銀行連携、レシートOCR、個人資産管理などは対象外。

### インフラ方針

- Cloudflare Workers + D1を第一候補としてプロトタイプを進める。
- SingfolioのApple / Google認証・セッション処理を、`worker/` にコピーして使う。リポジトリが別なので、共通のパッケージにはしない。データ領域・設定・クライアントIDは、アプリごとに分ける。
- コピーしたときは、コピー元のSingfolioのコミットを `worker/` のコードコメントに書く。Singfolio側で認証を直したときは、その差分を手で取り込む。
- Honoなど、既存プロジェクトで使っていない仕組みを理由なく追加しない。
- 開発中はFree枠で検証し、公開時にWorkers Paid（月額5 USDを目安）へ移行する案。
- D1はWorkerからのみアクセスさせ、クライアントから直接アクセスさせない。
- Durable Objects、シャーディング、読み取りレプリカ等は初期段階では導入しない。
- 月初の処理（脱退の確定など）と固定費の自動登録は、Cron Triggersで行う（7章）。

## 2. 金額・通貨・割合

### 金額

金額は浮動小数点ではなく、通貨の最小単位を整数で保存する。

| 通貨 | 表示例 | DB保存値 | 小数桁 |
|---|---:|---:|---:|
| JPY | 1,234円 | 1234 | 0 |
| USD | $12.34 | 1234 | 2 |
| EUR | €12.34 | 1234 | 2 |
| KWD | 12.345 KWD | 12345 | 3 |

- `expense_groups.currency_code` にISO 4217の3文字コードを保存する。
- `expense_groups.currency_minor_unit` にその通貨の小数桁数を保存する。
- 通貨マスター（通貨コードと小数桁数の対応表）は、アプリとWorker（`worker/src/currencies.ts`）の両方に置く（コードは共有しない）。最初のリリースから、主要通貨を選べるようにする。初期の一覧は JPY・USD・EUR・GBP・AUD・CAD・CNY・KRW。要望があれば追加する。クライアントは通貨コードだけを送り、小数桁数はWorkerが表から決める（桁数を間違えると、金額が100倍・1/100になるため、申告を受け付けない）。
- グループ作成時の初期値はJPY。
- グループ作成後、金額に関わるものが1つでもあれば通貨変更不可（409 `currency_locked`）。支出が1件でも登録されたとき、に加えて、固定費のテンプレート・上限額つきの負担・締めた月（通貨のスナップショットを持つ）がある場合も。金額は通貨の最小単位の整数なので、通貨を変えると、同じ整数が別の金額になる。
- 固定されるかは、**いまの状態**で決まる(一度固定したら戻らない、ではない)。支出をすべて消す、上限額を外す(メンバーの増減による割合のリセットでも外れる)と、また変えられる。締めた月は消せないので、締めたあとはずっと固定される。画面は「戻らない」と案内せず、グループ情報の `currencyLocked` で入口を出し分ける。
- **通貨を変えた直後に、古い通貨の画面から金額が送られても、別の額として保存しない。** 金額を送るAPI(支出の登録・編集、上限額つきの割合の保存)は、アプリが画面で見せていた通貨を `currencyCode` で添え、グループの通貨と違えば409 `currency_mismatch`(グループの通貨を添える。アプリはグループ情報を読み直して、金額を入れ直してもらう)。Workerは、任意項目として受け付け、送られたときだけ突き合わせる。**アプリは必ず送る**(アプリの実装時に、必須にするかを決める)。固定費のAPIも、同じ項目を持たせる。
- 月締めにも通貨コードと小数桁数をスナップショット保存する。
- 1件の金額の上限は `10^12`（JPYで1兆円）。APIで検証し、DDLにもCHECKを置く。
- 割合をかける掛け算は、BigIntで行う（`worker/src/settlement.ts`）。`10^12` に割合（最大10000）をかけると、JavaScriptの安全整数（2^53 - 1）を超えるため。月の合計や負担額そのものは安全整数に収まる前提で、超えたら計算を止める（エラー）。

### 負担割合

割合は1万分率（basis points）で整数保存する。

| 表示 | DB値 |
|---:|---:|
| 100% | 10000 |
| 60% | 6000 |
| 50% | 5000 |
| 40% | 4000 |
| 33.33% | 3333 |

- 負担対象メンバー間の割合合計は10000。
- 画面上は通常のパーセント表示にする。
- 0.01%単位まで指定可能な設計。UIでそこまで細かい指定を見せるかは別途判断する。

### 金額指定

- メンバーごとの指定額合計は支出総額と完全一致必須。
- 差額の自動配分はしない。合計不一致なら登録できない。

### 端数

- 均等割り・割合割りでは、最小通貨単位で計算する。
- 各メンバーの値を切り捨てで出し、残った端数を、割合が0より大きいメンバーに固定順で1単位ずつ配分する。
- 例：10,000円を3人で均等割り → 3,334円、3,333円、3,333円。
- 1円単位の公平性を追求する機能は設けない。ただし各メンバーの負担額の合計は、元の金額と必ず一致させる（一致しないと、精算の差額の合計がゼロにならない）。
- 固定順はメンバーIDなど、端末やリクエスト順に依存しない値を使う。
- 費目による負担では「費目の月合計」に対して、個別設定の支出では「その支出の金額」に対して、この端数処理を行う。

## 3. 負担・精算ロジック

### 負担方法

支出ごとに `split_method` を持つ。

- `category`：費目の負担割合を使う（既定）。負担額は支出ごとには保存せず、月の集計で計算する。
- `equal`：対象メンバーで均等割り。
- `ratio`：支出ごとに指定した割合で割る。割合合計は10000。
- `fixed`：支出ごとに金額を指定。指定額合計は支出額と一致。
- `single`：1人が全額負担する。

`category` 以外は、企画メモの「この支出だけ負担割合を変える」にあたる。支払った人（payer）と負担する人は別概念として保存する。支払った人が全額負担するとは限らない。

### 保存する負担データ

- `expenses.amount_minor`：支出総額
- `category_month_settings`：月ごと・費目ごとの設定（上限額つきの負担の、負担する人と上限額）
- `category_month_shares`：月ごと・費目ごと・メンバーごとの負担割合
- `expense_allocations`：`category` 以外の支出の、メンバーごとの確定負担額（`burden_minor`）。割合指定のときは `share_basis_points` も残す

`category` の支出には `expense_allocations` を作らない。割合を変えたときに、その月の支出を計算し直す必要をなくすため。個別設定の支出は、登録時に計算した負担額を保存し、あとから計算ロジックが変わっても変化しないようにする。

### 月ごとの負担割合

- ある費目・ある月の設定は、`category_month_settings` のうち、その月以前で最も新しい月の行と、同じ月の `category_month_shares` の行の組を使う（行が無い月は、直前の月の設定を引き継ぐ）。
- `category_month_settings` の1行と `category_month_shares` の行の組は、常に同じ月でまとめて書く。どの月の設定を使うかは、`category_month_settings` の月で決まる。
- 読み取り時には行をコピーしない。次のときに、その月の行の組を書く。
  - その月の割合を変更したとき
  - 費目を作ったとき（その月に参加しているメンバーで均等）。書く月は、最初の未締めの月と、それより後で割合の行がある月（`worker/src/categories.ts`）。最初の月だけに書くと、メンバーの増減で後の月に行が書かれている他の費目と違い、新しい費目だけが、後の月に古いメンバーの割合を引き継ぐ
  - メンバーが参加した月（その月の全費目を、新しいメンバーを含めた均等にリセットする）
  - 脱退が確定した月（その月の全費目を、残るメンバーでの均等にリセットする）
  - 月締め時（その月の行が無ければ、引き継いだ割合を書き、確定値として残す）。アーカイブした費目は、その月に支出がなければ書かない（使わない行が毎月増え続けるため。設定は、引き継ぐ元の行がそのまま使われる）
- 1つの費目・月の行は、その月に負担対象となる全メンバーの組として書き、合計を10000にする。
- 割合を変更できるのは、締めていない月だけ。
- メンバーの増減で均等にリセットするときは、上限額の設定も外す（`cap_member_id`・`cap_minor` をNULLにする）。

### 上限額つきの負担

`category_month_settings` に `cap_member_id`（負担する人）と `cap_minor`（上限額）があるとき、その費目の `category` の支出の月合計 `T` を次のように分ける。

1. 負担する人が `min(T, cap_minor)` を負担する。
2. 超えた分 `T - cap_minor`（0より大きいとき）を、`category_month_shares` の割合で全員に分ける（端数処理は2章）。負担する人の割合は、上限額を設定したときの既定値を0にする（変更できる）。

- 例：2人、外食の上限が自分の10,000円、超えた分の割合が自分0%・相手100%。`T` が8,000円なら、自分8,000円・相手0円。`T` が15,000円なら、自分10,000円・相手5,000円。
- 上限額は費目の月合計に対してかける。支出ごとの個別設定（`category` 以外）の支出は、`T` に含めない。
- 負担する人は、その月の `category_month_shares` に含まれるメンバーでなければならない（割合は0%でよい）。

### 月次集計

メンバーごとに次を集計する。

- 支払額：そのメンバーが支払った支出の合計
- 負担額：次の合計
  - 費目ごとに、`category` の支出の月合計 × その月の割合（端数処理は2章。上限額つきの費目は前節のとおり）
  - `category` 以外の支出の `expense_allocations.burden_minor`
- 差額：支払額 - 負担額
- 繰越：前の月の締めで `carried` にした送金の合計。送金先なら足し、送金元なら引く（4章）
- 精算する額：差額 + 繰越

精算する額がプラスなら受取側、マイナスなら支払側、ゼロなら精算不要。全員の差額の合計も、繰越の合計も、必ずゼロになる。

支出の総額・負担額・差額は、その月の支出だけから出す。繰越は精算する額にだけ入れる。

### 精算先の組み合わせ

「精算する額」をもとに、支払側と受取側をそれぞれ固定順で並べ、先頭同士から少ない方の残額を精算額として組み合わせる。残額がゼロになった側を次のメンバーに進める。全員の残額がゼロになるまで繰り返す。

- 繰越を足した後の額から作り直すため、繰り越した送金の組み合わせ（誰から誰へ）は、翌月には残らないことがある。たとえば「A → B」の繰越が、新しいメンバーCを経由して「A → C」「C → B」になることもある。各メンバーが払う・受け取る合計額は正しいので、これでよいとする。

- 3人以上でも同じアルゴリズムを使う。送金は最大で「差額がゼロでないメンバー数 - 1」件になる。件数が最少になることまでは保証しない（企画メモの「件数が少なくなるように」は、この意味とする）。
- 精算結果は `settlement_transfers` に保存し、後から再計算して過去の送金先・金額が変わらないようにする。

## 4. 月締め・精算・繰越

### 月締めの条件

Workerで次をすべて確認してから締める。

- 対象月が、カレンダー上の今月以前（グループのタイムゾーン）。月の途中でも締められるが、まだ始まっていない月は締められない。
- 対象月がまだ締められていない。
- 前の月が締め済みで、その送金がすべて `settled` または `carried`。グループで最初の月（最初の支出がある月、または作成月）はこの条件を問わない。
  - 「最初の月」は、締めがまだ1つも無いときの、最初の支出がある月以前の月（支出が1件も無ければ作成月以前）。作成月に支出が無く、翌月に最初の支出を登録したグループは、作成月を締めずに、翌月を最初に締められる。それより前の月に支出を登録すれば、そちらが最初の月になる。
  - 締めが1つでもあるとき、前の月が未締めなら締められない。飛ばした月も、古い月から順に締める。
  - 最後に締めた月より前で、締めていない月（飛ばした月）は、締められない（`month_skipped`）。締めた月は `month_closed`。古い月を後から締めると、翌月の締めに繰越を足す前提が崩れるため。
- 操作者が、その月に有効なメンバー（参加（復帰）した月から、脱退月まで。5章）。

### 月締めの処理

1. 対象月の支出・個別負担額・費目の割合と、前の月の締めの `carried` の送金を取得
2. メンバーごとの支払額・負担額・差額・繰越・精算する額を計算
3. 送金元・送金先・金額の組み合わせを計算
4. 1回の `batch()` で次を書く（8章の競合制御つき）
   - 行が無い費目の `category_month_settings`・`category_month_shares`（引き継いだ設定を書き、確定値として残す）
   - `monthly_closings`
   - `closing_member_summaries`
   - `closing_category_burdens`（費目ごとの合計と、メンバーごとの負担額。履歴画面の内訳用）
   - `settlement_transfers`
   - この月を脱退月に選んでいるメンバーの脱退の確定（5章の2。`worker/src/membership.ts` の `confirmLeaveStatements`）。そのメンバーが、グループの最後の1人のときは、締めずにグループを削除する（5章）
   - 脱退が確定した（`leaving`）メンバーのうち、脱退月（またはそれより後の月）が締められ、関わる送金に未処理が無く、繰越先の月が未締めの繰越も無く、脱退月より後の未締めの月の支出に関わっていないメンバーを `left` にする（5章の4。送金が0件なら、ここで脱退済みになる）

月締め後は、API側で対象月への支出の追加・編集・削除と、割合の変更を拒否する。UIだけで制限しない。

送金が0件の月（全員の差額がゼロ）は、締めた時点で処理済みとなる。

### 精算と繰越

送金ごとに状態を持つ。

- `pending`：未処理
- `settled`：精算済み
- `carried`：次月に繰越済み

- 許可する状態遷移は `pending → settled` と `pending → carried` だけ。どちらも、確定後に戻せない。
- 脱退を選んだメンバー（`leave_requested_month` あり）、`leaving`、`deleted` のメンバー（5章）が送金元・送金先のどちらかである送金は、`carried` にできず、`settled` にするしかない。削除されたユーザーとの送金も、金額と方向は表示されているので、残るメンバーが確認して精算済みにする。
- 月は、すべての送金が `settled` または `carried` になった時点で処理済みとなる。処理済みかどうかは送金の状態から判定し、別に保存しない。

### 繰越

- 繰越先は常に、締めた月の翌月。翌月を締めるとき、前の月の締めの `carried` の送金を、メンバーごとの繰越として精算する額に足す（3章）。
- 繰越の元は、元の送金レコード（`status = 'carried'`）。締める前の見込みの計算でも、同じレコードから足す。締めた結果は `closing_member_summaries.carried_in_minor` に残す。
- 前の月の送金がすべて処理済みでないと翌月は締められないため、翌月を締める時点で繰越の額は確定している。
- 繰越を何度選んでも、毎月「前の月の締めの `carried`」だけを足すので、同じ金額を二重に数えない（2か月前の繰越は、前の月の送金にすでに入っている）。
- 繰越分は、翌月の支出の総額・負担額には含めない。
- 繰越を含むことは、繰越先の月を閲覧できる全メンバー（その月に参加した新メンバーを含む）に見せる。

## 5. メンバーの参加・脱退・匿名化

### メンバーの状態

| `status` | 意味 |
|---|---|
| `active` | 参加中。`leave_requested_month` が入っていれば「今月で脱退する」を選んだ状態で、脱退が確定するまで取り消せる |
| `leaving` | 脱退が確定した（脱退月を締めた、または翌月1日を過ぎた）が、関わる送金が未処理のため、メンバーとして残っている |
| `left` | 脱退済み。名前は残す。グループのデータは見られない |
| `deleted` | アカウント削除済み。名前は匿名化する。削除した月までは、「削除されたユーザー」として集計に含める |

### 参加

- 招待URLを開いただけでは参加しない。招待内容の確認もログイン後に行う。
- 招待情報としてグループ名・招待元を表示する。
- ユーザーが「参加する」を押した時点で、トークン・期限・未使用・未取消を検証して参加処理する。
- 招待トークンは平文で保存せず、ハッシュを保存する。招待はワンタイム、期限は3日。
- 参加処理はグループへの書き込みとして `data_version` を上げる（8章）。同じ招待で同時に参加しようとしても、片方は409になる。
- 新規メンバーの `history_from_month` は参加月とする。
- **1つのグループの人数は5人まで**（`MAX_MEMBERS_PER_GROUP`。`worker/src/limits.ts`）。同棲・夫婦の2人が基本で、ルームシェアの3〜4人までを想定する。月締め・固定費の自動登録のD1のクエリ数と、精算の送金の件数が人数で増えるので、使い道の無い大人数のために、Freeの上限に余裕を残す。数えるのは、今月以降もグループにいる人（`countSeatedMembers`。`worker/src/membership.ts`）。脱退が確定した人（`leaving` 以降）と、脱退月が終わった人（Cronの確定の前でも。`isLeaveEffectiveFor`）は数えないので、入れ替わりの参加をふさがない。脱退を選んだだけで脱退月がまだ終わっていない人は、今月はいるので数える。上限なら、招待の発行も参加（`left` の人の復帰を含む）も、409 `group_full` で断る。**アプリは満員の判定を書き写さない**（脱退月が終わった直後でCronの確定の前、などでずれる）。グループ情報の `canInvite`（招待を発行できるか）と、招待内容の確認の `groupFull`（参加すると満員で断られるか）で知る（9章）。
- 参加月の全費目の割合を、新しいメンバーを含めた均等にリセットし、見直しのアラートを出す。参加月より後の月に割合の行があれば、それも、その月に参加しているメンバーでの均等に直す（行は、その月以前で最も新しい行の引き継ぎを上書きするので、残すと、新しいメンバーが、その月の割合に入らず、負担が0のまま続く）。後の月の行は、システムが書いたもの（アカウント削除・脱退の確定が、未締めの翌月に書いた均等の割合）のほか、手で直された割合・上限額も、メンバーの増減で戻る（企画メモの「メンバーが増減したとき、均等にリセットする」「確定した月から」に合わせた）。手で先の月に入れた設定が戻ることは、お知らせで伝える（12章）。
- `category` 以外の負担方法の固定費は、自動登録を止め（`paused_reason = 'member_changed'`）、アラートを出す。
- 一度脱退した人（`left`）が再参加する場合は、元のメンバー行を `active` に戻す。`history_from_month` は復帰した月にし、`leave_requested_month`・`expense_end_month`・`left_at` を消す。
- 参加月がすでに締められているとき（今月を早めに締めた後）は、締めた月の割合には触れず、**翌月**の全費目の割合をリセットする。`history_from_month` は、参加月（締めた月）のまま。
- 表示名は、参加するときに入力する（必須）。色は、サーバーが、他の参加中のメンバーと重ならないように選ぶ（9章の色の一覧）。復帰する人は、元の色が使われていなければ、そのまま。
- リセットする全費目には、アーカイブ済みの費目も含める（あとで戻した費目が、古い割合に戻らないように）。固定費は、すでに止まっているもの（手動の停止など）の理由を上書きしない。

### 招待の取り消し

- 発行した人は、未使用の招待をいつでも取り消せる（`revoked_at`）。
- 発行した人の脱退が確定したとき、またはアカウントを削除したときは、その人が発行した未使用の招待をすべて取り消す。
- `leaving` 以降のメンバーは招待を発行できない。

### 脱退

1. 「今月で脱退する」：`leave_requested_month` にカレンダー上の今月（脱退月）を入れる。確定するまでは取り消せる（値を消す）。最後の1人の場合は、グループのデータが完全に削除され元に戻せないことを確認ダイアログで示す。
2. 脱退の確定：脱退月を締めたとき（締めのbatchの中で）、または翌月1日（月初のCron、7章）の早いほう。脱退を選んだ時点で脱退月がすでに締められていれば（早めに締めた後）、その場で確定する。確定時に行うこと：
   - `expense_end_month` に脱退月を入れ、`status` を `leaving` にする。翌月以降の支出の支払者・負担者にできない。
   - 残るメンバーで、翌月の全費目の割合を均等にリセットし、アラートを出す。それより後の月に割合の行があれば、それも直す（参加と同じ）。リセットする最初の月は、脱退月の翌月と、最初の未締めの月（最後に締めた月の翌月）の遅いほう。締めた月の割合は確定しているので触れない（`worker/src/membership.ts` の `firstResettableMonth`）。
   - 発行した未使用の招待を取り消す。
   - 脱退者が支払者の固定費のうち、付け替えられていないものは自動登録を止める（`paused_reason = 'payer_left'`）。付け替えのアラートは、脱退を選んだ時点から出す。
   - `category` 以外の負担方法の固定費は、自動登録を止める（`paused_reason = 'member_changed'`）。脱退者が支払者の固定費は、先に `payer_left` で止まっているので、理由は `payer_left` のまま。すでに止まっているものの理由は、上書きしない。
   - 最後の1人だった場合は、グループを削除する（後述）。
     - 「最後の1人」は、参加中・脱退が確定した（`leaving`）メンバーが、抜ける1人だけのとき（`worker/src/membership.ts` の `isLastMember`）。2人以上が同時に抜けるときは、お互いの精算が残るので、グループは消さない（全員が脱退済みになったグループの後片付けは、12章）。
     - 月締めで確定するときは、その月を締めずにグループを削除し、200 `{ "groupDeleted": true }` を返す（9章）。脱退を選んだ時点で脱退月が締め済みなら、その応答で同じく `groupDeleted` を返す。
   - 脱退月が、最初の締めで飛ばされた月（作成月に支出が無く、翌月を最初に締めた。4章）のときは、脱退月の締めが無いので、締めでは確定しない。確定していないまま、その後の月を締めようとしたときは、先にCronと同じ処理で確定させる。確定すると、その月の割合から脱退した人が外れ、集計が変わるので、締めずに409 `conflict` を返し、読み直して締め直してもらう（確定の前の割合で締めると、脱退した人に負担が付く）。
3. `leaving` の間も、集計・締め・精算には通常どおり参加し、グループのデータを見られる。
4. 脱退月が締められ、その人が関わる送金がすべて `settled` になったら `left` にする（送金が0件なら、締めた時点で `left`）。この遷移は、締めと精算の処理の中で行う。
   - 脱退月が、最初の締めで飛ばされた月（作成月に支出が無く、翌月を最初に締めた。4章）のときは、脱退月は締められない。脱退月より後の月が締められていれば、脱退月が締められたものとして扱う。
   - 脱退月より後の、まだ締めていない月の支出に、その人が支払者・負担の対象（個別設定の割り当て）として関わっているあいだは、`left` にしない。今月を早めに締めたあとに、翌月の支出を登録して、そのあとで脱退を選ぶと、その場で確定しても、翌月の支出が残る。その月を締めると、その人が関わる送金ができるので、`left` にしていると、本人は見られず、精算できない（繰越と同じ）。その月を締め、送金を `settled` にすれば `left` になる。
   - `carried` の送金は、繰越先の月（締めた月の翌月）を締めるまで、未処理と同じに扱う。繰り越した額は、翌月を締めるまでどの送金にも入っていない。そのあいだに `left` にすると、翌月の締めでその人が関わる送金ができても、本人は見られず、精算できない。繰越先の月を締めると、繰越は翌月の送金に作り直され、その送金を `settled` にすれば `left` になる（`leaving` のメンバーは、脱退月より後の月も見られる）。
   - 繰り越したあとで、その人が脱退を選ぶこともある（締めた月のうちに脱退を選ぶと、その場で確定する）。脱退を選ぶ操作は、繰越が残っていても断らない。上の規則で、`left` にならずに待つだけ。
   - 繰り越した額の送金（翌月の送金）は、本人が脱退を選んでいるので、さらに繰り越せず、`settled` にする（4章）。

月の途中で抜けたいときは、脱退を選んでから、その月をすぐに締めて精算すればよい。その月の残りの支出は翌月分として登録し、翌月の通常の支出とあわせて、残るメンバーの新しい割合（均等リセット後）で計算する。

- **Cronが確定させるまでの間も、APIは、脱退月（`leave_requested_month`）が終わったメンバーを確定したものとして扱う。** 翌月1日のCronは1時間ごとで、競合すれば次の回に回るため、`status` が `active` のままの時間がある。その間も、本人は支出を記録できず（`worker/src/access.ts` の `canWriteExpenses`）、他のメンバーも、本人を翌月以降の支払者・負担の対象にできない（`worker/src/expenses.ts` の `isMemberAvailable`）。待つと、あとで確定しても戻らない個別の負担額が、翌月の支出に残る。脱退の取り消しは当月中だけ（9章）なので、脱退月が終わったあとに取り消されることはない。
- 他のメンバーを外す機能は設けない。
- 過去の支出・負担・精算履歴は削除しない。脱退後のメンバー行は履歴・精算参照のため残し、名前もそのまま表示する（「脱退済み」と併記）。
- 2人グループで1人が脱退した場合は、残った1人のグループとして存続する。

### グループの削除

最後の1人が脱退したとき、またはアカウントを削除したときに、そのグループのデータをすべて物理削除する。外部キーに `ON DELETE CASCADE` を付けていないため、1回の `batch()` で子から順に消す。

`settlement_transfers` → `closing_category_burdens` → `closing_member_summaries` → `monthly_closings` → `expense_allocations` → `expenses` → `recurring_expense_runs` → `recurring_expense_allocations` → `recurring_expenses` → `category_month_shares` → `category_month_settings` → `categories` → `invites` → `group_members` → `expense_groups`

### アカウント削除

- 認証はSingfolioの `POST /auth/delete` に揃える。セッションに加えて再認証を求め、その場で得たAppleの認可コードでrevokeする。リフレッシュトークンはD1に保存しない。
- 月単位の脱退の規則によらず、すべてのグループからすぐに抜ける。1回の `batch()` で次を行う。
  - 自分が最後の1人のグループを削除する（上記）。
  - 残りのグループで、自分のメンバー行（過去に脱退したものを含む）を `status = 'deleted'`、`display_name = '削除されたユーザー'`、`user_id = NULL` にする。参加中だったグループでは、`expense_end_month` をカレンダー上の今月にし、翌月の全費目の割合を残るメンバーでの均等にリセットする。
  - 削除した月までの、締めていない月の集計には、「削除されたユーザー」として含めたまま計算する（費目の割合・個別負担はそのまま）。削除後に登録する支出の支払者・個別負担の対象には選べない。費目の割合から外したいときは、残るメンバーが0%にする。
  - `closing_member_summaries.display_name_snapshot` も同じ表現に匿名化する。
  - 自分が発行した未使用の招待を取り消す。
  - 自分が支払者の固定費は自動登録を止め（`paused_reason = 'payer_left'`）、付け替えのアラートを出す。
  - 関わるグループすべての `data_version` を上げる。
  - 最後に `users` の行を消す。`identities`・`sessions` は `ON DELETE CASCADE` で消える。
- 実装は `worker/src/accountDeletion.ts` の `deleteAccount`（競合制御は8章の `writeToGroups`）。`POST /auth/delete`（`worker/src/deleteAccount.ts`。再認証・Appleのrevoke。9章の「認証API」）が、再認証のあとに呼ぶ。グループごとの扱いは次のとおり。
  - 「自分が最後の1人」は、自分以外に、参加中・脱退が確定した（`leaving`）メンバーがいないグループ。自分が脱退済みでも同じ（誰も見られないグループを残さない）。
  - 脱退が確定した（`leaving`）・脱退済み（`left`）のグループは、確定のときに、割合のリセット・招待の取り消し・固定費の停止を済ませているので、匿名化だけを行う（`expense_end_month`・`left_at` もそのまま）。
  - 参加中（`active`）だったグループの `expense_end_month` は、今月。ただし、脱退を選んだ月が今月より前なら（Cronが確定させる前）、その月。翌月の割合のリセットと、それより後の月に行がある月の扱いは、脱退の確定と同じ（リセットする最初の月は、翌月と最初の未締めの月の遅いほう。締めた月の割合には触れない。`worker/src/membership.ts` の `firstResettableMonth`）。
  - 固定費は、自分が支払者のものを `payer_left`、`category` 以外のものを `member_changed` で止める（企画メモの「メンバーの増減時」に合わせた。脱退と同じ）。
- 匿名化は外部キーの `ON DELETE SET NULL` に任せず、Workerが `users` を消す前に明示的に行う。`group_members.user_id` の `ON DELETE SET NULL` は、消し漏れに対する保険。
- 金額・支出・精算履歴は残す。支出の内容（自由入力）も消さない。グループで共有している記録で、他のメンバーが代わりに入力したものも混ざるため。名前は匿名化し、内容は残すことをプライバシーポリシーに書く。

**注意：** 脱退とアカウント削除は同じ操作ではない。脱退はグループ単位で月単位、アカウント削除は全グループにすぐ及び、本人情報も消す。

### DB制約とWorker検証の分担

DBで保証するもの：

- 主キー・外部キー
- 同じグループ内の関連付け（複合外部キー）
- 金額が負数にならないこと、上限を超えないこと
- 割合が0〜10000の範囲であること
- 月・日付の書式（`YYYY-MM`、`YYYY-MM-DD`）
- 送金の状態と、精算・繰越日時の整合
- 1グループ・1か月につき締めは1件だけ
- 1支出・1メンバーにつき負担レコードは1件だけ
- 1つの固定費テンプレート・対象月につき生成記録は1件だけ

Workerで保証するもの：

- 負担割合の合計が10000
- 金額指定の合計・負担額の合計が支出額と一致
- メンバーが対象月に有効であること
- 対象月が締め済みでないこと、締めの条件（4章）
- 送金の状態遷移と、脱退者の送金を繰り越さないこと
- グループ通貨が支出登録後に変更されないこと
- 操作ユーザーが対象グループの権限を持つこと
- 参加月より前の履歴を閲覧できないこと

SQLiteの `CHECK` 制約だけでは複数行の合計や他テーブルの状態を保証できないため、Workerの検証と、8章の競合制御で扱う。

## 7. 定期処理（Cron Triggers）

- Cronは1時間ごとに動かし、各グループの `timezone` で日付を判定する。処理はすべて冪等にする（同じ時刻に2回動いても結果が変わらない）。
- 月初の処理：脱退月が締められていない脱退の確定（5章）。実装は `worker/src/cron.ts` の `runScheduled`（確定の中身は `worker/src/membership.ts` で、月締め・脱退を選ぶ操作と共通）。
  - 対象は、`status = 'active'` で、`leave_requested_month` がグループの今月（グループのタイムゾーン）より前のメンバー。部分索引 `idx_group_members_leave_requested` で、脱退を選んだままのメンバーだけを読む（毎時、全グループを読まない）。
  - 1回の実行は、D1のクエリ数の予算（`QUERY_BUDGET_PER_RUN`。50。Freeの上限。batch の文も1つずつ数える。8章の「D1のクエリ数の数え方」）に収まる範囲で、古い月のグループから確定させる。1グループの確定は約15クエリ（読み込み5〜6、書き込み約10。`worker/test/cron.test.ts` で数えている。最後の1人の脱退でグループを削除するときは約19）。次のグループが収まるかは、`ESTIMATED_QUERIES_PER_GROUP`（20）と、これまでで最も大きかった1グループの、大きいほうで判定する（前のグループが小さくても、次の大きいグループで予算を超えないように）ので、Freeでは1回に2グループほど。予算に収まらないグループは、次の回に回す（1つ目は、予算を超えても必ず処理する）。見積もりは上限の保証ではなく、割合の行がある先の月が多いグループは、超えることがある（そのグループは例外になって次の回に回るだけ）。APIは、脱退月が終わったメンバーを確定したものとして扱う（5章）ので、遅れても、利用者の見える挙動は変わらない。**Paid（上限は1回につき1000）へ移すときは、予算を1000に近い値へ上げる。** 公式のとおり batch を1回と数えるなら、Freeのままでも、1回に確定できるグループは増える（確かめたあとに、数え方を直す。8章）。
  - グループごとの書き込みが競合した（`'version'`）ら、その回は何も変えずに、次の回に回す。想定外のエラーは、そのグループだけを失敗として数え、ほかのグループは続けて、最後に投げる（Cronの実行を失敗にする）。
  - 脱退月がすでに締められていれば、確定と同時に、送金が済んでいるメンバーは脱退済みになる。最後の1人の脱退は、確定と同時にグループを削除する。
- 固定費の自動登録（実装は `worker/src/recurringRun.ts` の `registerDueRecurring`。`runScheduled` が、**脱退の確定のあとに**呼ぶ。確定は固定費を止める（5章）ので、順番を逆にしない）：
  - 対象：`paused_at` が無く、`start_month` 以降、`end_month` 以前（または未設定）のテンプレート。**予定の月（`scheduled_month`）は、グループの今月（タイムゾーン）だけ**。過去の月の分は、Cronが止まっていても、停止していた固定費を再開しても、あとから作らない（Cronが予定日の当日中に動かなかったときも、その月の分は作られない）。
  - 予定の月の `day_of_month` に達したら（グループのタイムゾーンの今日 >= 予定日）、支出を作る。`day_of_month` がその月の日数より大きい（31日指定の4月、29〜31日指定の2月など）ときは、月末日に作る。支出の日付も月末日にする。
  - 登録先の月（`target_month`）は、予定の月が未締めならその月。早めに締められていれば、最も古い未締めの月（通常は翌月）。日付は予定日のまま。この場合、翌月には翌月分の支出も作られ、2件になる。
  - 登録者（`created_by_member_id`。必須の列）は、支払者にする。`category` 以外の負担は、作るときに、テンプレートの金額と個別の負担設定から計算して `expense_allocations` に保存する（支出の登録と同じ。あとから変えない）。
  - **作らないとき**（生成記録は残さない。次の回にまた判定する）：①費目をアーカイブしている（固定費は止めない。費目を戻すか、選び直すと作る。9章の「固定費API」）。②支払者・負担の対象に、登録先の月に使えないメンバー（`isMemberAvailable`。8章）が1人でもいる。脱退の確定が競合・予算で遅れても、脱退した人の支出は作らず、確定で固定費が止まる（`payer_left`・`member_changed`）と、以後は対象にならない。
  - 書き込みは、**グループごとに1回の `writeToGroup`**（その回に作る固定費をまとめて。バージョンは1つだけ上がる）。複数行を1文にまとめる（`insertRowsGuarded`）が、個別の負担は「固定費 × メンバー」行なので、文の数はメンバーの数で増える（上限50件・2人の均等割りで、探す1回を含めて24クエリ。人数の上限の5人で50件の金額指定なら、1グループで32（実測）。脱退の確定と同じ回に動くと、合わせてFreeの上限を超えうる。`worker/test/recurringRun.test.ts`）。そこで、**読んだあとに、書く文の数を数え（`writeCost`）、残りの予算に収まる件数（固定費のID順の先頭から）だけ作る**。収まらない固定費は、生成記録が無いままなので、次の回が作る（`postponedGroups` に入る）。外部キーの順は、支出 → 負担額 → 生成記録。
  - 負担額は、支出の登録と同じ `buildAllocations` で計算する（金額指定の合計の検査も同じ）。保存した設定が合わない固定費（行が無い、金額指定の合計が金額と違う。あってはならない不整合）は、**その固定費だけ飛ばし**、ログに残して `invalidTemplates` に数える。同じグループのほかの固定費は作る。定期処理は、直るまで気づけるように、毎回、最後に失敗として投げる。
  - **検索の結果を、書く内容に使わない。** 最初の検索（止まっていない固定費をすべて読み、作る時期に来たグループを探す）は、どのグループを調べるかを決めるだけ。グループごとに、バージョンを読んだ**あとで**、固定費・個別の負担設定・メンバー・締めた月を読み直す（8章。古い金額や、停止前の状態で支出を作らない）。検索は毎時、止まっている・終了した固定費も含めて固定費の表を全部読む（生成記録は主キーで引く。`worker/test/recurringRun.test.ts` でプランを確かめている）。
  - 作るときは `recurring_expense_runs` に `(recurring_expense_id, scheduled_month)` を入れる。主キーの一意制約で二重作成を防ぐ。作った支出をユーザーが消しても記録は残るので、作り直さない。`writeToGroup` の失敗は、次のように扱う（8章）。
    - `'unique'`: `recurring_expense_runs` に、作ろうとした(固定費, 予定の月)の行が**あることを読んで確かめたうえで**、正常として次の回に回す（全体が取り消されているので、何も作られていない。記録のある固定費は次の回で対象から外れ、残りが作られる）。行が1つも無ければ、別の原因（後続のSQLへの `GROUP_WRITE_GUARD` の付け忘れなど、実装の誤り）なので、正常にせずエラー（そのグループの失敗）として記録する。`'unique'` は、どの制約に違反したかを区別せず、メッセージの形にも頼れないため、そのまま「作成済み」と決めつけると、固定費が作られないまま気づけない。バージョンの競合（下の `'version'`）とは違い、`'unique'` は、バージョンを上げずに生成記録が入った異常なときにだけ起きる。
    - `'version'`: その実行ではやり直さず、次の時間のCronに回す。Cronは1時間ごとで冪等なので問題なく、利用者の操作との競合が続いても、1回の実行が長引かない。
  - 支出の作成は、通常の支出登録と同じく `data_version` を上げる（8章）。
  - D1のクエリ数の予算は、脱退の確定と共有する（`QUERY_BUDGET_PER_RUN`。cron.ts）。確定のあと、探す1回と1グループ分の最小の費用（`ESTIMATED_QUERIES_PER_RECURRING_GROUP`。12。見積もりではなく、手を付ける最低限の目安）が収まらなければ、その回は見送る（`skipped`）。収まる範囲でグループのID順に処理し、残りは次の回に回す（`postponedGroups`）。1グループの失敗で、ほかのグループを止めず、最後にCronの実行を失敗にする（脱退の確定と同じ）。
- テンプレートの変更は、まだ作っていない月の分から反映する。作成済みの支出は変更しない（当月分だけ直したいときは、作られた支出を編集する）。
  - 今月の分をまだ作っていない固定費の変更は、今月の分から効く（予定日の前なら）。**登録・再開・日や開始月の変更で、新しく今月の予定日を過ぎた状態にしたときは、今月の分を作らない**（企画メモ7章「設定変更は原則として翌月以降に反映」。すぐに作ると、手で入力した今月分と二重になる）。APIが、今月の分を「作らなかった」記録として、`recurring_expense_runs` に支出のID無し（`expense_id` が `NULL`）で残す（付録A-5のDDLが想定している）。応答の `thisMonthSkipped` で知らせるので、アプリは「今月の分は作られません。必要なら支出を直接登録してください」と案内できる。もともと作る時期に来ていた（Cronがまだ作っていないだけの）固定費の変更では、記録しない。**アーカイブした費目のせいで見送られていた固定費も、この「もともと作る時期に来ていた」ものとして扱う**（費目を選び直しても、費目を戻しても、記録しない。見送られていた今月の分は、次の回の自動登録が作る）。登録・再開は、利用者が「ここから始める」と決める操作なので、今月の分を作らない。費目の障害が解けただけの場合は、決めていた予定どおりに作る。手で入力済みなら二重になりうるが、二重は一覧で見えて、1件消せば直る（消した分は作り直されない）。作られないほうは気づきにくいので、作る側に倒している。

## 8. 同時操作・トランザクション

D1には対話的トランザクションがなく、`batch()` 単位でのみアトミック。`batch()` は直列に実行され、途中のSQLエラーで全体がロールバックされる。ただし、UPDATEやINSERT ... SELECTの対象が0件だっただけでは失敗しない。

### `expense_groups.data_version` と `write_token`

グループ内のデータへの書き込み（支出・割合・費目・固定費・締め・精算・繰越・参加・脱退・招待の発行と取り消し・グループ設定）は、すべて同じ方式で競合を検出する。

1. Workerが現在の `data_version`（`v`）を読む。そのあとで、検証と計算に使うデータを読み、検証と計算を行う（**バージョンが先**。下の注意）。
2. リクエストごとに一意な `write_token`（UUID）を作る。
3. batchの最初のSQLで、バージョンを上げ、tokenを書く。

   ```sql
   UPDATE expense_groups SET data_version = data_version + 1, write_token = ?token
    WHERE id = ?group AND data_version = ?v;
   ```

4. 後続のSQLは、すべて「`expense_groups.write_token` がこのリクエストのtokenと一致する」ことを条件にする。INSERTは `INSERT ... SELECT ... WHERE EXISTS (...)` の形、UPDATE・DELETEは `AND EXISTS (...)` を付ける。

   ```sql
   INSERT INTO expenses (...)
   SELECT ?, ?, ...
    WHERE EXISTS (SELECT 1 FROM expense_groups WHERE id = ?group AND write_token = ?token);
   ```

5. 最初のUPDATEの `meta.changes` が0なら、他のリクエストが先に書き込んでいる。このとき後続のSQLも条件を満たさず、何も変更されていない。

**注意：** 後続の条件を「`data_version = v + 1`」にしてはいけない。同じ `v` を読んだ別のリクエストが先に確定すると、バージョンは `v + 1` になっているため、0件だったはずの後続SQLが実行されてしまう。

**注意（読む順序）：** バージョンは、計算に使うデータより**先に**読む。データを先に読み、あとでバージョンを読むと、その間に入った別の書き込みの新しいバージョンと、古いデータを組み合わせてしまう。楽観ロックは通るので、別のリクエストの更新を黙って上書きする（lost update）。バージョンを先に読めば、間に入った書き込みはバージョンの不一致として検出される。検証用のデータの読み取りを増やすときも、この順序を崩さない。

実装は `worker/src/groupWrite.ts` の `writeToGroup`（後続SQLの条件は `GROUP_WRITE_GUARD`）。1つのグループへの書き込みは、必ずこれを通す（複数のグループにまたがるアカウント削除は、下の `writeToGroups`）。行数が多い書き込み（月締め）は、同じ条件つきで複数行を1文にまとめる `insertRowsGuarded` を使う（文の数を抑えるため。クエリ数の数え方は、下の「D1のクエリ数の数え方」。1文に束縛できる値は100まで）。検査は `worker/test/groupWrite.test.ts`（ローカルD1）で、次を確かめてある。

- 古いバージョンで書くと、後続のINSERT・UPDATE・DELETEは何も変更しない。同じバージョンを読んだ複数のリクエストが書くと、成功するのは1つだけ。
- 「`data_version = v + 1`」の簡略形では、負けた側の後続SQLまで実行される（上の注意の実例。テストに入っている）。
- バージョンを後に読む順序では、別のリクエストの更新が上書きされる（上の注意の実例。テストに入っている）。
- 失敗の理由は2種類に分けて返す。呼び出し側の扱いが違うため（下の「競合したとき」）。
  - `'version'`: 最初のUPDATEが0件。他のリクエストが先に書いた。グループが存在しない場合も、ここに来る（404にしたいAPIは、先にグループを読んで確かめる）。
  - `'unique'`: 一意制約違反（`UNIQUE constraint failed`）。batch全体（バージョンの更新も含む）がロールバックされる。バージョンが合っていたときだけ後続のSQLが実行されるので、この違反は読み直しても同じ結果になる。
- CHECK・外部キー違反は実装の誤りなので、競合にせず例外のまま投げる。
- **ローカルD1で確かめたのはロジックまで。** ローカルD1（miniflare）は `batch` を直列に実行するので、並行して走ったときの性質は確かめていない。一意制約違反の判定がメッセージ文字列頼みであることも含め、本番D1での確認は公開前に行う（13章の9）。ローカルD1のエラーは `D1_ERROR: UNIQUE constraint failed: ...` で、元のメッセージが `cause` にも入る。判定は `cause` もたどる。

#### 複数のグループにまたがる書き込み（`writeToGroups`）

アカウント削除のように、複数のグループを1回の `batch()` で書くときの方式（実装は `worker/src/groupWrite.ts`）。

- バージョンを上げる文は、**1文**の UPDATE。全グループの `data_version` が読んだとおりのときだけ、全グループのバージョンを上げて、同じ `write_token` を書く。1つでも合わなければ、どのグループも変えない（グループごとに別々のUPDATEにすると、一部だけ書き込めた状態が残る。`worker/test/writeToGroups.test.ts` に実例）。
- 後続のSQLは、自分のグループの `GROUP_WRITE_GUARD` で足りる。token を書くのは、この1文だけで、全グループか、どのグループにもか、のどちらかになるため。
- グループ・バージョンは、`json_each` の1つの束縛で渡す（1文に束縛できる値は100まで。グループの数に制限されない）。
- バージョンを上げる文に、追加の条件を足せる。アカウント削除は、「読んだあとに、新しいグループのメンバーになっていない」をここで確かめる（「どのグループのメンバーか」は、バージョンより前に読むしかないため）。外すと、処理の途中で別のグループに参加された本人が、匿名化されずに残る（テストに入っている）。
- `expense_groups` の行を消す文は、ほかの文の最後にまとめる（先に消すと、そのグループの token の条件で、後続の文が効かなくなる）。
- ローカルD1では、1文のUPDATEで全グループが上がること、`json_each` の条件が通ることまでを確かめた。並行して走ったときの性質は、本番D1で確認する（13章の9）。

### D1のクエリ数の数え方（Freeの上限）

- Freeは、1回の呼び出し（HTTPリクエスト、Cronの1回）につき、D1のクエリが50回まで（Paidは1000）。公式の [D1 Limits](https://developers.cloudflare.com/d1/platform/limits/)（2026-11-20に更新）は、この上限について、`db.batch()` を、文の数によらず**1回**と数えると書いている（例：2,000文のbatchは通り、2,000回の個別のクエリは失敗する）。Singfolioのdocsも同じ。batch の外のクエリは、1つずつ数える。
- **このリポジトリは、安全側に、batch の文も1つずつ数えている**（`prepare` の数。`worker/test/monthApi.ts` の `countingEnv`）。以前の見積もりが、公式と食い違う前提で作ってあったので、確かめるまでは、公式の記述にも頼らない（本番のFreeで確かめる。13章の9）。公式のとおりなら、実際の消費は、ここでの数より少ない。コード・テスト・docsの「D1のクエリ数」「予算」は、すべて、この1文ずつ数えた数。
- 確かめたあとの直し方：数える対象を、batch 1回に直す。Cronの予算（`QUERY_BUDGET_PER_RUN`）は、batch の外の読み込み（グループごとに1回ずつ）を数えるので、仕組みは残し、数え方だけを直す（1回に確定・登録できるグループが増える）。月締めの費目の上限（`MAX_CATEGORIES_PER_GROUP`）の根拠と、アカウント削除のグループ数の見積もり（12章の最初の項目）は、緩む。
- `insertRowsGuarded`（複数行を1文にまとめる）は、どちらの数え方でも残す。文の数を抑える狙いは、クエリ数だけでなく、文の準備・束縛のCPU時間（Freeは10ms）にもある（CPU時間への効きは、測っていない）。
- Workersの subrequest は、Freeは1回の呼び出しにつき50（D1・R2・KVなどのCloudflareのサービスへの呼び出しと、`fetch()` が対象）。内部サービス向けの別枠（1,000）があるが、どの呼び出しがどちらに数えられるかは、公式のページに書いてない（[Workersの上限](https://developers.cloudflare.com/workers/platform/limits/)、2026-11-19に更新）。アカウント削除は、D1が約10回、Apple・Googleへの `fetch()` が最大3回（公開鍵の取得、認可コードの交換、失効）なので、どちらの数え方でも収まる。

### 競合したとき

- 支出の登録・編集・削除、割合の変更、招待の発行・取り消しなど：Worker内で読み直して、1回だけやり直す。それでも競合したら409。`worker/src/groupWrite.ts` の `writeToGroupWithRetry` を使う。試行ごとにバージョンを読み、そのあとで、渡した `plan` が検証用のデータを読む。**検証用のデータの読み込みは、`plan` の中だけで行う**（外で読むと、バージョンより前に読むことになる）。
- 月締め・精算・繰越・参加・脱退を選ぶ・取り消す：やり直さず409を返し、アプリに最新の状態を読み直してもらう（確認ダイアログの内容が変わりうるため）。
- アカウント削除（`deleteAccount`）：読み直して数回（3回）までやり直す。それでも競合したら、何も変えずに失敗を返し、`POST /auth/delete` は503を返す（再認証に使った T は使用済みなので、アプリは再認証からやり直す）。
- バージョンの競合（`'version'`）だけが、やり直しの対象。一意制約違反（`'unique'`）は読み直しても同じ結果なので、やり直さない。業務上の扱いは呼び出し側が決める。
  - API：二重締め、すでに参加している、など。409を返す。
  - Cronの固定費の自動登録：`'unique'` は、作成済みであることを確かめたうえで正常として次へ進む。`'version'` は、その実行ではやり直さず、次の時間のCronに回す（7章）。

### 支出の対象月

- 支出は、登録する月（`target_month`）と日付（`expense_date`）を別に持ち、両者の関係は制限しない。入力漏れの書き方は利用者に任せる（内容に「先月分の○○」と書く、日付を月初にする、実際の日付のままにする、など）。
- 登録できる月は、未締めの月のうちカレンダー上の今月以前のもの。今月がすでに締められていれば、翌月。締めは古い月から順に行うので、未締めの月は連続している。通常は「今月（と、未締めなら前月）」、今月を早めに締めた後は「翌月」だけになる。
  - 下端は、最後に締めた月の翌月。まだ締めていなければ、グループを作った月（グループのタイムゾーン）。それより前の月に登録できると、未締めの月が連続しなくなるため。新しいメンバーは、これに加えて、参加（復帰）した月より前には登録できない（5章）。
  - 上端は、今月（グループのタイムゾーン）。下端のほうが新しければ（今月を締めた後）、下端と同じ。
  - 実装は `worker/src/months.ts` の `registerableRange`。
- アプリは、表示中の月を登録先にする。日付の既定値は今日。
- `target_month` が登録できる月であることは、Workerが読んだ時点で確認する。月締めもバージョンを上げるので、確認後に締められた場合は競合として検出される。やり直した検証で、その月は「登録できない月」として断られる（409 `month_not_registerable`）。
- 支出の支払者・負担の対象にできるメンバーは、その月に使えるメンバー（`worker/src/expenses.ts` の `isMemberAvailable`）。`deleted`・`left` は選べない。`active`・`leaving` は、参加（復帰）した月（`history_from_month`）から、脱退月までの月に選べる。脱退月は、脱退が確定していれば `expense_end_month`、脱退を選んだだけ（Cronの確定前）なら `leave_requested_month`（5章）。脱退月まで選べるのは、脱退が翌月1日のCronで確定した場合に、まだ締めていない脱退月の支出を、脱退者の支払として登録できるようにするため。

#### 認証API（実装済み）

実装は `worker/src/auth.ts`（入口）と `worker/src/login.ts`（ログインの処理）、`worker/src/appleWeb.ts`（AndroidのAppleログイン。コールバックとログイン）、`worker/src/appleNotification.ts`（Appleのサーバー間通知）、`worker/src/deleteAccount.ts`（アカウントの削除の入口と、再認証の手順）。`nonce.ts`・`idToken.ts`・`identity.ts`・`session.ts`・`appleToken.ts`・`appleClientSecret.ts` とあわせて、Singfolioの同名のファイルのコピー（コピー元: singfolio 61e0a82）。このアプリで変えたところは、各ファイルの先頭のコメントに書いてある（`deleteAccount.ts` のデータを消す処理は `accountDeletion.ts` を呼ぶ、`appleWeb.ts` の戻り先のURLスキームと文言、AppleのReturn URL（`APPLE_CALLBACK_URL`）をコードの定数ではなく `wrangler.jsonc` の `vars` に置く、`/auth/logout-others` は持たない）。コピーしたファイルの構造は、Singfolioの差分を手で取り込めるよう保つ（整形・分割をしない）。

| API | 本文 | 成功 |
|---|---|---|
| `POST /auth/nonce` | `{ "kind": "native" }`。`{ "kind": "web", "challenge": "<43字のbase64url>" }` も受け付ける（AndroidのAppleログイン用。その T は `/auth/apple/login` だけが受け付け、`/auth/login` に送ると必ず401） | 200 `{ nonce, expiresAt }`。有効は5分。D1に書かない（認証の要らない入口が書くと、Freeの書き込みの上限を使い切られる） |
| `POST /auth/login` | `{ "provider": "apple" \| "google", "idToken", "nonce" }`（`nonce` は直前に受け取った値） | 200 `{ session }` |
| `POST /auth/logout` | なし。`Authorization: Bearer <session>` | 204（本文なし） |
| `GET /auth/apple/callback` | クエリ `code`（または取りやめの `error`）と `state`。Appleが、Services IDのReturn URLへ戻すときのもの | 302。アプリのURLスキーム（`warikan-seikatsu://auth/apple`）へ、`code`・`state`・`error` を付けて戻す |
| `POST /auth/apple/login` | `{ "code", "nonce", "verifier" }`（`nonce` は `web` の T、`verifier` は V。4KBまで） | 200 `{ session }` |
| `POST /auth/delete` | 再認証の本文（下記）。`Authorization: Bearer <session>` | 200 `{ appleRevoked: true \| false \| null }` |

- アプリの手順：`/auth/nonce` で `nonce`（以下 T）を得る → T の SHA-256 の base64url（43字）を、Apple / Googleのサインインの `nonce` に渡す → 得たIDトークンと T を `/auth/login` に送る → 返った `session` を端末のSecureStoreに置き、以降は `Authorization: Bearer <session>` で送る（URLに載せない。ログにも出さない）。
- AndroidのAppleログイン（Web経由）の手順。AndroidにはAppleのネイティブのサインインが無いので、Appleの認可のWebのフロー（`appleid.apple.com/auth/authorize`）をブラウザ（Custom Tab）で開く。方式と理由の全体は、Singfolioの docs/singfolio-publishing-backend.md §8「AndroidのAppleログイン（Web経由）」。
  - アプリは、乱数の検証用の値 V を作り、`C = SHA-256(V)` の base64url（43字）を `/auth/nonce` に `{ "kind": "web", "challenge": C }` で送って T（web）を得る。V と T は、アプリのメモリにだけ置く。
  - 認可のURL：`client_id` に Services ID、`redirect_uri` に `APPLE_CALLBACK_URL`（Appleの設定のReturn URLと同じ）、`response_type=code`、`response_mode=query`、`state` と `nonce` に `SHA-256(T)`（同じ値）。名前・メールは要求しない（スコープなし）。
  - Appleは、コールバック（`GET /auth/apple/callback`）へ `code` と `state` を付けて戻し、コールバックが、アプリのURLスキームへ302で戻す。**戻り先は Worker のコードに固定で持ち、リクエストのパラメータからは決めない**（オープンリダイレクトにしない）。`code`・`state`・`error` は形を確かめ、URLエンコードして渡す。何も保存せず、Appleを呼ばず、D1にも触れない。
  - アプリは、戻ってきた `state` が `SHA-256(T)` と同じかを確かめてから、`code`・T・V を `/auth/apple/login` に送る（他のアプリが押し込んだ `code` を送らないため）。同じカスタムURLスキームを持つ別のアプリが `code` と `state` を横取りしても、T も V も無いので使えない（V は PKCE の代わり）。
  - Workerの順序：T の署名・種別（`web`）・期限 → **`SHA-256(V)` が T の中の C と一致するか（Appleを呼ぶ前。通らなければ呼ばない）** → Appleの `/auth/token` で認可コードを交換（`client_id` は Services ID、`redirect_uri` は `APPLE_CALLBACK_URL`）→ IDトークンの検証（`aud` は Services ID、`nonce` は `SHA-256(T)`）→ T を使用済みに → `resolveIdentity` → セッションの発行。D1に書くのは、IDトークンの検証が通ったあとだけ。失敗の応答は `/auth/login` と同じ（400・401・503・405・413。理由は教えない）。
  - 交換で得る `refresh_token`・`access_token` は、ログインでは、読まず、保存せず、ログにも出さない（アカウントの削除だけが、失効のためにメモリの中で使う）。Appleの `invalid_grant`（無効・期限切れ・使用済みのコード）は401、それ以外（通信の失敗・5xx・`invalid_client`・`invalid_request` など）は503。**設定の不備（`invalid_client`）は、本物のコードで試すまで分からない**（でたらめなコードには、設定が間違っていても常に `invalid_grant` が返る。Singfolioでの測定）。切り分けのため、失敗の分類だけを1行 `console.error` に出す（コード・トークン・Appleの応答の本文は出さない。Workers Logsは無効のままなので、`wrangler tail` で見る）。
  - `/auth/apple/login` は、認証なしで、Appleの `/auth/token` を呼ばせられる（T は `/auth/nonce` から誰でも得られる）。**WAFのRate limiting rules（リポジトリの外。Cloudflareのダッシュボード）で、このパスに1ルールを置く**（Pathが `/auth/apple/login`、IPで数える、目安は5件/10秒、Block。Freeは1ルール）。デプロイのときに作る（利用者の作業。12章）。
  - iOSの `sub` とAndroid（Services ID）の `sub` が、同じになるかは、本物のトークンで確かめる（Services IDを、このアプリのバンドルIDを primary App ID にして作れば、iOSのアプリと同じグループになり、資格情報は共有されるとAppleの資料にある。Singfolioのアプリとは、グループにしない）。違うと、AppleでのOSをまたぐ引き継ぎはできない（13章の9）。
  - アプリ側の、認可コードを得る部分は、次のとおり（Singfolioからのコピーを元にした。`src/repositories/appleWebSignInRepository.ts` が、認可のURLの組み立て・戻りのURLの読み取り・`state` の照合・取りやめや時間切れの判定。`platform/authBrowser.ts` が、expo-web-browser・Linking・AppState への接続。`app/+native-intent.tsx` が、戻りのURLを画面の遷移にしない）。`T`・`V`・`C` の生成、`/auth/*` を呼ぶHTTP、セッションの保存は、次の項目。それらをつなぐ層は、まだ無い（12章の「認証の残り」）。Services ID と Return URL は、アプリにも同じ値を持つ（コードは共有しない。`worker/test/config.test.ts` が一致を固定）。仮の値のあいだ、アプリは、ブラウザを開かず `provider-unavailable` で断る（Appleの「無効なクライアント」の画面が出て、利用者が閉じたように見えるのを避ける）。
  - **Custom Tab を開いているあいだに、アプリのプロセスが終わったときは、ログインはやり直しになる。** 戻りのURLは起動時のURLとして届き、`app/+native-intent.tsx` が `'/'` にして、ルートから始める（まだログインしていないので、docs/screens.md 1章のとおり、ログイン画面に着く）。認可コードは拾わない（`Linking` の `url` イベントは、起動時のURLでは発火しない）。`T`・`V` はメモリにしか無く（上の「V と T は、アプリのメモリにだけ置く」）、プロセスと一緒に消えているので、拾っても使えない。利用者には、何も言わずにログインが終わり、ログイン画面に戻ったように見える。ログイン画面を作るときに、起動時のURLからコードを拾う処理を足さない。
- **アプリ側の認証の土台**（Singfolioのアプリ側の同名のファイルのコピーを元にした。コピー元のコミットと、このアプリで変えたところは、各ファイルの先頭のコメント。構造・名前は、Singfolioの差分を手で取り込めるよう保つ）：
  - `T`・`V`・`C` の生成（`src/services/authCrypto.ts`。乱数とSHA-256の実体は注入し、`platform/authCrypto.ts` が expo-crypto を渡す）。`V` は32バイトの乱数の base64url（43字）。`C` と `SHA-256(T)` は、**文字列（UTF-8）の** SHA-256 の base64url（43字。Workerの `nonceHash` と同じ。`V`・`T` をデコードしたバイト列のハッシュではない）。想定の形でなければ、使わず `unexpected` で止める。
  - `/auth/*` を呼ぶHTTP（`src/repositories/apiClient.ts` が共通の扱い、`authRepository.ts` が各API）。再試行しない。401は `unauthorized`、429と5xx（JSONでない応答を含む）は本文を読まず `unavailable`、通信の失敗と時間切れ（10秒。`/auth/delete` だけ30秒）は `network`、ほかの4xxは `invalid-request`。`/auth/delete` の403だけ、本文の `error` で `reauth-failed`・`account-mismatch`。**`/auth/delete` の500と503は、どちらも `unavailable`**（上の「アプリが守ること（delete）」のとおり、層は、どちらも再認証からやり直す。401のときだけ、端末のセッションを捨てる）。Cookieは送らない・受け取らない。セッション・IDトークン・`T`・`V`・認可コードは、エラーの `message` にも載せない。`/auth/logout-others` は持たない（このアプリのWorkerに無い）。
  - セッションの保存（`src/repositories/sessionRepository.ts`。`platform/secureStorage.ts` が expo-secure-store を渡す）。SecureStoreのキー `warikan-seikatsu.session` の1つに、`{ v, session, provider }` のJSONを置く。読めない（壊れた値・知らない版・読み取りの失敗）ときは、投げずに `unreadable` で返す（値は消さない。扱いは層が決める。下の「サインインの層」）。Androidで、Keystoreの鍵が無い・`BadPaddingException` のときは、`expo-secure-store` が値を自分で消して `null` を返すので、`unreadable` ではなく `none` になる。**Singfolioと違い、ローカルDBの識別子を持たない**（Singfolioは、再インストールのあと、ローカルは空なのにセッションだけが生きている状態を避けるために結びつける。このアプリは、データがすべてサーバーにあり、端末にローカルDBが無いので、セッションが残っても、同じアカウントのデータが見えるだけ。代わりに、再インストールの印で、前のセッションを捨てる。下の「サインインの層」）。Keychainの項目は `WHEN_UNLOCKED_THIS_DEVICE_ONLY`。
  - **`expo-secure-store` の config plugin は、`app.json` に足さない**（`npx expo install expo-secure-store` は、自動で足す。足したら外す）。足すと、Androidのバックアップ規則が `<include domain="sharedpref">` になり、将来、端末に置くデータ（ローカルDBなど）がバックアップから外れる。iOSには、使っていないFace IDの文言（`NSFaceIDUsageDescription`）も足される。この2つは、plugin のオプション（`configureAndroidBackup: false`・`faceIDPermission: false`）で止められるが（57.0.4 のソースを読んで確認。ビルドでは確かめていない）、止めると plugin は何もしないので、足す理由が無い。`requireAuthentication` を使うなど、Face IDの文言が要る機能を使うときに、オプションつきで足すかを見直す。plugin が無くても、Androidのバックアップから戻された値は、Keystoreの鍵が移らず復号できない。`expo-secure-store` は、そのときの値を自分で消して `null` を返す（ソースで確認。復元そのものは、確かめていない）ので、`none`（サインインしていない）になり、`unreadable` にはならない。`USE_BIOMETRIC`・`USE_FINGERPRINT`（`androidx.biometric` が足す）は、`app.json` の `blockedPermissions` が外している。
  - **サインインの層**（`src/services/accountService.ts`。Singfolioの同名のファイルを元にした。`platform/accountService.ts` が、HTTP・セッションの保存・各社のサインイン・再インストールの印をつなぐ）：
    - 画面が使う `accountService`（`getSignedInProvider`・`signIn`・`signOut`・`deleteAccount`）と、APIを呼ぶ層だけが使う `sessionAccess.withSession`（セッションの値を画面に渡さない）。Singfolioと違い、`signOutOthers`（Workerに無い）と、ローカルDBの識別子を持たない。各社のサインインを待つ上限は5分（`T` の期限と同じ。過ぎたら `timeout`。OSの画面は閉じられない）。サインイン・ログアウト・削除は1本ずつ順に実行する（`withSession` は巻き込まない）。削除の要求（`/auth/delete`）を送ったあとの `network` と `invalid-response`（Workerが 200 を返すのは、D1を消したあとなので、応答が読めなくても、削除は済んでいるかもしれない）を、`delete-unconfirmed` に変えるのも、この層（`T` の取得などの、送る前の `network` は、そのまま。`unavailable`（429・5xx）は変えない: 何も消えていない）。
    - **保存先を読めない（`unreadable`）値は、「サインインしていない」と同じに扱わない。** `getSignedInProvider`・`deleteAccount`・`withSession` は、`storage-failed` を投げる（画面は「分からない」として扱い、すぐにログイン画面へ送らず、読み直す。端末がロック中の、一時的な失敗かもしれない。**ただし、壊れた値のように、ずっと続くこともある**ので、読み直しても直らないときは、ログイン画面を出す。`signIn` が上書きし、`signOut` が消すので、そこから先へ進める。画面の仕様は、screens.md 1章）。`signIn` は、読めない値が残っていても進めて上書きする（壊れた値が残る端末が、二度とサインインできなくなるため。ユーザーの操作でしか呼ばれないので、ロック中の失敗では起きにくい）。`signOut` は、読めない値も消し、失効を確認できたとは言わない（`serverRevoked: false`）。
    - **再インストールのあと、前のセッションを捨てる（決めた。ログインを残さない）。** iOSのKeychainは、アプリを削除しても残りうる（Androidは消える）。「アプリを消したらログアウトされる」という期待に合わせ、アプリの削除で消える保存先に置いた印（Documentsの `install-marker` ファイル。`platform/installMarker.ts`。Keychainやcacheには置かない）が無い起動では、Keychainのセッション（読めない値を含む）を捨て、サーバーでも失効させる（待たず、失敗は無視する）。**印を先に置いてから捨てる**（印を置けなければ、何も捨てない。順序を逆にすると、印を置けない端末は、起動のたびにログアウトされる）。捨てられなかったとき（ロック中など）は、前のセッションが残る（許すのと同じ状態に戻るだけ）。セッションを読む入口は、すべて、この確認を待つ。**印は、最初のリリースから置いておく**（印の無い版から入れた人は、印を足した版の最初の起動で、ログアウトされる）。**「印が無い = インストール直後」は、iOSの前提で、Androidでは成り立たない**: Androidは、印（`filesDir`）もAuto Backupの対象で（`allowBackup="true"`。除外の規則は無い）、バックアップから戻すと、印も戻り、確認は飛ばされる。実害は無い（Keystoreの鍵が移らず、SecureStoreが復号できない値を消して `none` を返す）。Androidで印に頼る処理を足すときは、注意する。依存は `expo-file-system`（もともとExpoの依存としてネイティブに入っていたものを、直接の依存に固定した）。AsyncStorageは足さない。
    - 組み込むサインイン：iOSのApple（`appleSignInRepository.ts`。`expo-apple-authentication`）、AndroidのApple（Web経由。上の認可コードの経路）。**Googleは、まだ組み込まない**（`signIn('google')` は `provider-unavailable`）。
    - APIの置き場は、`createAuthRepository(fetch)` の既定のまま（`API_ORIGIN`）。ローカルのWorkerに向ける必要が出たら、`platform/accountService.ts` で `options.origin` を渡す（12章の「認証の残り」）。
  - 実機での確認：Android（API 36のエミュレータ）で、`V`・`C`・`SHA-256` の生成（既知の値 `SHA-256("abc")` との一致を含む）と、SecureStoreの保存・読み戻し・削除が、期待どおりに動くことを確かめた（確認のための一時的な画面で。コミットしていない。2026-11-23）。**iOS（Keychain。`WHEN_UNLOCKED_THIS_DEVICE_ONLY`）は、未確認**（iOSのネイティブビルドは、このリポジトリではまだ作っていない）。Androidのバックアップからの復元も、確かめていない。
  - 層と再インストールの印の確認：Androidエミュレータ（API 36。arm64）で、実際の `expo-file-system`（`files/install-marker`）とSecureStoreを使い、印が無い起動で前のセッションを捨てて失効を頼むこと、印がある起動では残ること、壊れた値が `storage-failed` になること、Googleが `provider-unavailable` になることを確かめた（一時的な画面で。コミットしていない。2026-11-23）。**iOSでの、アプリの削除で印が消え、Keychainのセッションが残ること（この対策の前提）、iOSでのAppleのサインイン（`app.json` に `expo-apple-authentication` の plugin を足した。entitlement `com.apple.developer.applesignin` が入る。ビルドの前に、Apple Developerで、App ID の Sign in with Apple を有効にする）は、未確認。**
  - APIを呼ぶ先 `API_ORIGIN`（`src/repositories/apiClient.ts`）は、本番のドメインが決まるまで、仮の値（`https://not-created-yet.invalid`）。12章の「公開前に埋める認証の値」。
- アカウントは、初めてのログインで作られる（登録の操作は無い）。作られた直後はグループに入っていない（グループを作るか、招待で参加する）。同じ `sub` でも、AppleとGoogleは別のアカウントで、自動ではつなげない。保存するのは `sub` と手段（`apple` / `google`）だけで、メール・名前は受け取っても捨てる。
- 受け付けるIDトークンの `aud` は、T の種別に合う1つだけ。Apple（iOS。`native`）は `APPLE_BUNDLE_ID`（`com.yskms.warikanseikatsu`）、Apple（Android。`web`）は `APPLE_SERVICES_ID`（Services ID。予定の名前は `com.yskms.warikanseikatsu.web`）、Googleはサーバー用（Web）のクライアントID（`GOOGLE_WEB_CLIENT_ID`。iOSでもAndroidでも同じ）。もう一方の `aud` のトークンは拒否する。すべて `wrangler.jsonc` の `vars`。
- T は使い切り。IDトークンの検証まで通ったあとに使用済みにする（失敗した T は、同じ T で正しいトークンなら通る）。リプレイは401。
- セッションの期限は、最後に使ってから90日（目安）。24時間に1回だけ「最後に使った時刻」を書く（毎回書くと、認証済みのリクエストの数だけ書き込みを使う）。ログインごとに別の値を発行するので、端末ごとに持てる。
- ログアウトは、そのセッションだけを消す。何度呼んでも、知らない値でも204（`Authorization` が無い・形が違うときだけ401）。他の端末のセッションは残る。
- アカウントの削除（`POST /auth/delete`。データの規則は5章の「アカウント削除」）：
  - 本文は、再認証。iOSのApple：`{ "provider": "apple", "nonce", "idToken", "authorizationCode"? }`。AndroidのApple：`{ "provider": "apple", "nonce": "<T（web）>", "code", "verifier": "<V>" }`（ログインと同じフローで `code` を得る。T と V の結びつけも同じ）。Google：`{ "provider": "google", "nonce", "idToken" }`。`nonce`（T）とIDトークンは、ログインと同じ手順で新しく得る（使い切り。ログイン時のものは使えない）。ユーザーIDは受け取らず、セッションから決める。本文は10KBまで。
  - `provider` は、セッションを作ったログイン手段と同じでなければならない（違うと400。アプリの取り違え）。再認証のIDトークンの `sub` が、ログイン中のアカウントの `sub` と同じでなければ、消さない（別のAppleアカウント・Googleアカウントで再認証しても通さない）。
  - 順序：セッションの認証 → T の検査 → （AndroidのApple：V の照合と、認可コードの交換でIDトークンを得る）→ IDトークンの検証 → `sub` の一致 → T を使用済みに → （iOSのApple：認可コードの交換）→ **データを消す**（`accountDeletion.ts`）→ Appleのトークンの失効。AndroidのAppleは、本人確認の交換で、失効に使うトークンも同じ応答から得る（コードは1回限りなので、交換は1回）。失効は、そのトークンを得たときの `client_id`（Services ID）で行う。外部への待ちは、消す前に済ませる（消したあとに待つのは、失効の1回だけ）。アプリが先に打ち切っても、消す前なら何も消えず、やり直せる。
  - Appleのトークンの失効は、**あとから、削除を止めずに**行う。`authorizationCode` が無い、交換・失効に失敗した、鍵の設定が不備、のいずれでも、アカウントは消え、`appleRevoked: false` を返す（アプリは、Appleの設定から連携を解除できると案内する）。Googleは失効するものが無く `null`。`refresh_token`・`access_token` はメモリの中で交換から失効へ渡して終わり、D1・ログ・応答には出さない。失効の失敗は、分類だけを1行ログに出す（コード・トークン・Appleの応答の本文は出さない）。
  - 鍵（`APPLE_PRIVATE_KEY`）が読めなくても、削除は止まらない。公開前に本物の鍵を置くことを、デプロイ前の確認で担保する（12章の「公開前に埋める認証の値」）。
  - D1のクエリ数は、batch の文を1つずつ数える安全側の見積もりでは、グループの数と構成によって、Freeの上限（50）に当たることがある（残る人がいるグループだけなら5グループ以上、自分だけのグループなら3つ以上。12章の最初の項目）。公式のとおり batch を1回と数えるなら、グループの数によらず約10回で、当たらない（8章の「D1のクエリ数の数え方」。本番のFreeでの確認は13章の9）。当たったときは、未処理の例外（500）になり、何も消えない。
  - アプリが守ること（delete）：**503 は、理由によらず、再認証（新しい T）からやり直す。** 公開鍵を取れなかったときの503は T を使い切っていないが、応答では区別しない（区別すると、コピー元との差分が増える）。**500 は、何も消えていないものとして扱い、セッションは捨てず、再認証からやり直す。** やり直しの結果が401なら、すでに消えている（または、セッションが失効した）ので、端末のセッションを捨てる。403 では捨てない。
- Appleのサーバー間通知（`POST /auth/apple/notifications`）。Appleが、アプリとの連携の解除（`consent-revoked`）と、Apple Accountの削除（`account-deleted`）を送る。方式と理由の全体は、Singfolioの docs/singfolio-publishing-backend.md §8「Appleのサーバー間通知」。
  - 本文は `{ "payload": "<JWS>" }`（16KBまで）。Apple DeveloperのSign in with Appleの設定（primary App ID。Services IDが同じグループ）に、`https://<本番のドメイン>/auth/apple/notifications` を登録するまで、通知は届かない（デプロイのあと、利用者が行う。TLS 1.2以上が要る。12章）。
  - 検証：署名（IDトークンと同じ公開鍵のキャッシュ。`alg` はRS256のみ、`kid` 必須）、`iss`（`https://appleid.apple.com`）、`aud`（**バンドルIDとServices IDのどちらでもよい**。通知がどちらの `client_id` で来るかは、資料に書かれていない）。`exp`・`iat` は必須にしない（資料の例に `exp` が無い）。通らなければD1に何も書かず、401（どの検査かは教えない）。公開鍵を取れなければ503、本文の形の不備は400、413、405。通らなかった理由は、固定の語彙だけを1行 `console.error` に出す（`aud` の食い違いなどの設定の不備は、これでしか切り分けられない。通知の中身・トークンは出さない）。
  - `events` は、オブジェクトでも、JSONの文字列でも読む。`type`・`sub`・`event_time` が必須。`event_time` は、秒でもミリ秒でも読み（1e11未満なら秒）、受け取った時刻を超える値は、受け取った時刻に丸める。`email-enabled`・`email-disabled`・知らない種類は、200で何もしない。
  - 単位は、その Apple の `sub` の `identities` の行。**`consent-revoked`**：取り消しの時点（`event_time`）より前に作られたセッションだけを消し、`identities.consent_revoked_at` に `event_time` を記録する（1つのバッチ）。取り消しのあとにサインインし直した端末を、遅れて届いた通知でログアウトさせない。同じ通知の再送は、何も変えない。データ（グループのメンバー行など）は消さない。**`account-deleted`**（`account-delete` の綴りも読む）：順序を見ずに処理する（消えたApple Accountは戻らない）。このアプリは、1つのアカウントに1つのログイン手段しか持たない（AppleとGoogleは自動ではつなげない）ので、**アカウントごと消す**。データの処理は、`POST /auth/delete` と同じ `accountDeletion.ts`（残る人のいるグループは匿名化、自分だけのグループは消す。5章の「アカウント削除」）。**データを消す前に、その行のセッションを先に消す**（Singfolioには無い）。データの削除は、競合し続ける、D1のクエリ数の上限に当たる、などで何も消せないことがあり、そのままだと、Apple Accountを消した人のセッションが、ログイン中の端末から使える状態で残る。先に消せば、どう失敗しても、セッションは残らない（グループのデータとアカウントは、再送されたときに消える）。
  - 競合し続けて消せなかったときは、グループのデータとアカウントは消さず503（セッションは消してある。Appleが再送するかは分からない。再送されなければ、グループのデータとアカウントは、自動では消えないまま残る。12章の「Apple Accountの削除の通知で消せなかったとき」）。同じ通知の再送や、行が無い `sub` は、200。
  - ログインとの競合：通知の処理の最中に、その前に検証を通っていたログインがセッションを作ると、取り消し後のセッションが残りうる。`createSession` が、`consent_revoked_at` が、そのログインの開始時刻と同じか後なら、セッションを作らない（ログインは401。やり直せば通る）。通知の処理（削除と記録）も1バッチなので、どちらが先でも、取り消し後のセッションは残らない。残るリスク（受け入れる）は、Singfolioの docs に書いてある（取り消しの前後の1秒ほどに、サインインが重なったときだけ）。
- アプリ側が守ること（サーバーが前提にしている。守らないと、すべて401になる。本物のトークンで確かめるときに、最初に見る）：
  - Googleは、iOSでもAndroidでも、IDトークンの `aud` を**サーバー用（Web）のクライアントID**にする。iOSは、Google Sign-Inにサーバー用のクライアントIDを設定する（設定しないと `aud` がiOSのクライアントIDになる）。Singfolioの `plugins/withGoogleSignIn.js`（`GIDServerClientID`）が手本。
  - IDトークンの `nonce` は必須で、T の SHA-256 の base64url と一致しなければならない。GoogleもAppleも、`nonce` を渡せるサインインのAPIを使い、渡した値がそのままトークンに入ることを確かめる。変換しない。Singfolioの `src/repositories/googleSignInRepository.ts`・`appleSignInRepository.ts` が手本。

| 状態 | `error` | 意味 |
|---|---|---|
| 400 | `invalid_request` | 本文の形が不正（`provider`・`idToken`・`nonce` の欠落や型、JSONでない。nonce：`kind` が `native`・`web` 以外、`native` に `challenge` が付いている、`web` で `challenge` が無い・形が違う。`/auth/apple/login`：`code`・`nonce`・`verifier` の欠落や形の違い（`code` は印字できるASCII 1〜1024字、`verifier` は43字のbase64url）。callback：`code` と `error` が両方ある・どちらも無い、`code`・`state`・`error` の形が違う。delete：`authorizationCode` の形が違う、Googleに `authorizationCode` が付いている、`idToken` と `code`・`verifier` が混在している、`code`・`verifier` の形が違う、再認証の `provider` がセッションと違う） |
| 401 | `unauthorized` | ログイン：T・IDトークンの検証に通らない。どの検査で落ちたかは教えない。ログアウト：`Authorization` が無い・形が違う。delete：セッションが無い・期限切れ・失効済み（アプリは、このときだけ端末のセッションを捨てる） |
| 403 | `reauth_failed` / `account_mismatch` | delete のみ。`reauth_failed`：再認証が通らない（T・IDトークンの不備、使用済みの T）。`account_mismatch`：再認証は通ったが、ログイン中のアカウントと別のアカウント。どちらも何も消さず、セッションも残る（アプリは、サインアウトさせない） |
| 405 | `method_not_allowed` | POST 以外（`/auth/apple/callback` は GET・HEAD 以外） |
| 413 | `payload_too_large` | 本文が大きすぎる（nonce 1KB、`/auth/apple/login` 4KB、login・delete 10KB） |
| 500 | なし（Workerの未処理の例外。本文は決めていない） | delete のみ。D1のクエリ数の上限（Free）など。何も消えていない。アプリの扱いは上の「アプリが守ること（delete）」 |
| 503 | `service_unavailable` | Apple / Googleの公開鍵を取得できない、またはAppleの認可コードの交換が使えない（5xx・通信の失敗・`invalid_client` など。`/auth/apple/login`・AndroidのAppleのdelete。どれもトークンの問題ではない。アプリがやり直せる）。delete：データの削除が、他の書き込みと競合し続けた（何も消えていない。T は使用済みなので、再認証からやり直す） |

#### 招待・参加・脱退API（実装済み）

実装は `worker/src/invites.ts`（招待・参加）と `worker/src/leave.ts`（脱退を選ぶ・取り消す）。認証・エラーの形・月の形式は、支出APIの「共通」と同じ。グループを作るAPIは、次の「グループAPI」。

| API | 本文 | 成功 |
|---|---|---|
| `POST /groups/:id/invites` | なし | 201 `{ invite: { id, token, expiresAt, createdAt } }`。`token`（平文）は、この応答でだけ返す |
| `GET /groups/:id/invites` | なし | 200 `{ invites: [{ id, expiresAt, createdAt }] }`（自分が発行した、未使用で期限内のもの） |
| `DELETE /invites/:id` | なし | 204（発行した人だけ。すでに取り消し済みでも204） |
| `GET /invites/:token` | なし | 200 `{ alreadyMember: false, groupName, invitedByDisplayName, expiresAt, groupFull }`。すでに参加中なら 200 `{ alreadyMember: true, groupId }` |
| `POST /invites/:token/join` | `{ "displayName": "…" }` | 201 `{ groupId, memberId }` |
| `POST /groups/:id/leave` | なし | 200 `{ leaveRequestedMonth, confirmed }`。最後の1人の脱退が確定したときは、`groupDeleted: true` も付く |
| `DELETE /groups/:id/leave` | なし | 200 `{ leaveRequestedMonth: null }` |

- 招待トークンは、256ビットの乱数（base64url の43字）。D1にはSHA-256のハッシュだけを置く。期限は発行から3日、使い捨て。`/invites/:x` は、GET が招待トークン、DELETE が招待のID。形が違えば404。
- 発行できるのは、脱退が確定していない参加中のメンバー（`leaving` 以降と、脱退月が終わったメンバーは403）。1人が持てる、未使用で期限内の招待は10件まで（409 `too_many_invites`）。グループの人数が上限（5人。5章の「参加」）なら、発行できない（409 `group_full`）。
- 確認（GET）は、URLを開いただけでは何も変えない。使えない招待（知らないトークン・期限切れ・使用済み・取り消し済み・発行者が抜けた）は、理由を区別せず404 `invite_unavailable`。すでにそのグループに参加中なら、招待の状態によらず `alreadyMember: true`。`groupFull` は、グループの人数が上限で、いま参加すると 409 `group_full` になるか（5章の「参加」と同じ数え方）。満員でも招待は有効なので、404にはしない。アプリは、表示名を入力させる前に「満員です」と出せる。
- 参加（POST）: 人数が上限（発行のあとに、ほかの招待で埋まった）なら409 `group_full`（`left` の人の復帰も同じ）。表示名は必須（前後の空白を落として1〜20文字。コードポイントで数える）。色はサーバーが選ぶ（他の参加中のメンバーと重ならない最初の色。色は10あり、人数の上限の下では使い切らない。関数としては、全色が使われていれば、使われている数で一巡する）。色のキーは、仮の一覧 `pink, red, orange, yellow, green, teal, blue, purple, brown, gray`（`worker/src/membership.ts` の `MEMBER_COLORS`。アプリの色の一覧と揃える）。参加の中身は5章。
- 参加・脱退を選ぶ・取り消すは、やり直さずに409 `conflict`（同じ招待で同時に参加すると、片方だけが参加し、もう片方は409）。招待の発行・取り消しは、読み直して1回だけやり直す（8章）。
- 脱退を選ぶ: `leaveRequestedMonth` は、グループのタイムゾーンの今月。脱退月がすでに締められていれば、その場で確定する（`confirmed: true`。5章）。
- 脱退の取り消しは、確定するまで。脱退月が終わったあとは、Cronの確定の前でも取り消せない（409 `leave_confirmed`）。

| 状態 | `error` | 意味 |
|---|---|---|
| 401 | `unauthorized` | セッションが無い・無効・期限切れ |
| 403 | `forbidden` | 招待の発行：脱退が確定した（確定したものとして扱う）メンバー |
| 404 | `not_found` | グループ・招待が無い、メンバーでない、脱退済み・削除済み、発行した人でない（取り消し）。区別しない |
| 404 | `invite_unavailable` | 招待の確認・参加：使えない招待 |
| 409 | `already_member` | 参加：すでに参加中。`{ groupId }` を添える |
| 409 | `too_many_invites` | 招待の発行：未使用の招待が上限 |
| 409 | `group_full` | 招待の発行・参加：グループの人数が上限（5人） |
| 409 | `invite_already_used` | 招待の取り消し：すでに使われている |
| 409 | `leave_already_requested` | 脱退を選ぶ：すでに選んでいる |
| 409 | `leave_confirmed` | 脱退を選ぶ・取り消す：すでに確定した（脱退月が終わったものを含む） |
| 409 | `not_leaving` | 脱退の取り消し：選んでいない |
| 409 | `conflict` | 他のリクエストの書き込みと競合した（8章） |

#### グループAPI（実装済み）

実装は `worker/src/groups.ts`（入力の検査は `worker/src/groupInput.ts` と `worker/src/memberInput.ts`）。認証・エラーの形・月の形式は、支出APIの「共通」と同じ。アプリとは、コードを共有せず、この節を正として両側に書く。

| API | 本文 | 成功 |
|---|---|---|
| `POST /groups` | `name`・`displayName`・`timezone` が必須、`currencyCode`（既定 `JPY`）と `id`（作成の識別子）は任意 | 201 `{ group }`。同じ `id` の再送は 200 `{ group }` |
| `GET /groups` | なし | 200 `{ groups: [{ id, name, currencyCode, currencyMinorUnit, timezone, createdAt, memberId, memberStatus, historyFromMonth, leaveRequestedMonth, expenseEndMonth }] }`（作成の古い順） |
| `GET /groups/:id` | なし | 200 `{ group }` |
| `PATCH /groups/:id` | `name`・`currencyCode` のうち変えるもの（1つ以上） | 200 `{ group }` |
| `PATCH /groups/:id/members/me` | `displayName`・`color` のうち変えるもの（1つ以上） | 200 `{ group }` |

`group`（作成・詳細・変更の応答）：

```json
{
  "id": "…", "name": "ふたりの生活費", "currencyCode": "JPY", "currencyMinorUnit": 0,
  "timezone": "Asia/Tokyo", "createdAt": 1790000000000,
  "memberId": "…", "currencyLocked": false,
  "seatedMembers": 2, "maxMembers": 5, "canInvite": true,
  "members": [{ "id": "…", "displayName": "…", "color": "pink", "status": "active",
                "historyFromMonth": "2026-11", "leaveRequestedMonth": null, "expenseEndMonth": null, "isMe": true }]
}
```

- `members` は、脱退済み・削除済みも含む全員（IDの昇順。名前は残す。5章）。ユーザーのIDは返さない。`memberId` は操作している本人のメンバー。`currencyLocked` は、通貨を変えられないか（2章）。画面が変更の入口を出すかを決めるため。`seatedMembers` は人数の上限で数える人数、`maxMembers` は上限（5章の「参加」）、`canInvite` は、いま招待を発行できるか（本人の脱退が確定していない、かつ `seatedMembers` が上限未満。未使用の招待の上限 `too_many_invites` は含まない）。画面が招待の入口を出し分けるため。
- 一覧に出るのは、データを扱えるグループ（`active`・`leaving`）だけ。脱退済み・削除済みのグループは出さない。
- 作成：グループ名は1〜30文字、表示名は1〜20文字（前後の空白を落とす。コードポイントで数える。制御文字は不可）。`timezone` は、アプリが端末のIANA名（`Asia/Tokyo` など）を送る（必須）。実行環境が知っている名前だけを通し、`+09:00` のようなオフセットは断る。月の境目（今月）を決めるので、黙って既定値にしない。通貨は選べる通貨だけ（2章。違えば400 `currencyCode`）。
  - 1回の `batch()` で、グループ・自分のメンバー行・初期の費目と、その月の割合（自分100%）・上限額なしの設定を書く（新しいグループには競合する相手がいないので、バージョンは読まない。グループの行を `write_token` つきで作り、後続の文に `GROUP_WRITE_GUARD` を付ける）。D1のクエリ数は、書き込みの文が5(batch1回)、認証1と、作成後に読むグループ・メンバー・通貨固定の3文を含めて9(`worker/test/groups.test.ts` で数えている)。
  - 初期の費目は、家賃・食費・日用品・光熱費・外食・通信費・その他（screens.md 2章）。アイコン・色のキーは仮の値（`worker/src/groups.ts` の `DEFAULT_CATEGORIES`。アプリの一覧と揃える）。名前は日本語で固定（アプリが日本語だけのため）。
  - `id` は、費目の登録の再送と同じ仕組み（UUIDの小文字）。同じ `id` が、他の人のグループなら、中身を返さず409 `conflict`。同時に同じ `id` で作っても、成功するのは1つ。
  - 1人が作れるグループの数に上限は設けていない（12章）。
- 変更：変わるものが無ければ(同じ名前、同じ通貨)、書かずに現在の状態を返す(バージョンを上げない。同時の他のメンバーの書き込みを、不要に競合させないため。自分の名前・色と、費目の変更も同じ)。グループ名と通貨は、脱退が確定した（確定したものとして扱う月の終わりを含む）メンバーは403。他のメンバーは、全員が変えられる。通貨は、金額に関わるものが無いときだけ変えられる（2章。いまと同じ通貨を送るのは、固定されていても通る）。読み直して1回だけやり直す（8章）。やり直した検証で固定されていれば、409 `currency_locked`。
- 自分の名前と色：脱退が確定したあとも直せる（締めた月に出るのは、締めた時点の名前なので、締めた月は変わらない）。色は、メンバーの色の一覧（`pink, red, orange, yellow, green, teal, blue, purple, brown, gray`）のキーだけ。他のメンバーと同じ色も選べる（重ならない色を自動で選ぶのは、参加のときだけ）。

| 状態 | `error` | 意味 |
|---|---|---|
| 401 | `unauthorized` | セッションが無い・無効・期限切れ |
| 403 | `forbidden` | グループ名・通貨の変更：脱退が確定したメンバー |
| 404 | `not_found` | グループが無い、メンバーでない、脱退済み・削除済み。区別しない |
| 409 | `currency_locked` | 通貨の変更：金額に関わるものがある |
| 409 | `conflict` | 作成：他の人が使っている `id`。変更：他のリクエストの書き込みと競合した（8章） |

#### 費目・負担割合API（実装済み）

実装は `worker/src/categories.ts`（入力の検査は `worker/src/categoryInput.ts`）。認証・エラーの形・月の形式は、支出APIの「共通」と同じ。アプリとは、コードを共有せず、この節を正として両側に書く。

費目（`Category`）：`{ "id": "…", "name": "食費", "icon": "cart", "color": "green", "sortOrder": 1, "archivedAt": null }`。

| API | 本文 | 成功 |
|---|---|---|
| `GET /groups/:id/categories` | なし | 200 `{ categories: [Category] }`（`sortOrder`、`id` の順。アーカイブした費目も含む） |
| `POST /groups/:id/categories` | `name`・`icon`・`color` が必須、`id`（作成の識別子）は任意 | 201 `{ category }`。同じ `id` の再送は 200 |
| `PATCH /categories/:id` | `name`・`icon`・`color`・`archived`（真偽）のうち変えるもの（1つ以上） | 200 `{ category }` |
| `PUT /groups/:id/categories/order` | `{ categoryIds: [...] }`（全費目をアーカイブ済みも含めて、並べたい順に） | 200 `{ categories }` |
| `GET /groups/:id/months/:month/category-shares` | なし | 200 `{ month, closed, editable, memberIds, categories: [Rule] }` |
| `PUT /groups/:id/months/:month/category-shares/:categoryId` | `{ shares: [{ memberId, basisPoints }], cap?: { memberId, capMinor } \| null, currencyCode? }` | 200 `{ month, rule, overriddenMonths }` |

`Rule`：`{ "categoryId": "…", "sourceMonth": "2026-10", "shares": [{ "memberId": "…", "basisPoints": 5000 }], "cap": null, "archived": false }`。`sourceMonth` は、その月の割合が書かれている月（その月以前で最も新しい行。3章）。

- 費目の名前は1〜20文字。`icon`・`color` は、アプリの一覧のキー。サーバーは形（英小文字・数字・`_`・`-` の30字まで）だけを見て、一覧は持たない（知らないキーは、アプリが既定の見た目で出す）。
- 費目は削除せずアーカイブする（`archived: true`）。アーカイブした費目は、新しい支出で選べない（409 `category_not_available`）。過去の支出と割合は残る。すでにアーカイブしていれば、`archivedAt` は最初のまま。`archived: false` で戻せる。アーカイブした費目の固定費は、止めずに、自動登録だけを見送る（9章の「固定費API」）。
- 作成：新しい費目の `sortOrder` は、いまの最大の次。同じ `id` を同じグループで同時に送っても、片方が読み直して保存済みの費目を200で返す(409になるのは、別のグループが使っている `id` だけ。グループの作成と同じ)。1グループの費目は、アーカイブ済みを含めて30まで（仮の値。月締めの書き込みが費目の数に応じて増えるため。Freeでの実測は9章の月締めの項目。超えると409 `too_many_categories`）。月の設定と割合も同じ書き込みで書く（3章）。
- 並べ替え：グループの全費目（アーカイブ済みを含む）を送る。読んだあとに費目が増えた・知らないIDがある、で合わなければ409 `categories_changed`（読み直してもらう）。
- `GET .../category-shares`：割合が1つも無い費目（作る前の月）は含めない。`memberIds` は、その月の割合に入るメンバー（参加（復帰）した月から脱退月まで。削除したユーザーも、削除した月まで）。`editable` は、保存の入口を出してよいか（締めていない、直せる月、脱退が確定していない）。参加前の月は403。
- `PUT`：その月の割合を、置き換える（その月の設定と割合の行を消して書き直す）。
  - **直せる月は、登録できる月と同じ範囲**（8章の `registerableRange`）。締めた月は409 `month_closed`、それより先（今月より後、作成前）は409 `month_not_editable`（`{ from, to }`）。
  - `shares` は、`memberIds` の全員を、合計10000で送る。過不足は409 `members_changed`（`{ memberIds }` に、いま必要なメンバー）。画面を開いたあとにメンバーが増減したとき。削除したユーザーを外したいときは、0%にする（5章）。割合の形が違う・合計が10000でない、は400 `shares`。
  - `cap` を付けると上限額つき（3章）。上限を負担する人は、`shares` の中にいること（0%でよい）。外すときは、`cap` を送らないか `null`。上限額は1〜10^12（400 `cap.memberId`・`cap.capMinor`）。
  - 変更は「選んだ月とそれ以降」に効くが、**この月より後に、別の行がある月は書き換えない**。後の月の行は、メンバーの増減で書いた割合（アカウント削除・脱退の確定が書く、残るメンバーでの均等）で、上書きすると、その月に居ないメンバーが割合に残る。そうした月は `overriddenMonths` で知らせる。アプリは、「X月以降は別の設定があります」と案内できる。
  - `currencyCode` は、上限額を入力したときの通貨(2章)。違えば409 `currency_mismatch`。
  - アーカイブした費目の割合も直せる。
- 読み直して1回だけやり直す（8章）。競合が続けば409 `conflict`。月締めもバージョンを上げるので、確認のあとに月が締められると、やり直した検証で `month_closed` になる。

| 状態 | `error` | 意味 |
|---|---|---|
| 401 | `unauthorized` | セッションが無い・無効・期限切れ |
| 403 | `forbidden` | 脱退が確定したメンバーの変更。参加前の月の取得・変更 |
| 404 | `not_found` | グループ・費目が無い、メンバーでない、脱退済み・削除済み、他のグループのID。区別しない |
| 409 | `too_many_categories` | 費目の作成：上限 |
| 409 | `categories_changed` | 並べ替え：全費目と合わない |
| 409 | `month_closed` | 割合の変更：締め済みの月 |
| 409 | `month_not_editable` | 割合の変更：直せる月の範囲外。`{ from, to }` を添える |
| 409 | `currency_mismatch` | 割合の変更・支出の登録と編集：送られた `currencyCode` が、グループの通貨と違う。`{ currencyCode }` にグループの通貨を添える（2章） |
| 409 | `members_changed` | 割合の変更：その月のメンバーと合わない。`{ memberIds }` を添える |
| 409 | `conflict` | 作成：他のグループが使っている `id`。変更：競合した（8章） |

#### 支出API（実装済み）

実装は `worker/src/expenses.ts`（入力の検査は `worker/src/expenseInput.ts`、権限の判定は `worker/src/access.ts`）。アプリとは、コードを共有せず、この節を正として両側に書く。

共通：

- 認証は `Authorization: Bearer <セッションの値>`。本文・応答はJSON。HTTPSでないリクエストは403。
- ID（グループ・支出・費目・メンバー）は、英数字・`-`・`_` の64字まで。形が違うパス、知らないパスは、JSONの404 `{ "error": "not_found" }`。
- 知らない項目、型や範囲の違う値は400 `{ "error": "invalid_request", "field": "<直す項目>" }`（`split.shares` のように、入れ子は `.` でつなぐ。値は返さない）。空の本文など、項目を特定できないときは `field` を付けない。本文の上限は16KB（超えたら413）。
- 金額は通貨の最小単位の整数（`amountMinor`、1〜10^12）。割合は1万分率の整数（`basisPoints`）。
- 月は `YYYY-MM`、日付は `YYYY-MM-DD`（実在する日付）。内容（`description`）は任意で、前後の空白を落とし、空なら `null`。100文字まで（コードポイントで数える）。

支出（`Expense`）：

```json
{
  "id": "…", "expenseDate": "2026-11-19", "targetMonth": "2026-11",
  "description": "スーパー", "amountMinor": 4280,
  "categoryId": "…", "payerMemberId": "…", "createdByMemberId": "…",
  "recurringExpenseId": null,
  "splitMethod": "category",
  "allocations": [{ "memberId": "…", "burdenMinor": 500, "shareBasisPoints": null }],
  "createdAt": 1790000000000, "updatedAt": 1790000000000
}
```

`allocations` は、`category` 以外の支出の確定負担額（メンバーのID順）。`category` では `[]`（月の集計で計算する。3章）。`shareBasisPoints` は割合指定（`ratio`）のときだけ入る。

| API | 本文・クエリ | 成功 |
|---|---|---|
| `GET /groups/:id/expenses?month=YYYY-MM` | `month` は必須 | 200 `{ month, closed, expenses: [Expense] }`。日付の新しい順（同じ日付は登録の新しい順）。`closed` は、その月が締め済みか |
| `POST /groups/:id/expenses` | `expenseDate`・`targetMonth`・`amountMinor`・`categoryId`・`payerMemberId`・`split` が必須、`description`・`currencyCode`（金額を入力したときの通貨。2章）・`id`（登録の識別子。下の「二重送信」）は任意 | 201 `{ expense }`。同じ `id` の再送は、200 `{ expense }`（保存済みの支出） |
| `PATCH /expenses/:id` | 登録と同じ項目のうち、変えるものだけ（1つ以上）。`description` は `null` で消す。金額を送るときは `currencyCode` も添える | 200 `{ expense }` |
| `DELETE /expenses/:id` | なし | 204 |

負担の指定（`split`）：

| `method` | 項目 | 備考 |
|---|---|---|
| `category` | なし | 費目の割合で分ける（既定） |
| `equal` | `memberIds`（1人以上、重複なし） | 均等割り。端数は固定順（2章） |
| `ratio` | `shares: [{ memberId, basisPoints }]` | 合計10000。0%のメンバーも入れられる（端数は配らない） |
| `fixed` | `amounts: [{ memberId, amountMinor }]` | 合計が `amountMinor` と一致（違えば400 `split.amounts`） |
| `single` | `memberId` | 1人が全額負担 |

二重送信（同じ登録の再送）：

- 通信が途切れると、アプリは、登録が成功したか分からないまま同じ登録を送り直す。支出が2件できないよう、アプリは**登録の画面を開くたびに支出のID（UUID。`crypto.randomUUID()` の形の、小文字）を作り、`id` として送る**。Workerは、UUID以外（短い値、連番、大文字）を400 `id` で断る（支出のIDは、全グループで一意な主キー。形を許すと、アプリの実装ミスが、無関係なグループの409になる）。同じ登録の再送では、同じ `id` を使う。新しい登録には、新しい `id` を使う（成功したあとの「もう1件登録する」で、前の `id` を使い回さない。使い回すと、新しい内容が保存されず、前の支出が返る）。
- Workerは、同じ `id` の支出が、**同じグループに、同じメンバーが登録したもの**として残っていれば、何も書かずに、保存済みの支出を200で返す（バージョンも上がらない）。送られた内容は見比べない。最初の登録のあとに編集されていれば、編集後の状態を返す。登録できる月・メンバーの検査より前に判定するので、再送の間に月が締められても、同じ結果になる。認証・所属・書き込みの権限の確認は、再送でも先に行う。
- **アプリの実装での注意:** iOSのネイティブの `UUID().uuidString` は大文字を返す。そのまま送ると、登録がすべて400 `id` になる。小文字のUUIDを返す関数を使うか、送る前に `toLowerCase()` を通す。
- 同じ `id` を、別のメンバーが登録した支出、別のグループの支出が使っているときは、競合と同じ409 `conflict` にする（中身も、どのグループのものかも返さない）。IDが使われているかどうかは、409か登録できるかの違いで分かるが、`id` をUUIDに限るので、当てずっぽうで探すことはできない（`access.ts` の「区別せず404」と同じ水準では隠していない）。別のグループが同じ `id` を同時に登録したときは、グループごとにバージョンが別なので、一意制約違反（8章の `'unique'`）になり、同じく409。
- 最初の登録と再送が同時に走っても、成功するのは1つ（8章の競合制御）。負けた側は、やり直した判定で、勝った側の支出を見つけて200を返す。
- 消した支出の `id` の再送は、新しい登録として扱う（IDからは、消したことが分からない。登録と削除の間に再送が届くのは、まれ）。
- `id` を送らなければ、Workerが決める（再送は防げない）。`PATCH` では、`id` を送れない（400 `id`）。固定費の自動登録は、`recurring_expense_runs` で二重作成を防ぐ（7章）ので、この仕組みは使わない。

編集の規則：

- 送らなかった項目は変えない。`split` を送ると、負担額を丸ごと置き換える（`category` に戻すと負担額を消す）。
- **`category` 以外の支出の金額を変えるときは、`split` も送る**（無ければ400 `split`）。画面で確認した負担を、サーバーが勝手に計算し直さないため。金額を変えずに内容や日付だけ直すときは、保存した負担額をそのまま残す。
- 支払者・負担の対象は、その月に使えるかを、**新しく選んだメンバー（支払者を変えた、負担の指定に加えた）と、負担額が増えるメンバー**について検証する。脱退・削除したメンバーが入った既存の支出でも、内容や日付は直せる。負担の指定ごと送り直しても、その人の負担額が増えなければ通る。「増える」は、保存した負担額（金額）と比べる。そのため、割合を上げても、金額を下げて負担額が増えなければ通る。逆に、削除したユーザーを含む均等割り・割合割りは、金額を上げると全員の負担額が増えるので断られる（金額指定に切り替えれば、そのメンバーの負担額をそのままにして上げられる。画面の案内は screens.md 4章）。一方、本人が異議を出せない相手（削除したユーザーなど）に、負担を寄せ直すことはできない。`targetMonth` を変えるときは、全員分見直す。グループに居るかは、どのメンバーも必ず見る。
- アーカイブした費目の支出は、費目を変えないかぎり、編集できる（別の月に移すことも含む。アーカイブの判定は、費目を選ぶときだけ）。
- 登録する月を変えるときは、移し先が登録できる月（8章）であること。
- 締め済みの月の支出は、編集も削除もできない（409 `month_closed`）。

エラー：

| 状態 | `error` | 意味 |
|---|---|---|
| 401 | `unauthorized` | セッションが無い・無効・期限切れ |
| 403 | `forbidden` | 脱退が確定したメンバー（`leaving`）、または脱退月が終わったメンバー（5章）の書き込み。参加前の月の一覧 |
| 404 | `not_found` | グループ・支出が無い、メンバーでない、脱退済み・削除済み、他のグループのID、参加前の月の支出。区別しない（IDの存在を教えない） |
| 409 | `month_not_registerable` | 登録先の月が登録できない（締め済み、先すぎる、作成前、参加前）。`{ from, to }` に登録できる範囲を添える |
| 409 | `month_closed` | 編集・削除の対象が締め済みの月 |
| 409 | `member_not_available` | 支払者・負担の対象が、その月に使えない。`{ memberId }` を添える |
| 409 | `category_not_available` | アーカイブした費目 |
| 409 | `currency_mismatch` | 送られた `currencyCode` が、グループの通貨と違う。`{ currencyCode }` を添える（2章） |
| 409 | `conflict` | 読み直してやり直しても、他のリクエストの書き込みと競合した（8章）。入力は残して、読み直してもらう |

他のグループの費目・メンバーのIDを指定したときは、404でなく400。`field` は、費目なら `categoryId`、支払者なら `payerMemberId`、負担の対象なら負担の方法に合わせた項目（`split.memberId`・`split.memberIds`・`split.shares`・`split.amounts`）。

#### 固定費API（実装済み）

実装は `worker/src/recurring.ts`（入力の検査は `worker/src/recurringInput.ts`）。毎月の自動登録は7章（`worker/src/recurringRun.ts`）。認証・エラーの形・金額と月の形式は、支出APIの「共通」と同じ。アプリとは、コードを共有せず、この節を正として両側に書く。

固定費（`RecurringExpense`）：

```json
{
  "id": "…", "description": "家賃", "amountMinor": 80000,
  "categoryId": "…", "categoryArchived": false,
  "payerMemberId": "…",
  "split": { "method": "category" },
  "dayOfMonth": 25, "startMonth": "2026-11", "endMonth": null,
  "pausedAt": null, "pausedReason": null,
  "createdAt": 1790000000000, "updatedAt": 1790000000000
}
```

`split` は、支出の登録の `split` と同じ形（`category` / `equal` の `memberIds` / `ratio` の `shares` / `fixed` の `amounts: [{ memberId, amountMinor }]` / `single` の `memberId`）。`pausedReason` は `manual`（手動で止めた）・`payer_left`（支払者が脱退した）・`member_changed`（メンバーが変わって、個別の負担の見直しが要る）。

| API | 本文 | 成功 |
|---|---|---|
| `GET /groups/:id/recurring-expenses` | なし | 200 `{ recurringExpenses: [RecurringExpense] }`。作った時刻の古い順（同じならID順）。止めたもの・終了したものも含む |
| `POST /groups/:id/recurring-expenses` | `amountMinor`・`categoryId`・`payerMemberId`・`split`・`dayOfMonth`・`startMonth` が必須、`description`・`endMonth`・`currencyCode`（2章）・`id`（登録の識別子。支出と同じ「二重送信」。UUID（小文字）だけ）は任意 | 201 `{ recurringExpense, thisMonthSkipped }`。同じ `id` の再送は、200 `{ recurringExpense, thisMonthSkipped }`（保存済みのもの。最初の応答を受け取れなかったときも、案内を出せる） |
| `PATCH /recurring-expenses/:id` | 登録と同じ項目（`id` を除く）のうち、変えるもの（1つ以上）と、`paused`（真偽） | 200 `{ recurringExpense, thisMonthSkipped }`。`thisMonthSkipped` は、登録・変更・再送のどれでも同じ意味：**書いたあとに、今月の分の「作らなかった」記録（支出のIDが無い生成記録）があるか**。記録が残っているかぎり、止めて再開しても、ほかの項目を直しても `true`（今月の分は、実際に作られないため）。今月に支出を作った記録は、数えない |
| `DELETE /recurring-expenses/:id` | なし | 204。一度も支出を作っていない固定費だけ（今月の分は作らなかった記録だけなら消せる） |

- **削除（`DELETE`）は、一度も支出を作っていない固定費だけ。** 作った支出と生成記録が参照するので、一度でも作った固定費は消せない（409 `recurring_expense_in_use`。止める（`paused: true`）か、`endMonth` で終わりの月を決める）。間違えて作った固定費が、上限の件数と、通貨のロック（グループ情報の `currencyLocked`。2章）に残り続けないための入口。「作った」かは、生成記録の `expense_id` で見る（支出を作った記録。外部キーではなく、支出を消しても残る）。**今月の分は作らなかった記録（`expense_id` が `NULL`。7章）は数えず、固定費と一緒に消す。** 数えると、予定日を過ぎてから登録した固定費（月の途中の登録はよくある）が、ほとんど消せなくなる。生成記録は、支出と同じ書き込みで作る（7章）ので、支出を作った記録が無ければ、参照する支出も無い。消す間際に自動登録が作れば、バージョンが上がるので、読み直して判定し直し、消さずに409になる。**一度でも作った固定費が1件でも残っていれば、通貨は変えられないまま**（金額を持つので。生成した支出を消しても同じ）。
- 毎月の日（`dayOfMonth`）は1〜31。その月に無い日は月末日（7章）。`startMonth` は、グループの今月より前でもよい（作るのは今月の分から。7章）。`endMonth` は `startMonth` 以降（片方だけ送ったときも、保存してある相手と比べる。400 `endMonth`・`startMonth`）。
- 1つのグループの固定費は、終了・停止したものを含めて50まで（仮の値。`MAX_RECURRING_EXPENSES_PER_GROUP`。グループごとに全固定費の負担設定を読み、毎回の自動登録が書く行の数も、固定費に比例して増えるため。7章のとおり、1回に作る件数は予算に収まる分だけに区切るので、上限は、読む量の歯止め。一度も支出を作っていないものは `DELETE` で外せる。超えると409 `too_many_recurring_expenses`）。
- 登録の検査：費目は他のグループのIDなら400 `categoryId`、アーカイブした費目なら409 `category_not_available`。支払者・負担の対象は、グループに居なければ400（`payerMemberId`・`split.memberIds` など）、使えなければ409 `member_not_available`（`{ memberId }`）。**使えるかは、最初に支出を作る月で見る**（8章の `isMemberAvailable`。`startMonth` と今月の遅いほうが予定の月で、今月を早めに締めていれば、その翌月。自動登録と同じ決め方: `recurringTargetMonth`。APIは通すのに、Cronが黙って見送る、を避ける）。金額指定の合計が金額と合わなければ400 `split.amounts`。`currencyCode` が違えば409 `currency_mismatch`。
- **アーカイブした費目の固定費は、止めない。** 自動登録だけを見送る（7章）。一覧に `categoryArchived: true` を返すので、アプリは「費目を戻すか、選び直してください」と案内できる。`paused_reason` に費目の理由を足さないのは、状態（費目のアーカイブ）から導けて、費目を戻せば自動で作られるため。見送られていた今月の分は、費目を戻しても、費目を選び直しても、次の回に作られる（7章。今月の分を作らない記録は残さない）。アーカイブした費目の固定費の、費目以外の項目は直せる。再開の操作では、アーカイブした費目のままだと断る（409 `category_not_available`）。
- 変更：
  - 送らなかった項目は変えない。`description`・`endMonth` は `null` で消せる。
  - **金額指定（`fixed`）の固定費は、金額を変えるとき、`split` も送る**（無ければ400 `split`。金額指定は自動で配分しない）。割合・均等・単独は、金額に依らないので、金額だけ変えられる。
  - `split` を送ると、個別の負担設定を丸ごと置き換える（`category` に戻すと設定を消す）。送ったときは、その全員が検査の月に使えること。送らないときは、新しく選んだ支払者だけを見る（脱退した人が支払者の固定費の、内容や日付は直せる）。
  - 変更は、まだ作っていない月の分から反映する。作成済みの支出は変えない（7章）。
- **止める・再開する。** `paused: true` で `manual` で止める（止まっているものは、時刻も理由も変えない）。`paused: false` で再開する。
  - 再開では、支払者と負担の対象の**全員**が、今使えること（409 `member_not_available`）。支払者が脱退して止まった（`payer_left`）固定費は、`payerMemberId` を使える人に付け替えて再開する。付け替えるだけでは再開しない。
  - **`category` 以外の負担の固定費は、止めた理由によらず、`split` を送り直さないと再開できない**（400 `split`。企画メモ7章の「見直しを促す」。画面で確認した負担を、サーバーが勝手に有効にしない）。止まる理由は1つしか持てないので、手動（`manual`）や支払者の脱退（`payer_left`）で止まっていた間にメンバーが変わっても、`member_changed` にはならない。理由で求めると、見直しなしで再開できてしまう。送り直した負担の対象は、全員が使えること。
  - 再開しても、停止中の月の分は作らない。再開で新しく今月の予定日を過ぎた状態になるなら、今月の分も作らない（`thisMonthSkipped`。7章）。
- 権限：全メンバーが登録・変更できる（グループの設定と同じ。`canEditGroupSettings`）。脱退が確定したメンバーは書き込めず403。一覧は、脱退が確定したメンバーも見られる。他のグループの固定費・メンバーでない人・脱退済みの人は、区別せず404。
- 読み直して1回だけやり直す（8章）。競合が続けば409 `conflict`。

| 状態 | `error` | 意味 |
|---|---|---|
| 401 | `unauthorized` | セッションが無い・無効・期限切れ |
| 403 | `forbidden` | 脱退が確定したメンバーの登録・変更・削除 |
| 404 | `not_found` | グループ・固定費が無い、メンバーでない、脱退済み・削除済み、他のグループのID。区別しない |
| 409 | `too_many_recurring_expenses` | 登録：上限 |
| 409 | `recurring_expense_in_use` | 削除：一度でも支出を作った固定費 |
| 409 | `category_not_available` | アーカイブした費目の選択。アーカイブした費目のままの再開 |
| 409 | `member_not_available` | 支払者・負担の対象が使えない。`{ memberId }` を添える |
| 409 | `currency_mismatch` | 送られた `currencyCode` が、グループの通貨と違う。`{ currencyCode }` を添える（2章） |
| 409 | `conflict` | 登録：他のグループが使っている `id`。変更：競合した（8章） |

### 月締め・精算

#### 月締め・精算API（実装済み）

実装は `worker/src/closings.ts`（月次集計・月締め・締め結果）と `worker/src/transfers.ts`（精算・繰越）。集計の読み込みと計算は `worker/src/monthState.ts` の `loadMonthState` と `computeMonthFromState` にだけ置き、締める前の見込み（summary）と月締めで同じものを使う（締めた結果が、直前の見込みとずれないように）。アプリとは、コードを共有せず、この節を正として両側に書く。認証・エラーの形・金額と月の形式は、支出APIの「共通」と同じ。`:month` が `YYYY-MM` でなければ404。

| API | 本文 | 成功 |
|---|---|---|
| `GET /groups/:id/months` | なし | 200 `{ currentMonth, months }`。ホームの月ピッカー用の月の一覧（下の「月の一覧」） |
| `GET /groups/:id/months/:month/summary` | なし | 200 `MonthView`。締める前の月は現在の支出から計算した見込み（前の月からの繰越を足す）、締めた月は締めた時点の結果 |
| `POST /groups/:id/months/:month/close` | なし | 201 `MonthView`（締めた結果。`close` は付かない） |
| `GET /groups/:id/months/:month/closing` | なし | 200 `MonthView`（締めた月だけ。`close` は付かない） |
| `POST /transfers/:id/settle` | なし | 200 `{ transfer }`（精算済みにする） |
| `POST /transfers/:id/carry` | なし | 200 `{ transfer }`（次の月に繰り越す） |

`MonthView`（締めた月）：

```json
{
  "month": "2026-10", "closed": true,
  "closing": { "id": "…", "closedAt": 1790000000000, "closedByMemberId": "…", "processed": false },
  "totalMinor": 14000,
  "members": [{ "memberId": "…", "displayName": "…", "paidMinor": 10000, "burdenMinor": 7000,
                "differenceMinor": 3000, "carriedInMinor": 0, "netMinor": 3000 }],
  "categories": [{ "categoryId": "…", "totalMinor": 14000,
                   "burdens": [{ "memberId": "…", "burdenMinor": 7000 }] }],
  "transfers": [{ "id": "…", "fromMemberId": "…", "toMemberId": "…", "amountMinor": 3000,
                  "status": "pending", "settledAt": null, "carriedAt": null,
                  "processedByMemberId": null, "canCarry": true }],
  "close": { "closable": false, "reason": "month_closed" }
}
```

- `totalMinor` はその月の支出の総額で、繰越を含めない。`members[].burdenMinor` と `categories` の負担額にも繰越は入らない。繰越は `carriedInMinor`（送金先なら足し、送金元なら引く）と `netMinor`（精算する額 = 差額 + 繰越）にだけ入る（3章・4章）。
- `members` は固定のメンバー順（IDの昇順）。その月に参加している全員（参加月から脱退月まで。削除したユーザーも、削除した月まで）と、支出・費目の割合・繰越に出てくる全員が並ぶ。支出に関わらなくても0で出る。`displayName` は、締めた月では締めた時点の名前。
- `categories` は、支出がある費目だけ（`categoryId` の昇順）。`totalMinor` は個別設定の支出を含む合計、`burdens` は費目の割合による分と個別設定の分の合計で、負担額が0のメンバーの行は無いことがある。
- 締める前の月（`closed: false`）は、`closing` が `null`、`transfers` が見込み（`{ fromMemberId, toMemberId, amountMinor }` だけ。IDも状態も無い。締めるまで確定しない）。締めた月の `transfers` は、送金ごとに状態つき。
- `processed`：すべての送金が `settled` か `carried`（送金が0件の月も true。4章）。
- `canCarry`：未処理で、送金元・送金先がどちらも繰り越せるメンバー（`active` で `leave_requested_month` なし）のときだけ true。アプリが規則を持たなくて済むように返す。
- `close`（summary だけ）：その月を、いま操作しているメンバーが締められるか。締められれば `{ "closable": true }`、締められなければ `{ "closable": false, "reason": "…" }`。`reason` は、月締めの409・403のエラー名と同じ（下の表）で、`previous_month_not_closed`・`previous_month_unsettled` には `month`（先に済ませる月）が付く。まだ締められない月の見込みも、同じ形で返す（アプリが「先に10月を締めてください」を出せるように）。
- まだ始まっていない月も、summary は返す（集計は空に近く、`close.reason` は `month_not_started`）。
- 締めずに飛ばした月（最後に締めた月より前で、締めていない月）の summary は、`closed: false` のまま、`close.reason` が `month_skipped`。「締め済み」ではないので、アプリは `month_closed` と同じ表示にしない。

月の一覧（`worker/src/monthList.ts`。ホームの月ピッカーが、選べる月と状態の印を出すためのAPI。集計はしない）：

```json
{ "currentMonth": "2026-11",
  "months": [{ "month": "2026-10", "status": "unsettled" }, { "month": "2026-11", "status": "open" }] }
```

- `months` は古い順。範囲は、操作者が見られる最も古い月（`historyFromMonth`）から、支出を登録できる最も新しい月まで（8章の「支出の対象月」と同じ `registerableRange` の上端。今月を締めていれば翌月）。アプリが「選べる月」を計算しない。
- 始まりは、`canViewMonth`（`worker/src/access.ts`）が見せる最も古い月と同じ。一覧に並ぶ月は、すべてその人が summary で見られる月（`worker/test/monthList.test.ts` で確かめている）。閲覧期間の制限（Premium。screens.md 3章は、見られない月を鍵の印つきで並べる想定）を足すときは、`canViewMonth` と一覧を合わせる。
- 上端は、本人の脱退月で切らない。脱退が確定した（`leaving`）メンバーには、脱退月より後の月も並ぶ。5章の「脱退」4のとおり、繰り越した額は翌月の送金に作り直され、本人は、その月を開いて精算するため。脱退月より後の月は、支出を記録できない月だが、`status` は、その月の実際の状態を返す。
- `currentMonth` は、グループのタイムゾーンでのカレンダー上の今月で、ホームの初期表示の月。今月を締めていても、翌月にならない。
- `status`：`open`（未締め）、`skipped`（締めずに飛ばした月。最後に締めた月より前で、もう締められない。4章）、`unsettled`（締めたが、未処理の送金が残っている）、`settled`（締めて、すべての送金が処理済み。送金が0件の月も）。保存せず、締めと送金の状態から毎回導く。未処理が残りうるのは、実際には最後に締めた月だけ（前の月の送金が済まないと翌月を締められない）だが、一覧は月ごとに見て、その前提には頼らない。
- エラーは、認証・所属が他のグループ内のAPIと同じ（401、メンバーでない・脱退済み・他のグループのIDは404）。参加前の月は並ばないので、403は無い。
- D1のクエリ数は、認証・権限と、締めた月・最後に締めた月の読み込み（`batch` の2文）で固定。読む行数は、締めた月の数と、その送金の数に比例する（月ごとの `EXISTS` は、未処理が見つかるか、その月の送金を読み終えたところで止まる。`idx_settlement_transfers_group` を使う）。

月締めの書き込み（4章）は、1回の `writeToGroup`（8章）。この月を脱退月に選んでいるメンバーの脱退は、この書き込みの中で確定する（5章）。そのメンバーが最後の1人のときは、締めずにグループを削除し、200 `{ "groupDeleted": true }` を返す。**やり直さず**、競合したら409 `conflict`（確認ダイアログの内容が変わりうるため。アプリは読み直して案内する）。二重締めの同時実行は、片方だけが締まり、もう片方は409 `conflict`（すでに締められたあとなら `month_closed`）。脱退月が、最初の締めで飛ばされた月で、確定していないメンバーがいるときは、締めずに先に確定させ、409 `conflict` を返す（5章の4）。D1のクエリ数は（batch の文を1つずつ数えた、安全側の数。8章の「D1のクエリ数の数え方」）、読み込みが約16（認証・バージョン・権限・状態10・結果5。数は固定）と、書き込みの文の数。書き込みは複数行を1文にまとめている（束縛できる値は1文に100まで。1文に入る行数は、費目の設定・割合が19行、費目ごとの負担が16行、メンバーごとの集計が10行まで）ので、行数に比例して増えず、費目×メンバーの数に応じてゆるやかに増える。小さなグループで実測約25（認証を含む）、費目13・メンバー3で、書き込みは12文（`worker/test/closings.test.ts` の「D1のクエリ数」）。費目30(上限)・メンバー6では、割合を直していない月（前の月の行を引き継ぐ、よくある月）の月締めが実測47で、Freeの上限（1回の呼び出しにつき50）にぎりぎり収まる（引き継ぐ設定30行と割合180行を書き足すので、締める月に行がある月の実測35より約12文増える）。脱退の確定を含むと、引き継ぐ月で実測65、締める月に行がある月でも実測53で、超える（`worker/test/closings.test.ts` の「費目の上限(30)・メンバー6人」。脱退の確定を含む月締めは、1文ずつ数える見積もりでは、Freeに収まらない。公式のとおり batch を1回と数えるなら収まる）。収まる場合も余裕は3文しかなく、メンバーや費目の上限を増やす・書き込みの文を足すときは、この実測を取り直す。脱退の確定が入る月締めは、読み込み2回と書き込み約10文が増える（実測は、費目1つ・メンバー3人で34、費目13で37。`worker/test/closings.test.ts` の「脱退の確定を含む月締め」）。Workers Paid（上限は1回につき1000）へ移せば、1文ずつ数えても問題にならない（Paidへ移すかは未決。12章）。

精算・繰越（4章）：

- 状態は `pending → settled`、`pending → carried` だけ。確定後に戻せない（409 `transfer_not_pending`、`status` に今の状態を添える）。`UPDATE` にも `AND status = 'pending'` を付けている。
- 全メンバー（`active`・`leaving`）が、当事者でない送金も操作できる。ただし、送金のある月を見られるメンバー（参加前の月の送金は404）。
- 繰越は、送金元・送金先に、脱退を選んだ（`leave_requested_month` あり）・`leaving`・`left`・`deleted` のメンバーがいると、409 `transfer_not_carryable`。精算済みにはできる。
- 精算済みにした結果、脱退が確定した（`leaving`）メンバーの未処理の送金が無くなり、脱退月が締められていて、繰越先の月が未締めの繰越も、脱退月より後の未締めの月の支出への関わりも無ければ、そのメンバーを `left` にする（5章の4。同じ `batch` の中）。
- 精算・繰越も、やり直さずに409 `conflict`。応答の `transfer` は、更新後の送金（`canCarry` は false）。

エラー：

| 状態 | `error` | 意味 |
|---|---|---|
| 401 | `unauthorized` | セッションが無い・無効・期限切れ |
| 403 | `forbidden` | 参加前の月の summary・closing。月締めで、操作者がその月のメンバーでない（参加前の月、脱退月が終わった月） |
| 404 | `not_found` | グループ・送金が無い、メンバーでない、脱退済み・削除済み、他のグループのID、参加前の月の送金。区別しない（IDの存在を教えない） |
| 404 | `not_closed` | closing：まだ締めていない月 |
| 409 | `month_not_started` | 月締め：まだ始まっていない月（グループのタイムゾーンで、今月より後） |
| 409 | `month_closed` | 月締め：すでに締められている |
| 409 | `month_skipped` | 月締め：最後に締めた月より前で、締めていない月（飛ばした月。4章） |
| 409 | `previous_month_not_closed` | 月締め：前の月が未締め。`{ month }` に先に締める月を添える |
| 409 | `previous_month_unsettled` | 月締め：前の月の送金に未処理が残っている。`{ month }` を添える |
| 409 | `transfer_not_pending` | 精算・繰越：すでに処理済み。`{ status }` を添える |
| 409 | `transfer_not_carryable` | 繰越：脱退予定・削除したユーザーなどが関わる送金 |
| 409 | `conflict` | 他のリクエストの書き込みと競合した（8章）。読み直してもらう |

費目の設定が無い費目の `category` の支出が月にあると、集計できずに500になる（費目を作るときに、必ず月の設定と割合を書く。付録A-7）。

全APIで、認証・グループ所属・対象データのグループ一致・月の閲覧範囲・締め状態をWorker側で検証する。IDを知っているだけで他グループのデータにアクセスできないようにする。これらの判定は共通の関数にまとめる。Premiumの閲覧期間の制限（企画メモ10章）を導入するときも、同じ関数に足す。

## 11. 必須テスト

### 金額・負担計算

- JPY・USD・小数桁3の通貨での金額保存と表示
- 2人・3人以上の均等割り
- 割合合計10000の正常ケース、10000でないケースの拒否
- 金額指定の合計一致・不一致
- 端数が出る場合の固定順配分（割合0%のメンバーには配らない）
- 支払者と負担者が異なるケース
- 費目の月合計 × 割合で計算されること（企画メモ5章の精算例が、相手から自分へ17,000円になる）
- 上限額つきの負担：月合計が上限以下・ちょうど上限・上限超えの3通り。超えた分の割合を、負担する人0%・0%以外の両方で
- 月の途中で割合を変えると、その月の `category` の支出すべてに反映されること（`worker/test/categories.test.ts` の「その月の割合を置き換える。集計に反映される」。登録済みの支出の負担額が、直した割合で計算し直される）
- 個別設定の支出が、費目の合計から除外されること
- 割合の行が無い月が、直前の月の割合を引き継ぐこと
- 全員の差額の合計がゼロになること

### 月締め

- 通常の月締め
- 月の途中での締め、まだ始まっていない月の締めの拒否
- 前の月が未締め、または未処理の送金がある状態での締めの拒否
- 同じ月の二重締め
- 締め後の支出追加・編集・削除、割合変更の拒否
- 月締め中に支出登録・割合変更が競合（同じ `data_version` を読んだ2リクエストで、片方の後続SQLが実行されないこと）
- 3人以上の精算組み合わせ
- 精算済み・繰越・未処理の混在
- `settled`・`carried` から別の状態への変更の拒否
- 脱退予定・脱退処理中のメンバーが関わる送金の繰越の拒否
- 繰越が、翌月の支出の総額・負担額には加算されず、翌月の締めの精算する額に加算されること
- 2か月続けて繰り越したときに、金額を二重に数えないこと
- 3人で繰越がある月の送金の合計が、メンバーごとの精算する額と一致すること
- 早めに締めた後、同じ暦月の日付の支出を翌月分として登録できること
- 登録できる月以外（締め済みの月、2か月以上先の月）への登録の拒否

### メンバー・権限

- 招待URLを開いただけでは参加しない
- 期限切れ・使用済み・取消済み招待の拒否
- 同じ招待での同時参加で、1人だけ参加できること
- 発行者の脱退確定・アカウント削除で、未使用の招待が取り消されること
- 参加月の割合が均等にリセットされ、上限額の設定が外れること、個別負担の固定費が止まること
- 異なるグループのIDを指定した操作の拒否
- 参加月より前の履歴閲覧拒否
- 脱退の取り消し（当月中）と、翌月以降の取り消しの拒否
- 脱退月が終わったあと、Cronが確定させる前でも、本人が支出を記録できず、他のメンバーが本人を翌月以降の支払者・負担の対象にできないこと
- 脱退確定後、送金がすべて精算されるまで `leaving` のままであること
- 脱退後も過去の精算参照が壊れないこと、名前が残ること
- 再参加で元のメンバー行に戻り、履歴が復帰月以降になること
- 脱退月を早めに締めた時点で脱退が確定し、取り消せなくなること
- 早めに締めた後に脱退を選ぶと、その場で確定すること
- 最後の1人の脱退でグループのデータがすべて消えること
- アカウント削除時の名前匿名化（過去に脱退したグループを含む）
- 削除したユーザーが、削除した月までの集計に含まれ、翌月の割合から外れること
- 削除したユーザーが関わる送金を繰り越せず、精算済みにはできること
- アカウント削除後に認証情報から本人を再特定できないこと

### 二重送信

- 同じ `id` の登録を再送すると、支出が2件にならず、保存済みの支出が200で返ること（バージョンも上がらない）
- 最初の登録のあとに編集・月締めがあっても、再送は保存済みの状態を返すこと
- 再送でも、認証・所属・書き込みの権限を確認すること（脱退が確定した人が、確定の前に登録した支出の再送も403）
- `id` は、UUID（小文字）だけを受け付けること
- 別のメンバー・別のグループの支出と同じ `id` は、409 `conflict` で、何も書かないこと（別のグループと同時に登録した場合の一意制約違反も）
- 最初の登録と再送が同時に走っても、1件だけできること

### 固定費

固定費のAPIは `worker/test/recurring.test.ts`、自動登録は `worker/test/recurringRun.test.ts`（実施済み）。

- 同じ月に同じ固定費が二重生成されないこと（2回動かす、生成記録が先にある、利用者の書き込みと競合する）
- 生成記録が無いのに一意制約に違反したら、正常にせず、失敗として数えること
- 生成された支出を消しても、同じ月に作り直されないこと
- 生成済み支出がテンプレート変更で変化しないこと
- 31日指定など、月末に存在しない日付の扱い
- 停止中・終了後・開始前のテンプレートから新しい支出が生成されないこと（開始月・終了月の月は作ること）
- 予定の月が早めに締められていたら、最も古い未締めの月に登録されること
- グループのタイムゾーンで、今月と予定日を判定すること（UTCと月がずれる時刻）
- 過去の月の分は作らないこと
- 脱退の確定のあとに動くこと（確定で止まった固定費は作らず、確定が遅れても脱退する人の支出は作らない）
- アーカイブした費目の固定費は、止まらず、作られず、費目を戻すと作られること
- 1回の実行がD1のクエリ数の予算（Free: 50）に収まること（上限50件の固定費でも。予算が足りない回は、収まる件数だけ作り、残りは次の回で、二重に作らない。検査は、予算を小さくした場合と、人数の上限を超える12人の金額指定で行っている）
- 負担設定が合わない固定費だけが飛ばされ、同じグループのほかの固定費は作られること（定期処理は失敗として投げる）
- 予定日を過ぎてから登録・再開した固定費は、今月の分を作らず、来月の予定日に作ること（もともと作る時期に来ていたものは取り上げない）
- 再開は、止めた理由によらず、`category` 以外の負担なら `split` を送り直すこと
- 一度も支出を作っていない固定費だけが削除でき、通貨のロックと上限の件数から外れること（今月の分は作らなかった記録だけの固定費は消せて、記録も一緒に消える。支出を作った記録が1件でもあれば、支出を消していても消せない）
- `thisMonthSkipped` は、登録・変更・再送で同じ意味（書いたあとに、今月の作らなかった記録があるか）であること。止めて再開しても、ほかを直しても、記録がある間は true。支出を作った記録や、先月の記録だけなら false。月が変われば false
- グループ情報の `seatedMembers`・`maxMembers`・`canInvite`（脱退が確定した人・脱退月が終わった人は数えず、その人自身は false）と、招待内容の確認の `groupFull` が、参加・発行の判定と一致すること
- アーカイブした費目の固定費の費目を選び直しても、今月の分を作らない記録を残さないこと

## 12. 実装前に残る確認事項

- **アカウント削除のD1のクエリ数は、batch の文を1つずつ数える安全側の見積もりでは、Freeの上限（1回の呼び出しにつき50）に収まらないことがある。公式の数え方（batch は1回。8章の「D1のクエリ数の数え方」）なら、収まる。** `POST /auth/delete`（実装済み。9章の「認証API」）が、再認証のあとに、`worker/src/accountDeletion.ts` の `deleteAccount` を呼ぶ（複数グループの競合制御は、8章の `writeToGroups`で決めた）。上限は、データ処理だけでなく、エンドポイント全体に掛かる。実測は `worker/test/deleteAccount.test.ts` の「D1のクエリ数」（データ処理だけの数は `accountDeletion.test.ts`）。以下の数は、すべて、1文ずつ数えた数。
  - **公式のとおり batch を1回と数えるなら、** 削除は、グループ数によらず約10回（認証1〜2、T の使用済み1、読み込み6、書き込み1）。競合で3回やり直しても約25。グループ数の上限も、Paidへ移すことも、削除のためには要らない。確かめるのは13章の9。
  - **基本は11。** セッションの検索1、T を使用済みにする2、データ処理の読み込み6（グループの数によらず固定。`json_each` でまとめて引く）、バージョンの更新1、`users` の削除1。セッションを24時間以上使っていないと、認証が最後に使った時刻を更新するので、+2。
  - **グループごとに足される数。** 残る人がいる参加中のグループは9。**自分だけのグループ（削除するとグループごと消える）は15。** 脱退済みのグループは2（匿名化だけ）。翌月より先に割合の行がある月（削除や脱退の確定が書いたもの）は、参加中のグループ1つ・1か月につき4。
  - **競合してやり直すたびに、読み込み6 + 書き込み全体が加わる。** 1グループでも、1回の競合で37、2回で54。
  - **収まる範囲。** 残る人がいるグループだけなら4グループまで（47。セッションが古いと49。5グループで56）。**グループ数の上限だけでは、収まる保証にならない。** 3グループでも、自分だけのグループが3つなら56、残る人がいる3グループで、すべてに先の割合の月があり、セッションが古ければ52。脱退済みのグループも、1つにつき2ずつ増え続ける。
  - **1文ずつ数える場合、上限に当たると、`batch` が例外を投げ、`POST /auth/delete` は未処理の例外（500）になる。** 何も消えない。再認証の T は使用済みで、Appleの認可コードの交換は済んでいるが、失効は行われない。やり直しても、同じ失敗になる。
  - Paid（上限は1回につき1000）なら、1文ずつ数えても、100グループ以上まで。docs/plan.md は、公開時にPaidへ移すことを前提にしている（Freeのまま進めるかは、決めていない。13章の9の確認のあとで決める）。公式の数え方を本番のFreeで確かめられなかったときは、Freeにとどめるなら、グループ数の上限に加えて、読んだあとに文の数を数えて予算を超えるときは断る、または、削除の依頼を受け付けたあとで、Cronが予算に収まる数ずつ片付ける、といった設計が要る。複数の `batch` に分けると、5章の「1回の `batch()`」と食い違い、途中で止まった状態が残るため、必要になったときに決める。
- **Freeのまま運用するときの上限（Paidへ移る基準は未決）。** 出典は、Cloudflareの [Workersの上限](https://developers.cloudflare.com/workers/platform/limits/)（2026-11-19に更新）、[D1の料金](https://developers.cloudflare.com/d1/platform/pricing/)（2026-10-30に更新）、[D1 Limits](https://developers.cloudflare.com/d1/platform/limits/)（2026-11-20に更新）。

  - アプリがAPIを呼ぶ先 `API_ORIGIN`（`src/repositories/apiClient.ts`）：本番のドメインが決まるまで、仮の値（`https://not-created-yet.invalid`）。そのあいだ、アプリのHTTPは、名前が引けず `network` で失敗する。決まったら、`APPLE_CALLBACK_URL` と同じドメイン（origin）に置き換える（`worker/test/config.test.ts` が、origin の一致と、どちらも仮の値かどうかの一致を固定している。ドメインを分ける設計にするときは、そのテストを直す）。
  - アプリは、iOSのAppleの再認証で、サインインで得た `authorizationCode` を送る（送らなければ、削除はできるが、失効しない）。
  - AndroidのAppleログイン（Web経由）に要る値：`APPLE_SERVICES_ID`・`APPLE_CALLBACK_URL`（どちらも仮の値のままだと `npm run deploy` が止まる）。手順は、①Apple Developerで、Services ID（予定の名前: `com.yskms.warikanseikatsu.web`。バンドルIDとは別の識別子）を作り、Sign in with Apple を有効にして、primary App ID にこのアプリのバンドルIDを選ぶ。②Services ID の設定に、本番のドメインと、Return URL（`APPLE_CALLBACK_URL`。本番の独自ドメインの `/auth/apple/callback`。HTTPS）を登録する。③`wrangler.jsonc` の2つの値を置き換え、**アプリの `src/repositories/appleWebSignInRepository.ts` の `APPLE_SERVICES_ID`・`APPLE_CALLBACK_URL` も、同じ値に置き換える**（片方だけだと、`worker/test/config.test.ts` が落ちる。アプリ側は、値が仮の値でなくなれば、自動でブラウザを開くようになる）。本番のドメインは、まだ決めていない（`APPLE_CALLBACK_URL` をコードの定数にせず `vars` に置いたのは、そのため。決まったら定数に戻してもよい。Singfolioはそうしている）。鍵（`APPLE_KEY_ID`・`APPLE_PRIVATE_KEY`）は、上のiOSの失効と同じものを使う（Sign in with Apple の鍵は、primary App ID に結びつく。Services IDも同じ primary App ID なので、1つで足りる）。④Appleのサーバー間通知のエンドポイントを登録する：Apple Developerの primary App ID（このアプリのバンドルID）の Sign in with Apple の設定で、`https://<本番のドメイン>/auth/apple/notifications` を入れる（Services IDも同じグループなので、1つで足りる）。登録するまで、通知は届かず、Apple Accountを削除した人・連携を解除した人のセッションとデータは、自動では消えない。⑤Cloudflareのダッシュボードで、WAFのRate limiting rulesに、`/auth/apple/login` 用の1ルールを作る（9章の「認証API」）。ルールは独自ドメインのゾーンに置くので（`workers.dev` には置けない）、①〜④と同じく、本番のドメインが決まってから作る。リポジトリの外にあるので、デプロイのたびには作り直さない。

# 付録A：D1用SQL DDL 初版

> 注意：以下のDDLは `worker/migrations/0001`〜`0006` に分けて置いてある（10章）。ローカルのD1で適用と主な制約は確かめたが、トランザクション、削除・匿名化の挙動は、APIを作るときに確かめる。

共通の約束（Singfolioに揃える）：

- テーブルは `STRICT, WITHOUT ROWID`。IDはTEXT（UUID）。
- 日時はUnixエポックのミリ秒（INTEGER）。月は `YYYY-MM`、日付は `YYYY-MM-DD` のTEXT。
- D1は外部キーを既定で強制するので、`PRAGMA foreign_keys` は書かない。
- 金額の上限 `1000000000000`（2章）は、実装時に定数として1か所にまとめる。
- グループの配下のテーブルには、すべて `group_id`（またはその親のID）が先頭にくる主キーか索引を持たせる。理由は2つ。
  - グループの削除は `group_id` で行を消すので、索引が無いと、全グループの行を読むことになる。D1は読んだ行数で課金される。
  - 親の行（メンバー・費目など）を消すとき、SQLiteは子のテーブルを外部キーの列で探す。子の側に、外部キーのどれかの列が先頭にくる索引が無いと、子のテーブル全体を読む。複合外部キーは `(xxx_id, group_id)` なので、`group_id` が先頭の索引があれば、そのグループの行だけを読めば済む。
- 自由入力の文字数の上限は、DDLのCHECKにも置く（APIでも検証する）。グループ名30文字、表示名20文字、費目名20文字、支出・固定費の内容100文字。

```sql
) STRICT, WITHOUT ROWID;

CREATE INDEX idx_categories_group ON categories (group_id);

-- 行が無い月は、その月以前で最も新しい月の行と、同じ月の category_month_shares の組を使う（3章）。
-- 上限額つきの負担を使わない月も、行は書く（どの月の設定を使うかを、この表の月で決めるため）。
CREATE TABLE category_month_settings (
  group_id TEXT NOT NULL,
  category_id TEXT NOT NULL,
  target_month TEXT NOT NULL CHECK (target_month GLOB '[0-9][0-9][0-9][0-9]-[01][0-9]'),
  cap_member_id TEXT,
  cap_minor INTEGER CHECK (cap_minor BETWEEN 1 AND 1000000000000),
  PRIMARY KEY (category_id, target_month),
  FOREIGN KEY (category_id, group_id) REFERENCES categories (id, group_id),
  FOREIGN KEY (cap_member_id, group_id) REFERENCES group_members (id, group_id),
  CHECK ((cap_member_id IS NULL) = (cap_minor IS NULL))
) STRICT, WITHOUT ROWID;

CREATE INDEX idx_category_month_settings_group ON category_month_settings (group_id, target_month);

-- 超えた分の割合（上限額つきでなければ、月合計の割合）。category_month_settings と同じ月でまとめて書く。
CREATE TABLE category_month_shares (
  group_id TEXT NOT NULL,
  category_id TEXT NOT NULL,
  target_month TEXT NOT NULL CHECK (target_month GLOB '[0-9][0-9][0-9][0-9]-[01][0-9]'),
  member_id TEXT NOT NULL,
  share_basis_points INTEGER NOT NULL CHECK (share_basis_points BETWEEN 0 AND 10000),
  PRIMARY KEY (category_id, target_month, member_id),
  FOREIGN KEY (category_id, group_id) REFERENCES categories (id, group_id),
  FOREIGN KEY (member_id, group_id) REFERENCES group_members (id, group_id)
) STRICT, WITHOUT ROWID;

CREATE INDEX idx_category_month_shares_group ON category_month_shares (group_id, target_month);
```

## A-6. 月締め・精算

```sql
CREATE TABLE monthly_closings (
  id TEXT PRIMARY KEY NOT NULL,
  group_id TEXT NOT NULL REFERENCES expense_groups (id),
  target_month TEXT NOT NULL CHECK (target_month GLOB '[0-9][0-9][0-9][0-9]-[01][0-9]'),
  currency_code TEXT NOT NULL,
  currency_minor_unit INTEGER NOT NULL CHECK (currency_minor_unit BETWEEN 0 AND 3),
  data_version INTEGER NOT NULL,
  closed_by_member_id TEXT NOT NULL,
  closed_at INTEGER NOT NULL,
  FOREIGN KEY (closed_by_member_id, group_id) REFERENCES group_members (id, group_id),
  UNIQUE (id, group_id),
  UNIQUE (group_id, target_month)
) STRICT, WITHOUT ROWID;

CREATE TABLE closing_member_summaries (
  group_id TEXT NOT NULL,
  closing_id TEXT NOT NULL,
  member_id TEXT NOT NULL,
  display_name_snapshot TEXT NOT NULL,
  paid_minor INTEGER NOT NULL CHECK (paid_minor >= 0),
  burden_minor INTEGER NOT NULL CHECK (burden_minor >= 0),
  difference_minor INTEGER NOT NULL,
  carried_in_minor INTEGER NOT NULL DEFAULT 0,
  net_minor INTEGER NOT NULL,
  PRIMARY KEY (closing_id, member_id),
  FOREIGN KEY (closing_id, group_id) REFERENCES monthly_closings (id, group_id),
  FOREIGN KEY (member_id, group_id) REFERENCES group_members (id, group_id),
  CHECK (difference_minor = paid_minor - burden_minor),
  CHECK (net_minor = difference_minor + carried_in_minor)
) STRICT, WITHOUT ROWID;

CREATE INDEX idx_closing_member_summaries_group ON closing_member_summaries (group_id);

-- total_minor は、その費目の支出の合計（個別設定の支出を含む）。
-- burden_minor は、その費目でのそのメンバーの負担額（費目の割合による分と、個別設定の支出の分の合計）。
-- 費目ごとに、全メンバーの burden_minor の合計は total_minor と一致する。
CREATE TABLE closing_category_burdens (
  group_id TEXT NOT NULL,
  closing_id TEXT NOT NULL,
  category_id TEXT NOT NULL,
  member_id TEXT NOT NULL,
  total_minor INTEGER NOT NULL CHECK (total_minor >= 0),
  burden_minor INTEGER NOT NULL CHECK (burden_minor >= 0),
  PRIMARY KEY (closing_id, category_id, member_id),
  FOREIGN KEY (closing_id, group_id) REFERENCES monthly_closings (id, group_id),
  FOREIGN KEY (category_id, group_id) REFERENCES categories (id, group_id),
  FOREIGN KEY (member_id, group_id) REFERENCES group_members (id, group_id)
) STRICT, WITHOUT ROWID;

CREATE INDEX idx_closing_category_burdens_group ON closing_category_burdens (group_id);

CREATE TABLE settlement_transfers (
  id TEXT PRIMARY KEY NOT NULL,
  group_id TEXT NOT NULL,
  closing_id TEXT NOT NULL,
  from_member_id TEXT NOT NULL,
  to_member_id TEXT NOT NULL,
  amount_minor INTEGER NOT NULL CHECK (amount_minor > 0),
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'settled', 'carried')),
  settled_at INTEGER,
  carried_at INTEGER,
  processed_by_member_id TEXT,
  FOREIGN KEY (closing_id, group_id) REFERENCES monthly_closings (id, group_id),
  FOREIGN KEY (from_member_id, group_id) REFERENCES group_members (id, group_id),
  FOREIGN KEY (to_member_id, group_id) REFERENCES group_members (id, group_id),
  FOREIGN KEY (processed_by_member_id, group_id) REFERENCES group_members (id, group_id),
  CHECK (from_member_id <> to_member_id),
  CHECK (
    (status = 'pending' AND settled_at IS NULL AND carried_at IS NULL AND processed_by_member_id IS NULL)
    OR (status = 'settled' AND settled_at IS NOT NULL AND carried_at IS NULL AND processed_by_member_id IS NOT NULL)
    OR (status = 'carried' AND carried_at IS NOT NULL AND settled_at IS NULL AND processed_by_member_id IS NOT NULL)
  ),
  UNIQUE (closing_id, from_member_id, to_member_id)
) STRICT, WITHOUT ROWID;

-- 翌月の締めで、前の月の締めの carried の送金を読むときにも使う。
CREATE INDEX idx_settlement_transfers_group ON settlement_transfers (group_id, closing_id);
```

## A-7. DDLだけでは保証できないこと

以下は複数行・複数テーブルにまたがるため、Worker側の検証と8章の競合制御で保証する。

- `category_month_shares` の、1つの費目・月の割合合計が10000であること。
- `category_month_settings` と `category_month_shares` が同じ月でまとめて書かれること。上限額を負担する人が、その月の `category_month_shares` に含まれること。
- `expense_allocations.burden_minor` の合計が支出総額と一致すること。`category` の支出に行が無いこと。
- 金額指定の各 `amount_minor` の合計が支出総額と一致すること。
- 支払者・負担者が、支出の対象月に有効なメンバーであること。
- 月締め後に、対象月の支出・負担割合を変更できないこと。
- 送金の状態が `pending` からしか変わらないこと（UPDATEに `AND status = 'pending'` を付ける）。
- グループ通貨が支出登録後に変更されないこと。
- 費目ごとの `closing_category_burdens.burden_minor` の合計が `total_minor` と一致すること。
- 匿名化時に `group_members.display_name` と `closing_member_summaries.display_name_snapshot` の両方を更新すること。
- `users` の削除前に、メンバー行の匿名化と `user_id` の解除を済ませること。
