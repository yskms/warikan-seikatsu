# わりかん生活：画面設計メモ

画面の一覧、画面の移り方、各画面に出す内容をまとめる。仕様の正本は [企画メモ](plan.md)、データとAPIは [バックエンド設計メモ](backend-design.md)。この文書は、それらを画面に落としたもの。

見た目（色・余白・部品）の細かい指定はここでは決めない。決めているのは次だけ。

- 白・ライト基調。ダークモードにも対応する
- アクセントカラーは、`#FC75A4` 付近のピンク（旧アイコンの色）。アイコンを赤（`#C8000C`）に変えたので、アクセントをアイコンに合わせるかは未定
- 金額は大きく、精算の向き（誰が誰に）は矢印と名前で、ひと目で分かるようにする

## 1. 全体の構成

```
起動
 ├─ 未ログイン → ログイン画面
 │                └─（招待URLから来たとき）ログイン後に参加確認へ
 └─ ログイン済み
      ├─ グループが無い → グループ作成
      └─ グループがある → メイン

メイン（下のナビ）
 ├─ ホーム … 選んだ月の支出の総額、メンバー別の負担額、精算、支出の一覧。締めた月もここで見る
 ├─ ＋     … 支出の登録（シートを開く）
 └─ 設定   … カテゴリと負担割合、固定費、メンバーと招待、グループ、アカウント
```

- 下のナビは「ホーム・＋・設定」の3つ。＋は真ん中に置き、押すと支出の登録のシートを開く
- 履歴のタブや、集計・支出一覧の専用画面は設けない。過去の月も、ホームの月の切り替えで見る
- 複数のグループに入っている人は、画面上部のグループ名をタップして切り替える。グループが1つの人には、切り替えの操作を見せない
- 最後に開いたグループを覚えておき、次の起動ではそのグループを開く
- データは、画面を開いたときと、ホームに戻ったときに取り直す。引っ張って更新（pull to refresh）もできる。プッシュ通知やリアルタイム更新はMVPに入れない
- 起動時に、端末に保存したログイン情報を読めないことがある（サインインの層が `storage-failed` を返す。backend-design.md 9章の「サインインの層」）。「未ログイン」とは別の状態として扱い、すぐにログイン画面へ送らない。端末がロック中の一時的な失敗かもしれないので、短い間隔で数回、読み直す（アプリが前面に戻ったときにも読み直す）。**ただし、壊れた値のように、ずっと続くこともある**。読み直しても直らないときは、ログイン画面を出す。ログインすれば、読めない値は上書きされる（サーバーに残った古いセッションは、使われないまま90日で切れる）。設定のログアウトも、読めない値を消す。読めない状態のまま、先へ進めなくならないようにする

**実装したところ（グループの切り替えと、最後に開いたグループ）**: 開くグループは、①メモリ（この起動中に切り替えた・参加したグループ。`ui/activeGroup.ts`）、②端末に覚えた最後のグループ（`platform/lastGroup.ts`。Documentsの `last-group.txt` にIDだけ）、③作成の古い順の先頭、の順に、**所属の一覧にあるもの**を選ぶ（`src/services/groupChoice.ts` の `pickGroup`。`npm test` で確かめている）。一覧に無いIDを飛ばすのは、覚えていたグループから脱退した、別のアカウントでログインし直した、といったとき。端末の記憶はアカウントごとには分けない（IDだけでは、サーバーが所属を確かめるので、データに入れない。**同じ端末で、同じグループに入っている別のアカウントがログインし直すと、前の人が最後に開いたグループが開く**。どちらも、そのグループのメンバーなので、許容する。ログアウトでは、メモリの `activeGroup` も `last-group.txt` も消さない）。

- **覚えるのは、切り替え・参加のときだけ**（`openGroup`。メモリへ置くと同時に書く）。一覧から先頭を選んだだけのときは書かない。覚えるのに失敗しても、何も起こさない（起動中は、メモリが優先。次の起動で先頭になるだけ）。**グループを開く操作は `openGroup` だけを通す**（メモリだけに置く `activeGroup.set` を直接呼ぶと、次の起動で前のグループへ戻る）。
- **切り替えの入口は、ホームの上部のグループ名**（`ui/home/GroupSwitcher.tsx`）。2つ以上のグループに入っている人だけ、名前の横に矢印が出て、タップすると下から一覧のシートが出る（月のピッカー `MonthHeader.tsx` と同じ作り。いまのグループにチェック。長い名前は省略）。1つだけの人は、矢印もボタンも出ない（ただの見出し）。選ぶと、シートを閉じる指示と切り替えを同時に行う（`Modal` は、表示中のまま外れ、閉じるアニメーションは走らない。RN 0.86 のiOSは、`Modal` が外れたときに、表示中のモーダルを閉じる処理を持つ。`RCTModalHostViewComponentView.mm` の `ensurePresentedOnlyIfNeeded`。ソースで確かめただけで、iOSの実機・シミュレータでは未確認。待ってから切り替える形（`onDismiss` はiOSだけ）は、タイマーの分だけ複雑になるので採らなかった）。いまのグループを選んでも何もしない。**精算完了・繰越の通信の最中は、グループ名を押せない**（`HomeScreen` が `transfers.busy` を `disabled` で渡す。切り替えるとホームごと外れて、結果の文言・読み直しを受ける画面が無くなり、取り消せない繰越が済んだか分からないまま別のグループへ移るため。ほかにホームから始まる書き込みは無い。支出・月締め・カテゴリ編集のシートは、ホームの上に重なるので、開いているあいだは押せない）。
- **切り替えは、`GroupGate` が `key` を変えて、`(main)` の下を作り直す形**（ホームの読み込みの状態は、グループごとに別。`HomeScreen` の `groupId` は、作ったあとに変えない）。作り直されるので、下のナビは、ホームに戻る。切り替えの候補（名前）は、`GroupGate` が一覧を読んだときのもので、`GroupGate` が作り直されるまで（参加確認のあと、「もう一度」）取り直さない（グループ名を直す画面は、まだ無い。ホームの見出しは、ホームが読み直した最新の名前を出す）。
- **2つ目のグループを自分で作る入口は、作っていない**。1人が作れるグループの数の上限が未決（backend-design.md 12章）なので、決めてから、切り替えのシートに「グループを作る」を足すかを決める。いまは、招待に応じて参加すると、グループが増える。
- **確かめたのは**、Androidのエミュレータ（API 36。debugビルド）で、`fetch` とログインを偽のものに差し替えた状態（保存はしない一時の差し替え）。3つのグループのとき: 名前の横の矢印、シートの一覧（いまのグループにチェック、長い名前の省略）、選ぶと別のグループのデータに切り替わること（見出し・金額）、`last-group.txt` にIDが書かれること、アプリを終了して起動し直すと、最後に開いたグループが直接開くこと（先頭のグループを読まない）。覚えていたグループが一覧に無いときは先頭が開くこと。グループが1つのとき、矢印が出ないこと。ダーク。精算完了の通信を7秒に引き延ばし、その最中にグループ名が薄くなり、押しても一覧が開かないこと、完了後に押せる状態へ戻ること（レビュー対応。精算完了の確認ダイアログを経て確かめた。繰越は同じ `busy` を通る）。**未確認**: 本物のWorkerとの通信（`API_ORIGIN` が仮の値）、iOS、参加確認のあとに、参加したグループが次の起動でも開くこと（`openGroup` を通す配線は、型検査と `pickGroup` のテストだけ）、Androidの戻る操作でシートを閉じること、文字サイズを大きくしたとき、スクリーンリーダーでの読み上げ。

### ログインなしのお試し（MVPの後）

ログインは必須とする。メインの画面ができた後に、ログイン画面へ「ログインせずにサンプルを見る」を足す。

- サンプルのグループ（例：家賃は7:3、外食は月1万円まで自分）を端末内に持ち、支出を足したり消したりすると、負担額と送金がその場で変わる
- 計算は、サーバーと同じTypeScriptの関数を端末で動かす。データは保存しない
- 締め・招待・固定費・設定は、「ログインすると使えます」と案内してログイン画面に戻す
- この画面は、ストアのスクリーンショットにも使える

## 2. ログイン・はじめての設定

### ログイン画面

- アプリ名、ひとことの説明（「ふたりの生活費を、決めた割合で月ごとに精算」など）
- 「Appleでサインイン」「Googleでログイン」の両方を、両OSで出す。iOSではAppleを上、AndroidではGoogleを上にする
- 招待URLから来たときは、上部に「ふたりで使うには、データ保護のためログインが必要です」と出す。ログイン後は、招待情報を持ったまま参加確認に進む
  - 実装した（`app/login.tsx`。招待URLのトークンを持っているあいだだけ、上部に出す。狭い画面で「必／要です」と折り返さないよう、読点で改行している）。メインの画面は、ログインしていない人には出ない（`Stack.Protected`）ので、ガードで入れない画面へのURLは、最初の画面へ回されて捨てられる。招待URLで起動した未ログインの人の行き先は、何もしなければ残らない。そこで、URLからトークンを取り出して**メモリだけ**に持ち、ログイン後に参加確認へ回す（2章の「参加確認」の「実装したところ」）
- プライバシーポリシーと利用規約へのリンク
- 失敗したときの文言は、ボタンの**上**に出す（下に出すと、ボタンが押し上げられて、続けて押したタップが外れる）。利用者が取りやめたときは、何も出さない
- 端末の保存先を読めずにこの画面を出したとき（1章の最後の項目）は、「この端末に保存したログイン情報を読み取れませんでした。ログインし直してください。」と、ボタンの上に出す
- ログイン済みの人は、この画面に戻れない（戻るキーでも）。メインの画面は、ログインしていない人には出ない（`app/_layout.tsx` の `Stack.Protected`）

### グループ作成

ログイン後、グループが1つも無いときに出す。入力は最小限にして、すぐ使い始められるようにする。

- グループ名（初期値：「ふたりの生活費」。後から変えられる）
- 自分の表示名（このグループの中での名前。Apple / Googleの名前は使わない）
- 通貨（初期値：日本円。支出・固定費・上限額つきの負担・締めた月のどれかができた後は変えられない。バックエンド設計メモ 2章）

作ると、次の初期カテゴリを作る（自分100%）。相手が参加した月に、均等にリセットされる（企画メモ8章）。

| カテゴリ | アイコン |
|---|---|
| 家賃 | 家 |
| 食費 | カート |
| 日用品 | 洗剤のボトル |
| 光熱費 | 電球 |
| 外食 | ナイフとフォーク |
| 通信費 | Wi-Fi |
| その他 | 点3つ |

作った後はホームを開き、「相手を招待する」のカードを目立たせる（後述）。

実装した（`app/create-group.tsx`。起動後の分岐は `ui/GroupGate.tsx`。所属グループが空のときに、ここへ回す）。

- ボタンは画面の下に固定し、失敗の文言はその上に出す（ログイン画面と同じ理由。スクロールの中に置くと、文言が出るたびにボタンが下がり、直後に同じ場所を押しても外れる）。入力し直したら、その欄の検査のエラーは消す。
- 作成の識別子（`id`）は、画面を開いてから最初に送るときに1回だけ作り、やり直しでも同じ値を送る（通信が切れて結果が分からないとき、グループが2つにならない。サーバーは、作成が済んでいれば保存済みのグループを返す）。そのため、結果が分からない失敗のあとに入力を直して送り直すと、作成が済んでいた場合は、**送った内容の全部**（グループ名・表示名・通貨・タイムゾーン）が、直す前のままになる。グループ名・表示名はあとから変えられ、通貨も金額に関わるものが無いうちは変えられるが、タイムゾーンを変える手段は無い（端末のタイムゾーンは、やり直しのあいだに変わらないので、古くなりうるのは、利用者が直した入力だけ）。入力が変わったら新しい `id` にする案は、作成が済んでいたときにグループが2つでき、余分なグループがすぐには消せないので採らない（グループは、最後の1人が脱退するときに削除される。その確定は、脱退月を締めたときか翌月1日。脱退を選ぶ操作は、メンバーと招待の画面の一番下にある（6章）。バックエンド設計メモ 5章の「脱退」「グループの削除」と、この文書の6章）。
- タイムゾーンは、端末の値を送る（月の境目を決める）。取れないときは、既定値にせず、作成を止めて案内する。サーバーが名前を知らない（400）ときは、やり直しても直らないので、時間をおく案内ではなく、端末の日付と時刻の設定の確認と、アプリの更新を案内する。
- 作成の応答は、グループの `id` だけを読む。ほかの項目の形が少しずれても、作成が済んだものを失敗に見せない（同じ `id` で再送しても同じ応答が返り、同じ失敗になるため。アプリを開き直すまで、先へ進めなくなる）。
- 作らずに出る道として、ログアウト（「別のアカウントでログインし直す」）を置く。間違ったアカウントでログインした人や、脱退して所属が空になった人が、不要なグループを作らずに済むようにするため（作ったグループは、すぐには消せない。上の項目）。作成の最中は押せず、逆に、ログアウトの最中は、作成も押せない（作成の途中でセッションを捨てない）。
- **招待との関係**: 招待URLから来た人は、この画面（と、ログイン後の分岐 `ui/GroupGate.tsx`）を通らない。招待を持っているあいだは、ルート（`app/_layout.tsx` の `RootNavigator`）が、`(main)` もこの画面も外して、参加確認（`/join`）だけを出す（実装した。下の「参加確認」）。この画面を開いているときに招待URLが開かれた場合も、参加確認へ移る。
- 確かめたのは、Androidのエミュレータ（API 36）で、Serviceを偽のものに差し替えた状態（保存はしない一時の差し替え）。画面の表示、検査の表示、失敗からのやり直し、作成後に最初の画面（ホームは仮）へ移ること、ライト・ダーク、キーボードが入力欄に被らないこと、グループ名から表示名へフォーカスが移ること、作成画面からのログアウト。**未確認**: 本物のWorkerとの通信（`API_ORIGIN` が仮の値）、iOS（キーボード回避の `padding` と、下端の安全領域の余白が重ならないかを含む）、Android 14以下の実機（Pixel 3など。アプリは全バージョンでedge-to-edge（`android/gradle.properties` の `edgeToEdgeEnabled=true`）だが、OSがそれを強制するのはAndroid 15以上。キーボードは、支出のシートの確認で、`adjustResize` ではウィンドウが小さくならないと分かり、`KeyboardAvoidingView` の `padding` に直した。4章の「実装したところ」）、日本語の入力（確認はASCIIだけ）。

### 参加確認（招待URLを開いたとき）

ダイアログで出す。開いただけでは参加しない。

- グループ名、招待した人の表示名
- 自分の表示名の入力（初期値なし。必須）
- 「参加する」「キャンセル」
- 期限切れ・使用済み・取り消し済みの招待は、「この招待URLは使えません。招待した人に、新しいURLを送ってもらってください」と出す
- すでにそのグループに参加中なら、そのグループを開くだけにする
- グループの人数が上限（5人）なら、表示名を入力させる前に「このグループは満員です（5人まで）」と出し、「参加する」を押せなくする（招待内容の確認の `groupFull`。人数の数え方は、アプリで書き写さない）。確認のあとに埋まったときは、参加の応答の409 `group_full` で同じ案内を出す

**実装したところ（参加確認）**: 画面は `app/join.tsx`（`ui/join/JoinScreen.tsx`）。**ダイアログではなく全画面**（グループ作成と同じ作りで、入力欄・キーボードの避け方・下端に固定したボタンを揃えた）。失敗の分類と文言は `src/services/joinMessage.ts`、読み書きは `src/services/inviteService.ts` の `preview`・`join` と `src/repositories/inviteRepository.ts`（どれも `npm test` で守る）。

- **URLの受け取り**: 招待URLは2つの形を受ける（`src/services/inviteLink.ts` の `parseInviteLink`）: `https://<INVITE_URL_ORIGIN>/invite/<token>`（共有するURL）と、`warikan-seikatsu://invite/<token>`（URLスキーム。メッセージアプリでは押せないが、`adb shell am start -a android.intent.action.VIEW -d …`・`xcrun simctl openurl` での確認用）。置き場・スキーム・道が違うものと、トークンの形（43字のbase64url。Workerの `isInviteToken` と同じ）が違うものは、招待URLとして扱わない。起動したときのURLと、起動中に開かれたURLは、`platform/inviteLink.ts` が Linking から**直接**受け取り、expo-router には画面として渡さない（`app/+native-intent.tsx` が、起動時は `'/'`、起動中は `null` を返す。Apple再認証の戻りのURLと同じ扱い）。
- **起動したときのURLは、読み終えるまでスプラッシュを出したままにする**（`app/_layout.tsx` の `RootNavigator`。上限2秒）。読む前にログイン後の画面が描かれ、グループの一覧の読み込みとグループの作成への分岐が動くと、招待された人が、作る必要のないグループの作成画面へ回される。**上限を過ぎてから届いたURLも受け取る**（ルートが、招待を持った時点で参加確認へ移すので、遅れても間に合う）。
- **トークンは、メモリだけに持つ**（`src/services/pendingInvite.ts`。端末には保存しない）。ログイン中にアプリのプロセスが終わった場合は、もう一度招待URLを開いてもらう。持つのは1つだけで、新しい招待URLを開いたら置き換える。手放すのは、参加した・キャンセルした・すでに参加中だった・使えない招待を閉じた、のとき（`clear(token)` は、持っているトークンと同じときだけ手放す。確認の最中に新しいURLが開かれても、古い招待の終わりの処理が新しい招待を消さない）。手放すと、ルートが参加確認を外し、最初の画面（メイン、またはグループの作成）からやり直して、グループの一覧を読み直す。ログイン画面を経由する人も、すでにログインしていて起動中にURLを開かれた人も、同じ道を通る。
- **参加確認へ移すのは、ルートの `Stack.Protected`**（`app/_layout.tsx`。`join` は「ログイン済み、かつ招待を持っている」、それ以外のログイン済みの画面は「ログイン済み、かつ招待を持っていない」のときだけある）。**`GroupGate` や画面ごとの `Redirect` に戻さない**: `Redirect` は、その画面にフォーカスがあるときしか動かない（expo-router の `Redirect` は `useFocusEffect` の中で動く）ので、グループ作成の画面（`(main)` の外）や、設定の先の画面・支出のシートが開いていると、招待URLを開いても何も起きず、戻ったときに突然出る。ルートで外せば、どの画面にいても出る。**開いていた画面・シートは閉じられ、入力中のものは失われる**（アプリの外から来る操作なので、割り込みを許した。積む形にすると、キャンセルのあとに元の画面へ戻す処理と、戻る操作で招待を手放す処理が要る）。
- **ただし、書き込みの通信の最中の画面があるあいだは、切り替えを遅らせる**（`ui/inviteHold.ts` の `useHoldInviteSwap`。支出・月締め・カテゴリ編集のシートと、グループ作成、招待の発行。終わったら切り替わる）。書き込みの最中に画面が外れると、その結果（成功したあとの画面遷移・失敗の表示）を受ける画面が無くなり、完了後の `leave()`（`router.back()` / `router.replace()`）が、そのとき開いている別の画面に対して動きうる。招待の発行は、トークンが発行の応答でしか分からず、画面のメモリにだけ持つので、発行の最中に外れると、招待はできるのにトークンが失われ、未使用の招待として上限（`too_many_invites`）に数えられる（取り消すか、期限が切れるまで残る）。通信には上限（10秒）があり、画面が消えれば手放すので、招待がいつまでも出ないことはない（カテゴリ編集は、保存のあとの「保存しました」のダイアログを閉じるまでも続く。目の前のダイアログなので許容する）。**参加確認の画面は登録しない**（参加の通信の最中に、自分が外れる）。読み込みの最中や、結果を画面に出すだけの画面（ホームの精算の操作。メンバーと招待の取り消し）は、登録していない（外れても、取りこぼすものが無く、戻れば読み直す）。
- **守らないもの（意図している）**: ①**結果が分からない失敗（通信が切れた）のあと**。失敗の文言を出して、画面が残っているあいだも遅らせる形にはしない（文言を閉じるまで、招待URLを開いても何も起きないように見える）。そのため、支出のシートの保存の `id`（やり直しで二重登録を防ぐ）は、このとき捨てられる。保存されたかは、参加確認のあとに戻ったホームの一覧で分かる（保存されていれば、一覧に出る）。②**開いたままの確認ダイアログ**（支出の削除の確認、「締められました。登録しますか？」、カテゴリの「使わなくする」、入力の破棄の確認、ホームの精算完了・繰越の確認、招待の取り消しの確認）。画面は外れ、Androidの `Alert` は、Activityに付くので、参加確認の上に残りうる（未確認）。そこで押された操作は、画面が外れていれば**何もしない**（`ui/useMounted.ts` の `mounted`。見えない画面の支出・送金を、確認したときの状態のまま処理しない。繰越は取り消せない。月締めの確認が「開くときに読み直した内容で出す」のと同じ考え方）。**例外は、ログアウトの確認（`ui/useSignOut.ts`）**: アカウントの操作として明示的に押されたもので、ログイン画面へ戻るだけ（招待は持ったまま。データは消えない）。ダイアログを新しく足すときは、書き込み・取り消せない操作から始まるなら、`mounted` で守る（`Alert.alert` は、いまは11箇所。すべて、この規則で分類済み）。ダイアログの間も遅らせる形は、ダイアログが閉じられずに残ると遅らせ続けることになり、ダイアログの種類ごとに開閉の状態を持つ必要があるので、採らなかった。
- **外れた画面の完了後の画面遷移は、`mounted` が偽なら行わない**（支出・月締め・カテゴリ編集のシートの `leave()`、グループ作成の `router.replace('/')`。セッション切れで外れた場合も同じ）。エミュレータで、グループ作成の通信を6秒に引き延ばし、保留を切って、その最中に参加確認へ切り替えたところ、参加確認が出ている間の完了後の `router.replace('/')` は、ガードされたルートへ向かうので、何も起きなかった（無害）。有害なのは、完了までに参加確認を終えて別の画面へ進んでいた場合（`router.back()` が、開いている別の画面を戻す。カテゴリ編集の `router.replace('/categories')` が、設定の先の画面へ飛ばす）で、これは再現していない（`mounted` が、外れた画面で偽、外れていない画面で真になることだけを、同じ実験で確かめた）。通信の最中の保留（エミュレータで確認済み）と、この2つで、どちらも防ぐ。支出・月締め・カテゴリ編集のシートは、同じ関数を呼ぶだけで、通信の最中・ダイアログを開いたままでの確認はしていない。
- **Androidで、戻る操作でアプリを閉じたあと（Activityが終わり、プロセスは残る）に招待URLを開くと、`url` イベントは届かない**（新しいActivityが作られ、`onNewIntent` を通らない）。そのため、`getInitialURL` を、ルートがマウントされるたびに読み直す（`platform/inviteLink.ts` の `startInviteLinks`。エミュレータで、読み直さないと招待が捨てられることを確かめた）。**副作用（未確認。Androidの仕様からの推測）**: システムが同じActivityを作り直したとき（最近使ったアプリから開き直したときを含む）、そのActivityを起動したURLが、もう一度読まれ、手放した招待が、参加確認に出ることがある（参加済みなら、確認を出さずに、そのグループを開く。キャンセルしたものは、もう一度出る。使えない招待は、「使えません」の案内）。新しく開いたURLと、`getInitialURL` からは区別できないので、手放した招待を覚えて捨てる形にはしない（開き直したURLを無視するほうが悪い）。**見分ける手がかりの候補**: 最近使ったアプリから開き直した起動には、Intentに `FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY` が付く。このフラグが付いた起動の招待URLは捨てられる可能性があるが、JSの `Linking` からは読めず、ネイティブのコード（config plugin か小さなモジュール）が要る。本当に繰り返し出て困るなら、検討する（いまは、許容している）。
- **内容の確認（`GET /invites/:token`）は、画面を開いたときに1回**。すでに参加中なら、何も出さず、そのグループを開く。使えない招待（期限切れ・使用済み・取り消し済みなど。サーバーは区別しない）は、「この招待は使えません」と案内の文言、「閉じる」だけ。満員（`groupFull`）なら、表示名の入力欄を出さず、「このグループは満員です（5人まで）」を出して、「参加する」を押せなくする（「5人まで」は表示だけ。判定はサーバー）。確認に失敗したら（通信など）、「もう一度」と「キャンセル」。
- **参加（`POST /invites/:token/join`）は、送り直してよい**。冪等キーは無いが、すでに参加していれば、サーバーは使用済みの招待でも 409 `already_member`（`groupId` つき）を返す（確認の `alreadyMember` と同じ）。アプリはこれを**成功として扱い**、そのグループを開く。結果が分からない失敗（通信が切れた・応答が読めない・5xx）のあとの文言は、「参加できている場合があります。もう一度「参加する」を押してください」。**自動では送り直さない**。確認のあとに満員になった（409 `group_full`）・使えなくなった（404）ときは、確認の画面と同じ案内に切り替える。競合（409 `conflict`。同じ招待で同時に参加すると、片方だけが参加する）は、もう一度押してもらう。
- **表示名**: 初期値なし・必須。規則はグループ作成と同じ（`validateDisplayName`。前後の空白を落として1〜20文字、制御文字なし）。色はサーバーが選ぶ。
- **すでにグループに入っている人が、別のグループに参加したとき**: 参加した（またはすでに参加していた）グループを開く（`ui/activeGroup.ts` の `openGroup`。メモリに置き、端末にも覚える。1章の「グループの切り替えと、最後に開いたグループ」）。次の起動でも、そのグループが開く。
- **Androidの戻る操作**: 参加確認が最初の画面のとき（起動時に招待URLで開いた、またはログイン直後）は、アプリが閉じる（招待はメモリに残るので、開き直すと、また参加確認が出る）。参加確認から抜ける操作は、「キャンセル」「閉じる」。
- **確かめたのは**、Androidのエミュレータ（API 36。debugビルド）で、`fetch` とログインを偽のものに差し替えた状態（保存はしない一時の差し替え。Repositoryの読み方と本文は、本物のコードで通っている）。`warikan-seikatsu://invite/<token>` を `adb shell am start` で開いて、（レビュー対応のあと、次の4つも確かめた: グループ作成の画面にいるときに開く、支出のシートを開いているとき・設定のメンバーと招待の画面を開いているときに開く、戻る操作でアプリを閉じたあと（プロセスは残る）に開く。どれも参加確認が出る。修正前は、どれも出なかった）。未ログインの起動（ログイン画面の上部の案内 → ログイン → 参加確認）、ログイン済みの起動（グループの作成へ回されず、参加確認が出ること。招待なしの起動は、これまでどおりグループの作成へ回ること）、起動中の受け取り（メインから参加確認へ移ること）、表示名が空のときの検査、`POST` の本文（`{"displayName":"…"}`）、参加後にそのグループがメインで開くこと（2つ目のグループに参加したとき、参加したほうが開くこと）、使えない招待・満員（確認の時点と、参加の時点）・競合・すでに参加中（確認の時点）・確認の通信失敗と「もう一度」・参加の応答が途中で切れたあとの送り直し（409 `already_member` で、そのグループが開くこと）・「キャンセル」、キーボードを出したときにボタンが隠れないこと、ダーク、戻る操作。**未確認**: 本物のWorkerとの通信（`API_ORIGIN` が仮の値）、iOS（URLスキーム・Universal Links、`xcrun simctl openurl`）、https の招待URL（置き場が未決で、Universal Links / App Links を設定していないので、OSがアプリへ渡さない。`parseInviteLink` は、置き場を指定したテストで確かめている）、本物のApple / Googleのログインを経由した流れ、Android 14以下の実機、スクリーンリーダー、文字サイズを大きくしたとき、長いグループ名・表示名。

## 3. ホーム

アプリを開いて最初に見る画面。選んだ月の支出の総額、メンバー別の負担額、精算、支出の一覧を、1画面の縦スクロールで出す。

### 月の切り替え

- 上部に「◀ 2026年11月 ⌄ ▶」。矢印で前後の月に移り、月の表示をタップすると月の選択（ピッカー）を開く
- 初期表示は、カレンダー上の今月
- 選べるのは、自分が参加（または復帰）した月から、支出を登録できる最も新しい月まで（今月を早めに締めていれば翌月まで）。月の一覧API（`GET /groups/:id/months`）が返す範囲をそのまま使い、アプリで計算しない。初期表示の今月も、同じ応答の `currentMonth`
- ピッカーでは、月ごとに状態の印を出す（未締め / 精算が残っている / 処理済み）。印は、同じ応答の `status`（`open` / `unsettled` / `settled`）の値で決める。締めずに飛ばした月（`skipped`。もう締められない）は、未締めと別の印にする
- 月を変えると、総額・負担額・精算・支出の一覧がすべてその月に切り替わる
- Premiumの導入後は、Freeは処理済みの月を直近3ヶ月だけ見られる。それより古い月は、ピッカーに鍵の印を出してPremiumに案内する（未処理の月は常に見られる）。MVPには入れない

### 画面の上から順に

1. **お知らせ**（あるときだけ。複数あれば重ねて出す）
   - 前の月が未締め：「10月がまだ締められていません」。タップで10月に移る。出すのは、選んだ月の `close` が、前の月を先に締めるよう求めているとき（`previous_month_not_closed`）だけ。グループで最初の月は、前の月が未締めでも締められる（バックエンド設計メモ 4章の「最初の月」）ので、そのときは出さない
   - 前の月の送金が未処理：「10月分の精算が残っています」。タップで10月に移る
   - メンバーが増減した：「メンバーが変わったため、負担割合を均等に戻しました。見直してください」。タップでカテゴリの一覧へ。「確認した」で閉じる（実装したところの「メンバーが増減した」お知らせ）
   - 固定費が止まった：「家賃の固定費が止まっています。支払う人を選び直してください」。タップで固定費の編集へ
   - 1人だけのグループ：「相手を招待する」のカード
2. **その月の支出の総額**（いちばん大きく出す）
   - 「2026年11月の共同支出 ¥128,450」。その月に登録した支出だけの合計で、繰越は含めない
   - 締めた月は「締め済み」の印を添える
3. **メンバー別の負担額**
   - メンバーごとに、アイコン（名前の頭文字）、名前、その月の負担額。繰越は含めない
   - 3人までは横一列。4人以上は折り返す
   - 下の「内訳を見る」（折りたたみ）で、メンバーごとの支払額・負担額・差額・繰越と、カテゴリごとの合計・負担額・割合を出す。上限額つきのカテゴリは「月1万円まで自分」を添える
   - 締めていない月では、内訳のカテゴリをタップすると、その月のカテゴリの編集（6章）を開く。割合を見ながら直せるようにする
4. **精算**（後述）
5. **支出の一覧**
   - その月の支出を全件出す。日付の新しい順
   - 1行に、内容（無ければカテゴリ名）、カテゴリ、日付・支払った人、金額（右側に大きく）
   - 「この支出だけ負担を変える」を付けた支出と、固定費から作られた支出には、小さな印を付ける
   - タップで、詳細を挟まずに編集のシートを開く（締めた月は読み取り専用）
   - 支出が無い月は、「＋から支出を登録できます」と出す

### 精算のカード

送金は、誰から誰へいくら払うかの組み合わせで出す（「彼女 → あなた ¥13,450」）。3人以上で送金が複数あるときは、縦に並べる。前の月からの繰越は、合算した後の送金として出す。

**締める前（見込み）**

- 見出しは「いまの精算見込み」。その時点の支出と、前の月の繰越から計算した送金を出す
- 繰越があるときは、「先月からの繰越 ¥5,000 を含みます」と添える（内訳は「内訳を見る」で、メンバーごとに出す）
- 差額が無いときは「いまのところ精算はありません」
- 送金の操作ボタンは出さない（締めるまで確定しないため）
- カードの下に「この月を締める」ボタン。押せないときは、ボタンを押せなくして理由を添える
  - 前の月が未締め：「先に10月を締めてください」
  - 前の月の送金が未処理：「先に10月分の精算を済ませてください」
  - まだ始まっていない月は、そもそも選べない

**締めた後**

- 見出しは「11月の精算」と、未処理の件数（「未処理 2件」）
- 送金ごとに、向き・金額・状態（未処理 / 精算済み / 繰越済み）
- 未処理の送金には「精算完了」「繰越」のボタン（5章）
- すべて処理済みなら、「11月分は処理済みです」と出し、カードを小さくする

## 4. 支出の登録・編集

下のナビの＋、または支出の一覧の行のタップで、下から出るシート（モーダル）を開く。登録も編集も同じシートを使う。

```
┌──────────────────────────┐
│ 支出を登録            ✕ │
│        ¥ 1,200+800       │  ← 金額（式と結果）
│ [▲家賃][▲食費][▲外食]→  │  ← カテゴリ（▲はアイコン）
│ 支払った人 [あ あなた|か 彼女] │
│ 11/19(水)    内容 >      │
│ □ この支出だけ負担を変える │
├──────────────────────────┤
│  1   2   3   ÷          │
│  4   5   6   ×          │
│  7   8   9   −          │
│  0  00   ⌫   +          │
│ [     保存 ¥2,000      ] │
└──────────────────────────┘
```

### 金額（電卓つきのキーパッド）

- シートを開くと、画面下に専用のキーパッドを出す。OSのキーボードは使わない
- 数字、`00`、`⌫`、`+ − × ÷` のキー。小数のある通貨（USDなど）では、`00` の代わりに `.` を出す
- 式を入れると、金額の欄に式と結果を出す（「1,200+800 = ¥2,000」）。`=` キーは置かず、保存のボタンに結果を出す（「保存 ¥2,000」）
- `×` `÷` で通貨の最小単位より細かくなったときは、四捨五入する
- 結果が0以下、または上限（1件 `10^12`）を超えるときは、保存ボタンを押せなくする
- 編集で開いたときは、保存されている金額を式なしで入れておく
- 数字の並びは、設定で「電卓（7 8 9 が上）」と「スマホ（1 2 3 が上）」から選べる。初期値はスマホ。演算子・`00`・`⌫`・保存の位置は、どちらでも変えない

### 他の項目

上から順に、よく変える項目を並べる。

1. **カテゴリ**：アイコンつきのチップを横スクロールで並べる。並びは設定で並べた順（グループで共通）。初期値は、この端末で前回選んだカテゴリ
2. **支払った人**：メンバーのアイコン（頭文字と色）と名前の切り替え。初期値はいつも自分。3人以上でも横に並べ、収まらなければ横スクロール
3. **日付**：初期値は今日。タップでカレンダーを開く。登録する月と関係なく選べる
4. **内容**：任意。1行。タップしたときだけOSのキーボードを出し、キーパッドは隠す。金額をタップすると、キーパッドに戻る
5. **登録する月**：選べる月が2つ以上あるときだけ出す（例：「10月分 / 11月分」）
   - 初期値は、日付の月が登録できる月ならその月、できなければ、登録できる月のうち今月に最も近い月
   - 早めに締めた月の日付を選んだときは、「10月は締めたため、11月分として登録します」と添える
6. **この支出だけ負担を変える**：チェック。オンにすると、次を出す
   - 方法：割合で分ける / 均等に分ける / 金額を指定する / 1人が全額負担
   - 割合・金額は、メンバーごとに入力する（金額はキーパッドで入れる）。合計が合わないときは、差を出して保存できなくする
   - 各メンバーの負担額のプレビュー
   - オフのときは、「カテゴリの割合（7:3）で分けます」とだけ出す。1件ごとの負担額は出さない（カテゴリの負担は月の合計に割合をかけて計算し、上限額もあるため、1件ずつの金額は実際の計算と合わない）

### 保存・削除

- 「保存」で保存して、シートを閉じてホームに戻る。続けて登録するボタンは置かない
- 登録した支出の月とホームで見ている月が違うときは、「11月分として登録しました」のトーストを出す（ホームの月は切り替えない）
- 編集のときは、シートの下に「この支出を削除」も出す（確認ダイアログあり）
- 締めた月の支出は、同じシートを読み取り専用で開く。キーパッド・保存・削除は出さない
- 削除されたユーザー・脱退済みのメンバーは、新しく登録する支出の支払者・負担の対象に選べない。脱退が確定したメンバーは、脱退月までの月の支出には選べ、翌月分には選べない（バックエンド設計メモ8章。既存の支出には名前のまま出す）
- 入力中にシートを閉じようとしたときは、「入力内容を破棄しますか？」と確認する
- 保存したときに他のメンバーの更新とぶつかった場合は、サーバーが1回だけやり直す（バックエンド設計メモ8章）。それでも失敗したときは「他のメンバーが更新しました。もう一度保存してください」と出し、入力内容は消さない
- 保存しようとした月が、その間に締められていたときは、「11月は締められました。12月分として登録しますか？」と聞く
- 削除されたユーザー・脱退済みのメンバーが負担に入っている支出は、そのメンバーの負担額が増える編集（金額を上げる、割合を上げる、など）を保存できない（サーバーが409 `member_not_available` を返す）。保存の前に画面で見分け、「○○さんは負担の対象にできません。負担の分け方を変えてください」と出して、入力内容は消さない。金額だけを上げたいときは、負担の方法を「金額を指定する」にして、そのメンバーの負担額をそのままにすれば保存できる。内容や日付だけの編集は、これまでどおり保存できる

### 実装したところ

下から出るモーダル（`app/expense.tsx` → `ui/expense/ExpenseSheet.tsx`）。登録は `/expense?groupId=`、編集は `&expenseId=&month=` を付ける（片方だけなら開かない。別の支出を作ってしまわないため）。入力の状態・検査・リクエストの組み立ては、画面の外の `src/services/expenseForm.ts`（金額の式は `amountExpression.ts`、日付は `calendar.ts`。`npm test` で守る）。画面は、それを並べて、押されたものを渡すだけ。

- **作った**: 電卓つきのキーパッド（式と結果、`保存 ¥2,000`）、カテゴリ・支払った人のチップ、日付（自前のカレンダー。ネイティブの部品は足していない）、内容、登録する月（登録できる月が2つ以上のときだけ）、「この支出だけ負担を変える」（割合・均等・金額指定・1人が全額負担）、削除（確認あり）、締めた月の読み取り専用の表示、入力中に閉じるときの破棄の確認（✕と戻る操作の両方）、保存に失敗したときの文言（入力は消さない）。
- **登録できる月は、アプリで計算しない**: 月の一覧（`GET /groups/:id/months`）の `open` の月を使う。日付の月が登録できないときは、今月に最も近い登録できる月へ入れ、「10月は締めたため、11月分として登録します。」と添える（締めた月と、そうでない月で文言を分ける）。月を自分で選んだら、日付を変えても、その月のまま。月・日付を変えて、新しい月で選べない支払者になったときは、保存できない（「支払った人を選び直してください」。チップには何も選ばれていない見た目になる）。支払者は外さないので、選べる月に戻せば、選び直さなくても、また保存できる（`syncForMonth`・`checkDraft`）。登録できる月が無いときは、支払者などより先に、「登録できる月がありません。」を出す。
- **負担額の計算とプレビューは出さない**: 上の設計は、割合・均等で「メンバーごとの負担額のプレビュー」を出すとしていたが、端数の配り方をアプリに書き写すことになり、「負担・精算の計算はWorkerだけが持つ」（CLAUDE.md）と衝突するので作っていない。金額指定は、入力した金額が負担額なので、そのまま。ここでするのは、入力の形の検査（割合の合計が100%、金額指定の合計が金額と一致、など）と、リクエストの組み立てだけ。「カテゴリの割合（7:3）で分けます」の割合も、費目の割合を読む画面が無いので、「カテゴリの割合で分けます。」とだけ出す。
- **保存できない理由は、保存ボタンの上に1か所だけ**出す（割合・金額指定の合計の食い違いも）。入力欄の下に出すと、キーボードで隠れて、理由の見えないまま保存できなくなる（エミュレータで確かめた）。
- **キーボード避け**: `KeyboardAvoidingView` の `behavior="padding"` を、Androidでも使う。アプリは edge-to-edge（`android/gradle.properties` の `edgeToEdgeEnabled=true`）で、`adjustResize` を指定しても、キーボードでウィンドウが小さくならない（このシートで、保存ボタンがキーボードの下に隠れることを、エミュレータ（API 36）で確かめた）。**作成画面（`app/create-group.tsx`）も、Androidで `behavior` を指定していなかったため、下端の「作成」がキーボードの下に隠れた**（エミュレータで確かめた。入力欄は上のほうにあるので、2章の確認では見逃した。キーボードの確定キーでは作成できた）。同じく `padding` にして、ボタンがキーボードの上に出ることを確かめた。モーダルかどうかは関係なかった。
- **登録の識別子**（`id`）は、最初に保存を押したときに1回だけ作り、やり直しでも同じ値を送る（通信が切れて結果が分からないとき、支出が2件にならない）。副作用として、結果が分からない失敗のあとで入力を直して送り直すと、最初の登録が済んでいた場合は、直した内容は反映されない（保存済みの支出が返る。反映されなかった内容は、ホームの一覧から編集できる）。グループの作成と同じ判断。
- **編集は、変えた項目だけを送る**（内容・日付だけの編集で、保存された負担額に触れない）。割合・金額指定で `split` を送るときも、**0%・0円のメンバーの行は送らない**（元の負担にいた人を除く）。途中参加のメンバーの0の行を足すと、負担額が無いのに行が増え、あとで脱退が確定するとき、負担に関わっているとみなされうる（`worker/src/closedMonth.ts` の `markLeftStatement`）。送らなくても、負担は同じ。金額を変えるときは `currencyCode` を添え、費目の割合でない支出では `split` も添える（サーバーが求める）。負担の指定を変えたときも `split` を送る。知らない負担の方法（サーバーが足した値）の支出は、アプリが変えられないので、`split` を送らず、金額も変えられない（シートに、その旨を出す）。
- **編集で「金額を指定する」へ切り替えたとき**は、保存された負担額が初期値に入る（割合・均等の支出から切り替えても。使えないメンバーを含む支出の金額を上げる回避策で、そのメンバーの負担額を「そのまま」にできる。保存値の表示で、計算ではない）。
- **保存・削除の最中**は、✕も、戻る操作も効かない（閉じると、完了したあとに、閉じたシートから画面を戻してしまう）。止めているのは `beforeRemove` で、これは `dispatch` された操作（戻る・閉じる）の除去でだけ評価される（React Navigation の `shouldPreventRemove` を呼ぶのは `useOnAction` と、親の除去だけ）。**セッション切れで画面が外れるとき（`Stack.Protected` のガードの切り替え）は、通らない**ので、保存の最中にセッションが切れても、ログイン画面へ戻れる（ソースを読んで確かめた。実機では未確認）。
- **登録・編集のあとの案内**: ホームで見ている月と違う月に保存したら、ホームに「10月分として登録しました」を5秒出す（トーストではなく、画面の上のお知らせ。Androidだけにある部品に頼らないため。`src/services/expenseNotice.ts` で、シートからホームへ受け渡す）。登録先の月が、開いているあいだに締められたら、「11月は締められました。12月分として登録しますか？」と聞く（同じ `id` で、月だけ変えて送る。聞く先は、サーバーが返す登録できる範囲のうち、選んでいた月に近いほう。月の選択肢は、開いたときに読んだ月の一覧から出すので、締め以外の理由では起きない）。使えないメンバーで断られたときは、支払者が原因なら「支払った人を選び直してください」、負担の対象が原因なら「負担の分け方を変えてください」と分けて案内する。
- **前回選んだカテゴリ**は、この端末の Documents（`platform/lastCategory.ts`）に、グループごとに覚える。読み書きに失敗しても、先頭のカテゴリから始まるだけ。
- **キーパッドの並び**は、アプリの設定（6章の「アプリの設定」）で、スマホ（1 2 3 が上。初期値）と電卓（7 8 9 が上）から選ぶ。割合の入力は、OSの数字キーボード（キーパッドは隠れる）。
- **まだ作っていない**: 保存の前の、メンバーが使えない編集の見分け（「○○さんは負担の対象にできません」。サーバーが409 `member_not_available` を返したときに、同じ文言を出す。入力は消さない）。
- **確かめたのは**、Androidのエミュレータ（API 36）で、`fetch` を偽のものに差し替えた状態（保存はしない一時の差し替え。Repositoryの読み方と、リクエストの本文は、本物のコードで通っている）。登録（本文の中身を、偽のサーバー側で確認）、編集（金額だけ変えた本文は `amountMinor` と `currencyCode` だけ、割合の支出は `split` つき）、削除、締めた月の読み取り専用、競合・登録先が締められたときの案内と再送、破棄の確認（✕とハードウェアの戻る）、キーパッドの金額指定（メンバーごと）、割合の合計エラー、カレンダー、登録する月の選択と、ホームのお知らせ、ライト・ダーク。**未確認**: 本物のWorkerとの通信（`API_ORIGIN` が仮の値）、iOS（キーボード回避、モーダルの見た目）、Android 14以下の実機（Pixel 3は、ロック中で操作できなかった）、日本語の入力（確認はASCIIだけ）、文字サイズを大きくしたとき、スクリーンリーダーでの読み上げ、4人以上のメンバー、小数のある通貨の画面（ロジックは `npm test` で確認済み）、通信の失敗（`network`）の画面、**保存・削除の最中にセッションが切れたとき**（上の `beforeRemove` の説明どおり、ログイン画面へ戻れるか）。

## 5. 締めと精算

### 締めの確認

ホームの精算のカードで「この月を締める」を押すと、確認のシートを出す。

- 確定する送金の一覧（「彼女 → あなた ¥13,450」）。前の月の繰越があれば「先月からの繰越を含みます」
- 「締めた後は、この月の支出を追加・変更・削除できません」
- 月の途中で締めるときは、「まだ月の途中です。この月の残りの支出は、12月分として登録します」を目立たせる
- 脱退を選んでいるメンバーがいるときは、「Aさんの脱退は、この月を締めると確定します」
- 「締める」「キャンセル」

締めると、ホームの精算のカードが「締めた後」の表示に変わる。他のメンバーが先に締めていた・支出を変えていたときは、「内容が変わりました」と出して、確認の内容を読み直す（締めはやり直さない。誰かの操作とは言わない: 脱退月が飛ばされた月の締めも、同じ競合になる。実装したところを参照）。

### 精算完了・繰越

締めた後の精算のカードで、未処理の送金ごとに操作する。

- 「精算完了」：確認ダイアログ「彼女 → あなた ¥13,450 を精算済みにします。元に戻せません」
- 「繰越」：確認ダイアログ「¥13,450 を12月の精算に合算します。元に戻せません」
- 繰越できない送金（脱退するメンバー・削除されたユーザーが関わる）は、「繰越」を出さず、「脱退するメンバーや削除されたユーザーが関わる送金は、繰り越せません」と添える
- 精算済み・繰越済みには、操作した日を添える
- 繰り越した金額は、翌月のホームで、精算の見込みに合算して出る（3章）

### 実装したところ

締めの確認のシートは、下から出るモーダル（`app/close.tsx` → `ui/close/CloseSheet.tsx`。`/close?groupId=&month=`）。出す内容の組み立ては画面の外の `src/services/closeView.ts`、失敗の文言は `settlementMessage.ts`、HTTPは `settlementRepository.ts`（どれも `npm test` で守る）。精算完了・繰越は、ホームの精算のカード（`ui/home/SettlementCard.tsx`）のボタンから、`ui/home/useTransferActions.ts` が、確認ダイアログ、実行、ホームの読み直しの順に行う。

- **確認のシートは、開くときに読み直した集計で出す**（グループ・月の一覧・その月の集計。`settlementService.loadClose`）。ホームが読んだ集計を渡して出す形に、簡略化しない。サーバーは、確認した内容を指定して締めることができず、他のメンバーがそのあいだに支出を変えると、締めた結果は、確認の内容と違いうる。せめて、開いた時点の最新を見せる。締めたあとの結果は、ホームが取り直した値が正。
- **締められるかは、サーバーの答え**（summary の `close.closable`）に従う。押せないときは、ボタンを押せなくして理由を添える。「月の途中」（サーバーが返す今月と同じ月）と、脱退が確定するメンバーの注意書きは、表示のためだけで、判断に使わない。
- **締めは、やり直さない**。断られたとき（`conflict`・`month_closed`・前の月が未処理、など）は、文言を出して、確認の内容を読み直す（自動で締め直さない。内容を見て、もう一度押してもらう）。読み直しに失敗したら、読み込みの失敗の表示（「もう一度」つき）にする。**そのとき、断られた理由（「先に10月分の精算を済ませてください」など、次にやることが分かるもの）は、捨てずに、読み込みの失敗の文言の上に並べる**（`withReloadFailure`）。他のメンバーが先に締めていたとき（読み直すと、締めた月の結果が届く）は、上の案内（「この月は、すでに締められています」）だけを出し、断りの文言は重ねない。
- **競合の文言は、「内容が変わりました」**（誰かが操作したとは言わず、読み直せたとも言わない）。`conflict` は、他のメンバーの書き込みとの競合のほかに、脱退月が最初の締めで飛ばされた月のとき（Workerが、先に脱退を確定させて、締めずに409を返す。バックエンド設計メモ 5章の「脱退」2）にも返る。精算・繰越の読み直しは、ホームの読み込みが担い、失敗しても投げない（読み直せたかを、操作の側は知らない）ので、「読み直しました」とは言わない。通信の失敗・応答が読めないときは、読み直さず、「ホームで確認してください」と案内する（済んでいても、もう一度押すと 409 `month_closed` で断られるだけで、二重にはならない）。
- **応答は、使う項目だけ**を検べる（CLAUDE.md）。月締めは `groupDeleted` と `closed`、精算・繰越は `transfer.id`。締めた結果（`MonthView`）は読まず、ホームが取り直す。
- **精算完了・繰越**: 確認ダイアログ（取り消せないことを添える）、実行、ホームの読み直し。通信の最中は、すべての操作ボタンを押せなくする（1つずつ処理する）。サーバーが断ったとき（他のメンバーが先に処理した、など）は、文言を出して、読み直す。通信の失敗では、読み直さない。「繰越」を出すかは、送金の `canCarry`（サーバーの値。未処理のときだけ）。出さない送金には、「脱退するメンバーや削除されたユーザーが関わる送金は、繰り越せません」を添える。確認ダイアログの繰越先の月の名前（「12月」）は、締めた月の翌月を、表示のために出しているだけ（繰越先はサーバーが決める）。
- **最後の1人の脱退で、締めずにグループごと消えたとき**（応答 `groupDeleted`）は、シートでそのことを案内して閉じ、所属グループの一覧を読み直す（`reloadGroups`。3章の「所属を失ったとき」）。**締める前に、サーバーの値で警告する**: 集計の `close.deletesGroup`（締めると、グループのデータがすべて消える。バックエンド設計メモ 9章の「月締め・精算API」）が true の月は、確認のシートが、削除の警告を目立たせ、ボタンを「グループを削除して脱退」にし、押したあとに確認ダイアログを挟む（取り消せないため）。このとき、月は締められず、送金も作られないので、確定する送金・月の途中の注意・脱退の注意・「締めた後の制限」は出さない（`src/services/closeView.ts`。`npm test` で確かめている）。最後の1人かの規則（Workerの `isLastMember`）は、アプリに書き写さない。`deletesGroup` は、読めなければ失敗にする（警告が出ないまま、締めさせないため。読み込みの応答は、全項目を検べてよい）。 **確認の申告**: 締めるとグループが消える、という警告を出した確認（`deleteConfirm`）のあとにだけ、締める呼び出しに申告（`acknowledgeDelete=true`）を付ける。シートを開いたあとで、他のメンバーが脱退済み・削除済みになり、通常の締めのつもりが、グループを消すことになったときは、サーバーが何も消さずに409 `delete_not_acknowledged` で断る（文言は「状況が変わりました。この月を締めると、グループのデータがすべて削除されることになったため、確認し直してください。」。断られたので、シートは読み直し、警告つきの確認に変わる）。
- **通信の最中**は、シートの✕も、戻る操作も効かない（`beforeRemove`。前提と限界は、4章の「保存・削除の最中」と同じ）。
- **シートを開くボタンの二重タップ**: `app/_layout.tsx` の `expense`・`close` に `dangerouslySingular` を付けている（外さない）。付けないと、「この月を締める」を素早く2回押したとき、`router.push` が2回通って、シートが2枚重なる（エミュレータで確かめた。戻る操作を1回しても、下のシートが残った）。付けると、戻る操作1回でホームに戻る（締めのシートと、＋の支出のシートで確かめた。＋は、付ける前の状態は試していない）。**`members`（メンバーと招待）にも付けている**（入口は、設定の行と、ホームの「相手を招待する」カード）。付ける前は、カードを2連打（`adb shell 'input tap … & input tap … & wait'`）すると、戻る操作を1回しても「メンバーと招待」が残った（2枚重なった）。付けたあとは、2連打を2回試し、どちらも戻る操作1回でホームに戻り、1回のタップでは通常どおり開く。この画面は、発行した招待のトークンを画面のメモリだけに持つので、重なっていると、上の画面で発行して戻ったとき、下の画面の一覧では「共有」で出し直せない（取り消して作り直すしかなくなる）。設定の行から開いた場合は、同じ設定なので確かめていない。**`categories`（カテゴリと負担割合。入口は設定の行だけ）にも付けた**。付ける前も付けたあとも、エミュレータでは試していない（expo-routerのソースを読んで、`members` と同じ仕組みで効くと判断した）。次にエミュレータを動かすときは、設定の行を2連打して、戻る操作1回で設定に戻ることを見る。
- **確かめたのは**、Androidのエミュレータ（API 36。debugビルド）で、`fetch` を偽のものに差し替えた状態（保存はしない一時の差し替え。Repositoryの読み方と本文は、本物のコードで通っている）。10月の未処理の送金2件（繰り越せるものと、脱退するメンバーが関わり繰り越せないもの）、10月が済むまで11月の「この月を締める」が押せず理由が出ること、繰越・精算完了の確認ダイアログ（キャンセルでは通信しないこと）と実行、すべて処理済みで小さくなること、11月の確認のシート（月の途中の注意）、1回目の締めが競合（409）になり、文言と読み直した金額が出ること、2回目で締まってホームが締め済みになること、精算完了が断られた（`transfer_not_pending`）ときの文言、ライト・ダーク。読み込み・組み立て・文言・Repository・Serviceは、`npm test` で確かめている。**未確認**: 本物のWorkerとの通信（`API_ORIGIN` が仮の値）、iOS、Android 14以下の実機、通信の失敗（`network`）・応答が読めないとき・締めの最中にセッションが切れたときの画面、締めの最中の✕・戻る操作が止まること、開いているあいだに他のメンバーが先に締めたときの画面（組み立ては `npm test`）、`groupDeleted` の画面、脱退を選んでいるメンバーの注意書きの表示（組み立ては `npm test`）、メンバーが多く送金が何件も並ぶときの見た目、文字サイズを大きくしたとき、スクリーンリーダーでの読み上げ。
- **（解決済み）脱退を選ぶ操作（6章）を作る前に決めたこと**: 最後の1人が脱退を選んでいる月を締めると、Workerは締めずにグループのデータをすべて消す（`groupDeleted`）。脱退を選ぶときの確認ダイアログだけでは、選んでから締めるまでに時間が空くので、**締める直前のシートでも警告する**。最後の1人かの規則は書き写さないので、サーバーが `summary` の `close.deletesGroup` で返し、シートは、それで警告と「締める」の文言を出し分ける（上の項目）。
- **（解決済み）ホームの「相手を招待する」カード**: 最後の1人が脱退を選んでいる月は、人数の値だけではカードを止められないので、**自分の `leaveRequestedMonth` で止めることにした**（3章の「相手を招待する」カード）。最後の1人かの判定は、これでは要らない（脱退を選んでいる人には、最後の1人でなくても出さない）。
- **まだ作っていない**: 精算済み・繰越済みの送金に、操作した日を添えること（応答の `settledAt`・`carriedAt` を、アプリは読んでいない。出すときは、グループのタイムゾーンで表示する）。

**実装したところ**: 下のナビの「設定」（`ui/settings/SettingsScreen.tsx`）は、いまは「このグループ」の**カテゴリと負担割合**・**固定費**・**メンバーと招待**・**グループの設定**（それぞれ下の節。脱退を選ぶ操作は、メンバーと招待の画面の一番下）と、「アプリの設定（この端末だけ）」の**キーパッドの並び**、「アカウント」の**ログアウト**・**アカウントを削除**、**このアプリについて**（それぞれ下の節。このアプリについては、ライセンスを含む）。

### カテゴリと負担割合

**一覧**

- 上部に、対象の月（「6月の負担割合」）。締めていない月の間で切り替えられる。初期値はホームで見ている月
- カテゴリごとに、名前と割合（「家賃 7:3」）。上限額つきなら「外食 月1万円まで自分、超えた分 0:10」
- 「カテゴリを追加」。並べ替えは長押しのドラッグ（実装は上下の矢印。下の「実装したところ」の「並べ替え」）。この並びが、支出の登録画面のチップの並びになる（グループで共通）
- この一覧のほかに、ホームの「内訳を見る」のカテゴリからも、同じ編集画面を開ける
- 変更は、選んだ月とそれ以降の月に反映される（締めた月は変わらない）ことを、一覧の下に書く。ただし、それより後の月に別の設定がある月（メンバーの増減で均等に戻した月）は変わらない。保存の応答の `overriddenMonths` に、その月が入るので、「X月以降は別の設定があります」と案内する

**割合の表示**

- 2人のとき、10%単位で割り切れる割合は「7:3」、それ以外は「65% : 35%」と出す
- 3人以上のときは、%で並べる（「40% / 30% / 30%」）
- 均等にリセットした割合（3人の33.34% / 33.33% / 33.33%など）は「均等」と出す

**カテゴリの編集**

- 名前
- アイコンと色：用意したアイコン（30個ほど。家・カート・食器・電球・電話・Wi-Fi・車・薬など）と、色（10色ほど）から選ぶ。絵文字は使わない（両OSで見た目をそろえるため）
- 負担割合
  - 2人のとき：スライダーと、よく使う割合のボタン（5:5、6:4、7:3、8:2、10:0）。1%単位
  - 3人以上のとき：メンバーごとの%入力と「均等にする」。合計が100%でないときは、差を出して保存できなくする
  - 0.01%単位の入力は見せない（DBは0.01%単位で持つ。均等のリセットのときだけ使われる）
- 上限額つきにする（スイッチ）
  - 上限まで負担する人、上限額（月あたり）

  - 説明の例を、入力した値でその場に出す（「月の合計が8,000円なら、自分が8,000円。15,000円なら、自分が10,000円、相手が5,000円」）

**実装したところ（カテゴリと負担割合）**: 一覧は `ui/settings/CategoriesScreen.tsx`（`app/categories.tsx`。`dangerouslySingular`。5章の「シートを開くボタンの二重タップ」）、追加・編集のシートは `ui/settings/CategoryEditSheet.tsx`（`app/category-edit.tsx`。`dangerouslySingular`。下から出る）。出す内容の組み立ては `src/services/categoryView.ts`、入力の検査と保存の組み立ては `src/services/categoryForm.ts`、失敗の文言は `src/services/categoryMessage.ts`、読み書きは `src/services/categoryService.ts` と `src/repositories/categoryRepository.ts`・`categorySharesRepository.ts`（どれも `npm test` で守る。画面は、並べて、押されたものを渡すだけ）。**負担額の計算も、プレビューも出さない**（CLAUDE.md）。

- **月**: 切り替えは、一覧の `status` が `open`（締めていない月）の月だけ。初期値は、いま選んでいる月が選べればそれ、なければ今月（**設計の「ホームで見ている月」は引き継いでいない**。ホームの月の状態は、画面をまたいで持っていないため）。その月の割合を直せるかは、読んだ割合の `editable` で決まる（アプリで月の範囲を計算しない）。直せない月は、シートの割合の欄を出さず、名前・アイコン・色だけ変えられる。**切り替えの通信の最中は、行と「カテゴリを追加」を押せない**（まだ前の月の割合を持っていて、シートが前の月で開く。戻ったときの読み直しが、切り替えの応答を捨てて、選んだ月が前の月に戻ることもある）。
- **割合の表示**: `src/services/shareFormat.ts`（「7:3」「65% : 35%」「40% / 30% / 30%」「均等」。2人の5:5は「均等」ではなく「5:5」）。並びは、**自分が先**、あとはグループのメンバーの並び（サーバーが返す `memberIds` の順は使わない）。上限額つきの行は、「月¥10,000までゆうき、超えた分 0:10」。
- **割合の入力**: スライダーは作っていない。2人のときは、よく使う割合のボタン（5:5・6:4・7:3・8:2・10:0。先頭の人の割合）と、メンバーごとの%の入力欄で、**片方を直すともう一方が残りになる**（空・読めない値・100%超のあいだは、もう一方を変えない）。3人以上は、欄ごとの入力と「均等にする」。合計が100%でないときは、差を添えて保存を止める（保存ボタンの上に出す）。**設計の「1%単位」「0.01%単位の入力は見せない」との差**: 入力欄は、小数第2位（0.01%）まで打てて、検査で止めない（`parsePercent`。支出のシートと同じ）。均等にリセットした割合（33.34 / 33.33 / 33.33）を読み込んで、そのまま保存できるようにするため。0.01%単位を促す操作（細かいスライダー、刻みのボタン）は作っていない。
- **上限額つき**: スイッチを入れると、超えた分の割合は「上限まで負担する人を0%、残りを均等」にする（先頭は自分）。人を変えても同じ。**スイッチを入れて切ると、割合は入れる前に戻る**（試しに入れて切っただけで、割合が書き換わって「変更あり」にならない。開いたときから上限つきの費目は、つける前の割合を知らないので、切っても欄の値のまま）。**切って、また入れると、切る前の上限つきの入力（超えた分の割合・人・上限額）に戻る**（元の割合を、初期値で上書きしない）。上限額は、金額の式の評価（`amountExpression.ts`）で最小単位にする。**設計にあった「入力した値でその場に出す説明の例」は作っていない**（負担額の計算を、アプリに書き写すことになる）。
- **保存**: 名前・アイコン・色（`PATCH`）と、割合・上限額（`PUT`）の2つの呼び出しで、**変えたものだけを送る**。`PUT` が `overriddenMonths` を返したら、「○月には、別の設定があるため、変えていません。」と案内する。名前などが済んで割合が断られたら、名前などは済んだこととして、やり直しでは割合だけを送る（そのあとに閉じるときの破棄の確認は、「先に保存した名前・アイコン・色は、そのまま残ります」と伝える）。「使わない」を、入力を直したあとに押すと、その確認のダイアログが「入力した変更は保存されません」と伝える（そのまま閉じて、破棄の確認は出ないため）。破棄の確認を出すかは、スイッチの入り切りのような、元に戻った操作を数えない（`isDirty`）。他のメンバーの操作で古くなった（`conflict`・`members_changed`・`categories_changed`・`month_closed`）と断られたら、読み直して、入力を新しい内容から作り直す。
- **追加**: 名前・アイコン・色だけ。割合は、サーバーが均等で作る（**設計にあった、追加のときに割合を入れることは作っていない**。2つの呼び出しの途中で失敗した状態を増やさないため。追加したあと、一覧から直す）。`id` は、最初に保存を押したときに1回だけ作り、やり直しでも使い回す。**サーバーは、同じ `id` の再送に、保存済みの費目をそのまま返す（内容は見比べない）ので、結果が分からない失敗（通信の失敗・応答が読めない・混雑）のあとに入力を直して送り直すと、直した内容が反映されない。そのため、その送り直しのあとに、直した内容を `PATCH` で送る**（同じ内容なら変わらない）。サーバーが断った失敗（作られていない）のあとは、送り直さない。追加が断られても、**読み直さず、入力を残す**（追加の入力に、サーバーの内容に合わせて作り直すものが無い）。**作成の呼び出しの** 409 `conflict` には、Workerで2つの意味がある（この `id` を他のグループが使っている、書き込みの競合が2回続いた）。どちらも作られていないので（他のメンバーの操作との競合ではない）、新しい `id` にして、もう一度押してもらう。**作成が済んだあとの `PATCH` の失敗は、作成の失敗と分ける**（文言は、失敗の種類によらず「カテゴリは追加できましたが、入力した内容を反映できませんでした。」から始める。通信の失敗でも、追加できなかったと思わせない。作成は済んでいるので、`id` を取り直さない。取り直すと、同じカテゴリが2つできる）。そのあとに閉じるときの破棄の確認は、「カテゴリは、すでに追加されています。入力した変更は保存されず、名前などは追加したときの内容のままです。」と伝える。やり直しでは、作成は送らず、`PATCH` だけを送る。この手順は `src/services/categoryCreate.ts` にあり、「通信失敗 → 作成は成功したが `PATCH` が409 → 次に押す」の流れを含めて `npm test` で守っている。新しいカテゴリのアイコン・色は、既存と重ならないものを先に選ぶ。アイコンは30個（`src/theme/categoryIcons.ts`）、色は10色。
- **使わない（アーカイブ）**: 編集のシートの下のボタン（確認のダイアログつき）。使わないカテゴリは、一覧の下にまとめて薄く出し、開くと「また使う」になる。

### 固定費

**一覧**

- 名前（内容）、金額、毎月の日、支払う人、カテゴリ
- 止まっている固定費は、上にまとめて理由を出す（「支払う人が脱退しました」「メンバーが変わったため、負担の見直しが必要です」）
- カテゴリをアーカイブしている固定費（`categoryArchived: true`）は、止めずに「自動登録されていません」と出し、カテゴリを戻すか選び直すよう案内する。見送られていた今月の分は、戻す・選び直すのどちらでも、すぐ後に作られる。手で入力済みなら二重になるので、「手で入力した分があれば、あとで片方を削除してください」と添える

**編集**

- 金額、内容、カテゴリ、支払う人、毎月の日（1〜31日。29〜31日は「その日がない月は月末日」と添える）
- この固定費だけ負担を変える（支出の登録と同じ入力）
- 開始する月。変更は、まだ作っていない月の分から反映することを書く
- 「止める」「再開する」「削除」（削除は、一度も支出を作っていない固定費だけ。「今月の分は作られません」と案内した固定費も、まだ消せる。作った固定費は、「止める」か、終了する月を決める）
- 今月の予定日を過ぎてから登録・再開したとき（応答の `thisMonthSkipped` が true）は、「今月の分は作られません。必要なら支出を直接登録してください」と添える（登録の再送の応答でも返るので、通信が切れたあとでも出せる）。`thisMonthSkipped` は「今月の分を作らない記録がいまある」という状態なので、止めて再開したときや、内容を直しただけのときも true が返る。案内は、登録・再開・日・開始月・終了月を変えた操作のあとに出し（終了した固定費の終了月を今月以降に延ばして、今月の予定日を過ぎているときも、今月の分を作らない記録が残る。サーバーの `isDueThisMonth` は終了月も見る）、内容を直しただけのときは出さなくてよい。個別の負担の固定費を再開するときは、負担の指定を確認する画面を挟む（止まっていた間にメンバーが変わっているかもしれない）

**実装したところ**（一覧は `ui/settings/RecurringScreen.tsx`、登録・編集のシートは `ui/settings/RecurringEditSheet.tsx`（下から出るモーダル。`app/recurring.tsx`・`app/recurring-edit.tsx`）。入力の規則は `src/services/recurringForm.ts`、一覧の組み立ては `recurringView.ts`、失敗の文言と案内は `recurringMessage.ts`、読み書きは `recurringService.ts` と `src/repositories/recurringRepository.ts`。`npm test` で守る。画面は、並べて、押されたものを渡すだけ）:

- **一覧**: 止まっている固定費（上にまとめて、理由を注意の色で）、登録している固定費、「固定費を追加」、終了した固定費（終了する月が今月より前。薄く）の順。「終了」は表示にだけ使う区分（作る・作らないを決めるのは、サーバー）。カテゴリをアーカイブした固定費は、止まっている欄には入れず、行に「自動登録されていません」を出す（編集のシートに、戻す・選び直すの案内と、二重になる注意。`CATEGORY_ARCHIVED_HELP`）。内容が無い固定費は、カテゴリの名前を題にする。負担を変えている固定費には印を付ける。開くたび・シートから戻るたびに読み直す（読み直しの失敗は、表示中の内容を残して知らせる）。
- **シート**: 金額（支出と同じキーパッド）・カテゴリ・支払う人・毎月の日（1〜31の格子。29〜31日は「その日がない月は月末日」）・内容・開始する月・終了する月・この固定費だけ負担を変える（支出のシートと同じ `SplitEditor`。入力の規則 `src/services/splitForm.ts` を支出と共有している）。**支払う人・負担の対象に選べるメンバーは、「最初に支出を作る月」で見る**（`firstTargetMonth`。開始する月と今月の遅いほう。それが締められていれば、最も古い未締めの月。月の一覧の `open` から決める。サーバーの `recurringTargetMonth` と同じ。サーバーも検べる）。**前回選んだカテゴリは使わない**（`lastCategory` は支出の既定。固定費のカテゴリを、日々の支出の既定にしない）。毎月の日は、選ぶまで空（既定の日を置かない）。日・月を選ぶあいだは、キーパッドを隠す（下のボタンまで届くように。金額をタップすると戻る）。
- **保存は、変えたものだけを送る**。負担の指定（`split`）は、変えたときと、**金額指定（`fixed`）の固定費の金額を変えるとき**だけ送る（割合・均等・1人は、金額だけ変えられる。いつも送ると、使えなくなったメンバーが負担に残る固定費の金額が直せなくなる）。**0%・0円の行は送らない**（支出と違い、もとの負担にいたメンバーの0の行も残さない）: サーバーは、負担を送ると、その全員が使えるかを検べる（0%の行も対象）ので、脱退したメンバーを0%にして直しても、その行を送ると409になる。「変えていないか」の比較も、もとの負担の0の行を除いて行う（`withoutZeroRows`）。
- **「止める」は、確認のダイアログのあと `paused: true` だけを送り、入力を変えているあいだは押せない**（変更を一緒に止めるのか、捨てるのかが分からなくなる）。**「再開する」（入力を変えていれば「保存して再開」）は、入力の変更も一緒に送る**（支払う人の付け替えと再開は、1回の操作でないと、サーバーが断る）。**`category` 以外の負担の固定費は、変えていなくても `split` を送り直す**（サーバーが400で求める）ので、確認のダイアログに、送る負担の分け方を出してから送る（`describeSplit`。入力した値を文にするだけで、負担額は計算しない）。再開では、もともと負担にいたメンバーの0%・0円の行は残さない（使えなくなったメンバーの行が残ると、再開が409で断られる）。再開できない理由（支払う人・負担の対象が使えない、カテゴリが「使わない」設定、負担の方法をアプリが読めない）は、送る前に `resumeBlocker` が文言で止める。
- **負担の方法をアプリが読めない固定費**（知らない方法。`RecurringExpense.split` が `null`）は、一覧を失敗にせず、金額と負担を変えられず、再開もできない（ほかの項目は直せる）。支出の `unsupported` と同じ扱い。
- **削除は、いつも出す**: 「一度でも支出を作ったか」は、一覧のAPIが返さない。作った固定費は409 `recurring_expense_in_use` で断られるので、「止める」か終了する月を決めるよう、文言で案内する。
- 今月の分が作られないとき（応答の `thisMonthSkipped`）は、**登録・再開・日・開始月・終了月を変えた操作のあとだけ**、案内のダイアログを出してから閉じる（`skippedNotice`）。内容や金額を直しただけのときは出さない。
- 登録の手順は `src/services/recurringCreate.ts`（カテゴリの追加の `categoryCreate.ts` と同じ形。`npm test` で守る）。`id` は、最初に保存を押したときに1回だけ作り、やり直しでも使い回す（固定費が2件になると、毎月2件ずつ支出が作られる）。**サーバーは、同じ `id` の再送に、保存済みの固定費をそのまま返す（内容は見比べない）ので、結果が分からない失敗のあとに入力を直して送り直すと、直した内容が反映されないまま成功する（その金額のまま、毎月、自動で支出が作られ続ける）。そのため、送り直しのあとに、いまの入力を `PATCH` で送る。** 登録が済んだあとの `PATCH` の失敗は、別の段階（`create-update`。「固定費は登録されましたが、直した内容を反映できていません」）として出し、`id` を取り直さない（やり直しでは `PATCH` だけを送る。新しい `id` にすると、同じ固定費が2件できる）。登録の409 `conflict`（他のグループが同じ `id` を使っている）は、登録されていないので、新しい `id` にする。通信の最中は、✕・戻る操作が効かない（`beforeRemove`）。招待URLによる参加確認への切り替えは、通信の最中だけ遅らせる（`useHoldInviteSwap`）。完了後に画面を戻す処理と、ダイアログから始まる書き込みは `useMounted` で守る。`app/_layout.tsx` の `recurring`（一覧）・`recurring-edit`（シート）の `dangerouslySingular` は外さない（開く行・ボタンの二重タップで、同じ画面が2枚重なる）。
- **ホームのお知らせ**（固定費が止まった・支払う人が脱退予定）と、メンバーと招待の脱退の欄の添え書き（自分が支払う人の固定費）は、作った（3章の「固定費のお知らせ」・下の「メンバーと招待」）。
- **まだ作っていない**: 固定費の並べ替え（サーバーの順のまま）。「一度でも支出を作った」固定費の見分け（APIが返さない）。
- **確かめたのは**、Androidのエミュレータ（API 36。debugビルド）で、`fetch` を偽のものに差し替えた状態（保存はしない一時の差し替え。Repositoryの読み方と本文は、本物のコードで通っている）。一覧（止まっている・登録している・カテゴリを使わない設定・負担を変えている・負担の方法を読めない固定費）、止まっている固定費のシート（理由の案内、日の選択でキーパッドが隠れること）、割合の固定費の再開（確認のダイアログに「あなた 70%、彼女 30%」。送った本文が、変えた日と、送り直した `split` と `paused: false` だけ）と、今月の分が作られない案内、登録（本文。`id`・`split`・`currencyCode`）と案内、止める（確認のダイアログと `{"paused":true}`）、作った固定費の削除が断られたときの文言、負担の方法を読めない固定費のシート（金額・負担が変えられない案内）、入力を変えて閉じたときの破棄の確認、内容の入力でキーボードが出ても保存ボタンが隠れないこと、ダーク。読み込み・組み立て・文言・Repository・Serviceは、`npm test` で確かめている。**レビュー対応のあとに、同じ手順で確かめたのは**: 脱退したメンバーを0%にして「止めたまま保存」すると、そのメンバーの行を送らない（送った本文 `{"split":{"method":"ratio","shares":[{"memberId":"m1","basisPoints":10000}]}}`）こと、登録の1回目が「結果が分からない失敗」（サーバーでは登録済み、応答が届かない）になったあとに金額を直して送り直すと、同じ `id` で再送され、そのあとに直した金額が `PATCH` で送られ、一覧に固定費が1件だけ出ること（偽サーバーは、再送に保存済みの固定費を返す）。**未確認**: 終了月を延ばしたときの案内の表示（組み立ては `npm test`）、`create-update` の失敗の画面。本物のWorkerとの通信（`API_ORIGIN` が仮の値）、iOS、Android 14以下の実機、開始する月・終了する月の送りと終了する月の入力、割合・均等・金額指定の入力（支出と共通のコードだが、このシートでは未確認）、カテゴリを使わない設定の固定費のシートの案内、終了した固定費の行、再開が断られたときの文言（`resumeBlocker`・409）、通信の失敗・セッション切れの画面、保存の最中の✕・戻る操作が止まること、文字サイズを大きくしたとき、スクリーンリーダーでの読み上げ。

### メンバーと招待

- メンバーの一覧と状態
  - 参加中
  - 脱退予定（「6月で脱退。締めるか7月1日に確定」）
  - 脱退済み（名前は残す）
  - 削除されたユーザー
- **招待する**：招待URLを作り、OSの共有シートを開く。送る文面の例：「わりかん生活で生活費を一緒に記録しよう。このURLから参加できます（3日間有効）」
  - いま招待できないとき（グループ情報の `canInvite` が false）は、ボタンを押せなくする。満員（`seatedMembers` が `maxMembers` に達している。脱退が確定した人は数えない）なら「1つのグループは5人までです」と添える。自分の脱退が確定しているときは、そもそも画面を出さない。人数の判定はアプリで書き写さない
- 未使用の招待の一覧（自分が作ったもの）。期限と「取り消す」
- **このグループから脱退する**
  - 確認ダイアログ：「6月で脱退します。6月を締めるか、7月1日に確定します。確定するまでは取り消せます」
  - 自分が支払う人の固定費があれば、「家賃の固定費は、支払う人を選び直す必要があります」と添える
  - 最後の1人のときは、「このグループのデータはすべて削除され、元に戻せません」と出し、ボタンも「グループを削除して脱退」にする
  - 脱退予定の間は、ここが「脱退を取り消す」になる

**実装したところ（メンバーと招待）**: `ui/settings/MembersScreen.tsx`（`app/members.tsx`）。メンバーの一覧と状態、招待URLの発行と共有、自分が発行した未使用の招待の一覧と取り消し。出す内容の組み立ては `src/services/memberView.ts`、失敗の文言と読み直しの判断は `src/services/inviteMessage.ts`、URLと共有の文面は `src/services/inviteUrl.ts`、読み書きは `src/services/inviteService.ts` と `src/repositories/inviteRepository.ts`（どれも `npm test` で守る。画面は、並べて、押されたものを渡すだけ）。人数の判定は書き写さず、サーバーの `canInvite` で決める（満員の説明にだけ `seatedMembers`・`maxMembers` を使う）。

- **メンバーの並び**: いる人（自分が先、あとはサーバーの並び）と、「以前のメンバー」（脱退済み・アカウントを削除した人。薄く出す）に分ける。状態は、脱退を選んだだけの人に「6月で脱退予定（6月を締めるか、7月1日に確定）」、脱退月が終わった人（Cronが `status` を書く前。サーバーが確定したものとして扱う。メンバーの `leaveEffective`）に「6月で脱退が確定」、`status` が脱退が確定した人に「脱退が確定（精算が残っています）」、脱退済みの人に「脱退済み」を添える。**脱退月が終わったかは、アプリで月を比べず、`leaveEffective` で決める**（Workerの `isLeaveEffectiveFor`。backend-design.md 9章の「グループAPI」）。**参加中（脱退を選んでいない）の人には、何も添えない**（見出しの「メンバー」で分かるため。設計の「参加中」の表示は作っていない）。削除したユーザーは、サーバーが名前を「削除されたユーザー」にしているので、文言を重ねない。**知らない状態（`unknown`）の人は、何も添えず、いる人として出す**（この画面は、メンバーの状態で操作の可否を決めない。招待できるかは、サーバーの `canInvite`。`GroupMember.status` の注意書きへの、この画面での答え）。
- **招待の欄**: 自分の `leaveEffective` が true のとき（`status` が `leaving` 以降の人と、`active` のまま脱退月が終わった人）は、欄だけを出さない（設計は「そもそも画面を出さない」。設定の行は、グループの情報を読まない設定の画面からは出し分けられないので、画面は開き、メンバーの一覧だけを出す）。押せないときは、ボタンを押せなくして、満員なら「1つのグループは5人までです。」、それ以外は「いまは、招待できません。」と添える。
- **共有**: OSの共有シート（React Nativeの `Share`。ネイティブの依存は足していない）に、「わりかん生活で生活費を一緒に記録しよう。このURLから参加できます（3日間有効）」とURLを渡す。URLは文面の最後の行（メッセージアプリが、リンクとして認識する）。発行が済んだら、そのまま共有シートを開く。
- **トークンは、発行の応答でしか分からない**（サーバーはハッシュだけを持つ）。この画面を開いているあいだだけ、発行した招待のトークンをメモリに持ち、一覧の「共有」で、URLを出し直せるようにする（共有シートを閉じてしまったとき、メッセージアプリに貼り損ねたとき用）。**端末には保存しない**（持ち続けると、ハッシュだけを持つ設計が意味を失う）。画面を閉じる・アプリを閉じると失われ、その招待は、一覧に「取り消す」だけが残る（「取り消して、新しく発行してください」と案内する）。
- **発行は冪等ではない**（同じ呼び出しを送り直すと、新しい招待がもう1つできる）。結果が分からない失敗（通信が切れた・応答が読めない）のあとは、招待ができているかもしれないので、一覧を読み直す（トークンはもう分からないので、できていても共有はできない。取り消せる）。1人10件までの上限（`too_many_invites`）に当たったら、不要な招待を取り消すよう案内する。
- **一覧**: 新しく発行したものが上。期限は「あと2日5時間」の形（端末の時計との差で出す。タイムゾーンに依らない。分は切り上げるので、発行した直後は「あと3日」）。**表示は、30秒ごとと、アプリが前面に戻ったときに更新する**。端末の時計で期限が切れた招待は、「期限切れ」と薄く出して、**「共有」だけを隠す**（画面を開いたままでも、使えないURLを送らないため）。**行は一覧から外さず、「取り消す」は残す**: 端末の時計が進んでいると、サーバーでは有効な招待が「期限切れ」に見える。外すと、送ったURLは使えるままなのに、取り消す手段が画面に無くなる（時計が3日以上進んでいれば、発行した招待がすぐに消え、`too_many_invites` で「取り消して」と案内しても、一覧が空になる）。一覧を読み直しても、この判定は端末の時計のまま（サーバーの一覧には戻らない）。取り消しは、取り消し済み・期限切れでも、サーバーが成功にする。未使用の招待が上限（`too_many_invites`）のときも、一覧を読み直す（別の端末で発行した招待は、読み直すまで出ないため）。取り消しは、確認のダイアログのあとに送る（取り消し済み・期限切れでも成功するので、送り直してよい）。使われた招待は、409 `invite_already_used` で「すでに使われています」と出し、読み直す。404（`not_found`）は、自分がもうメンバーでない・グループが無い・自分が発行した招待でない、のいずれか（取り消し済みと期限切れは、サーバーが成功にする）なので、「グループの状態が変わったかもしれません」と出す。

- **設定の「アプリの設定（この端末だけ）」に、「キーパッドの並び」の行を1つだけ置く**。右に、いまの並び（スマホ / 電卓）を出し、押すと選ぶ画面（`/keypad-layout`）へ進む。「アプリの設定」だけの画面は、項目が1つのあいだは作らない（行を足すときに、見直す）。選ぶ画面は、2つの選択肢（ラジオ。`accessibilityRole="radio"`）を、小さな図つきで並べる。**選ぶと、すぐ反映する**（保存のボタンは無い。戻るだけ）。
- **切り替わるのは、数字の3行の順だけ**。演算子（右の列。上から ÷ × − +）・`0`・`00`（小数のある通貨では `.`）・`⌫` は、どちらの並びでも同じ位置（仕様）。**キーパッドの実物（`ui/expense/AmountKeypad.tsx`）も、選ぶ画面の図も、同じ関数 `keypadRows` で作る**（数字の並びが、図と実物でずれない。並びを足すときは、そこだけを直す）。**図の下の段は、いつも `00` で描く**（端末の設定で、グループの通貨に依らないため。小数のある通貨のグループでは、実物の `00` が `.` になる）。図の文字は、文字サイズの設定で大きくしない（キーが枠からはみ出す）。選択肢の読み上げは、名前と説明（「スマホ、1 2 3 が上」）で、図は読み上げから外す。選んだ枠の太さは変えず、色だけを変える（変えると、中の図が1dpずれる）。
- **この端末の Documents（`keypad-layout.txt`）に、文字列（`phone` / `calculator`）で覚える**（`lastGroup.ts` と同じ置き場。cache は、OSが消すことがある）。アカウント・グループごとには分けない（端末の好み）。**保存は、選んだ順に直列に行う**（続けて選んだとき、先の保存があとから終わって、古い並びが残らないようにする。保存先を非同期のものに替えても守られる。`npm test`）。**覚えるのに失敗しても、画面には何も出さない**: この起動中は、選んだ並びのまま使え、次の起動で、初期値（スマホ）に戻るだけ。金額の入力を妨げないための割り切りで、直す必要が出たら、`choose` の結果を画面に返して、文言を足す。知らない値・読めない値は、初期値（将来、並びを足した版で書かれた値を、古い版が読んでも壊れない）。
- **読み込みは、アプリの起動時に1回**（`app/_layout.tsx` の `RootLayout` の `useEffect`。`keypadLayoutPreference.start()`）。金額を入れる画面は、ログインのあとの通信（所属グループの一覧など）が済んでから開くので、通常は、それより先に読み終わる（小さなファイル1つ）。**先に読み終わる保証はしていない**（待つ仕組みは無く、スプラッシュも待たせない）: 遅れたら、キーパッドはスマホの並びで開き、読み終えた時点で、覚えていた並びに描き直される（打っている途中で並びが変わりうる。実害はほぼ無いと判断した。気になる出方をしたら、スプラッシュを、`linksReady` と同じように、読み込み（上限つき）まで待たせる）。**読み終える前に、並びを選んでいたら、読んだ値は捨てる**（古い値で、いま選んだ並びを上書きしない。`npm test` で守る）。
- **確かめたのは**、Androidのエミュレータ（API 36。debugビルド）で、`fetch` とログインを偽のものに差し替えた状態（保存はしない一時の差し替え）。初期値のスマホで、支出のシートのキーパッドが 1 2 3 が上。設定の行に「スマホ」が出て、選ぶ画面（図・チェック・枠の色）が開くこと。電卓を選ぶと、`keypad-layout.txt` に `calculator` が書かれ、設定の行が「電卓」になること。支出のシートで、7 8 9 が上になり、演算子の列と `0` `00` `⌫` の位置が変わらないこと。実際に `7` `8` `9` `×` `2` を押して、`789×2` と `= ¥1,578`、「保存 ¥1,578」になること（ラベルどおりの数字が入る）。**アプリを終了して起動し直しても、電卓のまま**であること（支出のシートで確認）。スマホへ戻すと `phone` が書かれ、シートが 1 2 3 が上に戻ること。ダーク（選ぶ画面）。文字サイズ2.0倍（設定の行と選ぶ画面。行の値は収まり、説明は折り返し、図は大きくならず、はみ出さない）。**未確認**: iOS、Android 14以下の実機、スクリーンリーダーでの読み上げ（`radio` の役割と `checked` の状態が、読み上げでどう聞こえるか）、小数のある通貨のキーパッド（`.` の位置は `npm test` で確かめた）、保存に失敗したとき（書き込めない状態を作っていない）、読み込みが終わる前に選んだときの動き（`npm test` まで）、Androidの戻る操作（選ぶ画面から設定へ戻ることは、画面の矢印でしか試していない）、選ぶ画面の二重タップ（`dangerouslySingular` の効果。`app/_layout.tsx`）。

### グループの設定

- グループ名
- 自分の表示名（このグループでの名前）
- 自分の色：メンバーのアイコン（名前の頭文字を丸に入れたもの）の色。10色ほどから選ぶ。参加したときは、他のメンバーと重ならない色を自動で選ぶ。写真は使わない
- 通貨（支出・固定費・上限額つきの負担・締めた月が1つもないときだけ変えられる。変えられるかは、グループ情報の `currencyLocked` で分かる。支出をすべて消すと、また変えられるので、「一度決めたら戻らない」とは案内しない。ただし、一度でも支出を作った固定費は消せないので、その固定費が残るかぎり変えられない）

**実装したところ（グループの設定）**: 設定の「このグループ」の「グループの設定」から、専用の画面（`ui/settings/GroupSettingsScreen.tsx`、ルートは `app/group-settings.tsx`。`dangerouslySingular`。外さない）を開く。上から、グループ名、通貨（チップ）、自分の表示名、自分の色（アイコンの丸の色を、10色から選ぶ。選んだ色と頭文字のプレビューつき）、下端に固定した「保存」。入力の規則は `src/services/groupSettingsForm.ts`、保存の手順は `groupSettingsSave.ts`、失敗の文言は `groupSettingsMessage.ts`（どれも `npm test` で守る。画面は、並べて、押されたものを渡すだけ）。
- **変えられるかは、サーバーの値で決める**: 脱退が確定した人（自分のメンバーの `leaveEffective`）は、グループ名・通貨を変えられない（サーバーが403。欄を読み取り専用にして、理由を添える）。自分の表示名・色は、いつも変えられる。通貨は、`currencyLocked` のとき選べない（「支出・固定費・上限額つきの負担・締めた月のどれかがあるあいだは、通貨を変えられません。」。「戻らない」とは案内しない）。メンバーの `status` は見ない（操作の可否に使わない。`GroupMember.status`）。
- **保存は、変えたものだけを送る**（全項目を送り直す形に「簡略化」しない: 他のメンバーが先に直したグループ名や、別の端末で直した表示名を、開いたときの古い値で上書きする）。送り先は2つ（グループ名・通貨は `PATCH /groups/:id`、自分の表示名・色は `PATCH /groups/:id/members/me`）で、**グループ名・通貨 → 自分の表示名・色の順**に送り、失敗したらそこで止める（グループ名・通貨のほうが断られる理由が多い。先に送れば、断られたとき、何も保存していない状態で止まる）。途中で失敗したら、済んだほうは保存済みとして基準に取り込み（`applySaved`）、**やり直しでは残りだけを送る**。失敗の文言は、済んだ段階があれば、「グループ名・通貨は保存しました。」から始める。グループ名・通貨で止めて、自分の表示名・色を送っていないときは、「自分の表示名・色も、まだ保存していません。」を添える（通貨だけが断られたように読めて、ほかは保存されたと誤解されないため）。
- **断られたあと**: 脱退が確定した・通貨が固定された（403 `forbidden`・409 `currency_locked`）と分かったときだけ、読み直して、入力を載せ直す（`rebase`: 触っていない項目は読み直した値に、触っていて、いまも変えられる項目は入力を残し、もう変えられない項目は読み直した値にする）。競合（409 `conflict`）・通信の失敗・応答が読めない失敗は、**読み直さず**、もう一度押してもらう（同じ内容の送り直しは、サーバーが変わらなければ書かないので、結果が変わらない）。グループが無い（404）ときは、所属グループの一覧を読み直し（`reloadGroups`）、この画面の入力欄・通貨・色・保存を操作できなくして（入力を変えると、保存できない理由の文言が消えるため）、戻る操作の破棄の確認も出さない（この画面から先へは進めない。`GroupGate` が、別のグループか、グループの作成へ切り替える）。
- **グループ名を変えたら、所属グループの一覧を読み直す**（`reloadGroups`。ホームの上部・グループの切り替えに出る名前が、古いままにならない）。**名前を送った呼び出しが、済んだか分からない失敗（通信が切れた・混雑・応答が読めない。`saveResultUnknown`）で終わったときも読み直す**（サーバーでは済んでいることがあり、やり直さずに戻ると、起動し直すまで古い名前が残る）。**既知の限界**: 通信の失敗が、10秒のタイムアウトで打ち切ったときは、サーバーの処理が続いていることがある。失敗の直後の読み直しが、書き込みより先になり、古い名前を拾うことがある（頻度は低い。直していない。次に所属グループの一覧を読み直すまで、古い名前が出る）。通貨は、ホームが戻ったときに読み直す。
- 変えた入力があるときの戻る操作（戻る矢印・Androidの戻る操作）は、破棄の確認を出す（グループ名・通貨が保存済みなら、「さきほど保存したグループ名・通貨は、元に戻りません。」と、保存した時点を示して伝える。そのあとにグループ名をもう一度変えていても、本文が事実と合う）。通信の最中は、戻る操作が効かない。iOSの端のスワイプは、通信の最中と、変えた入力があるあいだ、無効にする（`beforeRemove` と `gestureEnabled`）。招待URLによる参加確認への切り替えは、保存の通信の最中だけ遅らせる（`useHoldInviteSwap`）。保存後は、前の画面へ戻る（外れたあとは戻さない。`useMounted`）。
- 応答は、書き込みなので `group.id` があることだけを確かめる（`groupRepository.update`・`updateMe`）。画面を開くときの読み込み（`GET /groups/:id`）は、全項目を検べる（ホームと同じ）。
- **確かめたのは**、Androidのエミュレータ（API 36。debugビルド）で、`fetch` とログインを偽のものに差し替えた状態（保存はしない一時の差し替え。Repositoryの読み方と本文は、本物のコードで通っている）。通常のグループで、4項目を変えて保存（2つの `PATCH` が、変えた項目だけ、この順に送られること。前の画面へ戻ること。ホームの上部の名前が変わること。開き直すと、保存した値で、保存ボタンが押せないこと）、通貨が固定されたグループ（チップが選べない・理由）、脱退が確定した人（グループ名・通貨が読み取り専用・理由）、保存が403で断られたとき（読み直して、グループ名が読み取り専用に変わり、自分の表示名の入力は残ること。もう一度押すと、自分の表示名だけが送られること）、409 `currency_locked`（通貨が元に戻って選べなくなり、グループ名の入力は残ること）、2つ目の呼び出しだけが失敗したとき（503。「グループ名・通貨は保存しました。」の文言。破棄の確認の文言。もう一度押すと、自分の表示名・色だけが送られること）、1つ目の通信が切れたとき（文言。もう一度押して通ること）、変えた入力があるときの戻る操作の確認、ダーク、文字サイズ1.5倍（スクロールして、保存ボタンが下端に固定されたままであること）。**未確認**: 本物のWorkerとの通信（`API_ORIGIN` が仮の値）、iOS（端のスワイプの無効化、`announceForAccessibility`）、Android 14以下の実機、スクリーンリーダー、文字サイズの最大、長いグループ名・表示名、通貨を実際に変えたあとの、ホーム・支出のシートの金額表示（偽のサーバーは、ホームのデータを返していない）、脱退を選んで確定した直後にこの画面を開いたままにした場合。**レビュー対応で足した次の5つは、エミュレータでも確かめた**（同じ偽サーバー）: 1つ目で止めたときの「自分の表示名・色も、まだ保存していません。」（409 `currency_locked`。表示名だけが変えてあり、グループ側の `PATCH` だけが送られること）、破棄の確認の新しい文言（保存したあとにグループ名をもう一度変えて戻る）、済んだか分からない失敗のあとの一覧の読み直し（名前は書き込まれたが、応答が届かない。失敗の直後に `GET /groups` が呼ばれ、破棄して戻ったホームの上部に新しい名前が出ること）、グループが無い（404）ときの、入力欄・通貨・色・保存の無効化と理由の文言の維持、そのあとの戻る操作で、破棄の確認が出ないこと。

### アカウントを削除

- 説明：すべてのグループからすぐに脱退すること、名前は「削除されたユーザー」になり、支出・精算の記録はグループに残ること、自分が最後の1人のグループは削除されること、元に戻せないこと
- 精算が残っている送金があれば、「削除すると、この精算は繰り越せなくなります」と添える
- 再認証（Apple / Googleでもう一度ログイン）してから削除する

**実装したところ**: 設定の「アカウント」の、ログアウトの下の行（エラーの色）から、専用の画面（`ui/settings/DeleteAccountScreen.tsx`、ルートは `app/delete-account.tsx`）を開く。説明（上の項目）→「アカウントを削除」→ 確認ダイアログ → 各社の画面で本人確認 → 削除、の順。再認証と削除の手順は、`accountService.deleteAccount`（`platform/accountService.ts` の包み）が持ち、画面は手順にもWorkerのデータの扱いにも触れない。失敗の文言は `src/services/deleteAccountMessage.ts`（`npm test` で確かめている）。
- **「精算が残っている送金」の注意は、あるかどうかを調べずに、いつも出す**: 全グループの未精算の送金を数えるAPIが無く、グループごとに読み込む処理を足すほどの理由もないため（文言は「精算が済んでいない送金があるときは、…」）。

- 実行中の案内に、秒数は書かない（本人確認の画面を待つ時間が最大5分、通信の上限は、`T` の取得が10秒、削除が30秒で、合計は一定でない）。
- 結果の読み上げ: Androidは `accessibilityLiveRegion` で読まれる。**iOSは読まれないので、`announceForAccessibility` で読み上げる**（削除の画面の失敗・削除は済んだ結果と、ログイン画面の上の案内）。
- 実行中（本人確認の画面を待つあいだと通信）は、戻る矢印・Androidの戻る操作・iOSの端のスワイプを止める（`beforeRemove` と `gestureEnabled`）。招待URLによる参加確認への切り替えは遅らせる（`useHoldInviteSwap`）。確認ダイアログから削除を始めるので、画面が外れていれば何もしない（`useMounted`）。`app/_layout.tsx` の `delete-account` に `dangerouslySingular` を付けている（外さない。理由は、シートと同じ）。
- 削除のあとも、最後に開いたグループの記憶（`platform/lastGroup.ts`）は消さない（ログアウトと同じ。1章）。
- Googleのアカウントでの削除は、Googleのログイン（`modules/warikan-google-signin`）の組み込み後は、再認証のIDトークンを同じ部品で得る。**Googleのログインは、Android実機（Pixel 3）で通った。アカウントの削除は、まだ確かめていない**。
- **確かめたのは**、Androidのエミュレータ（API 36。debugビルド）で、アカウントの層（`getSignedInProvider`・`signIn`・`signOut`・`deleteAccount` と `withSession`）とグループ一覧のAPIを偽のものに差し替えた状態（保存はしない一時の差し替え。`withSessionLostNotice` の包みと画面は、本物のコード）。設定の行、説明、確認ダイアログ、実行中の表示（スピナー・説明文・戻る矢印が薄くなる・戻る操作が効かない）、取りやめ（何も出ない）、本人確認の失敗、結果が分からない失敗（`delete-unconfirmed`）の文言、401でログイン画面へ移り文言がその上に出ること、ログインで文言が消えること、端末のセッションを捨てられなかったときの結果と「ログアウト」、成功でログイン画面の上に2行（削除した・Appleの連携）が出ること、設定の行の2連打（`adb shell 'input tap … & input tap … & wait'`）のあとに、戻る操作1回で設定へ戻ること（`dangerouslySingular` を付けた状態。付ける前は試していない）、ダーク。**未確認**: 本物のWorker・Apple・Googleとの通信（`API_ORIGIN` が仮の値。本物の再認証の画面と、削除、Appleの失効）、iOS（端の戻るスワイプの無効化、Appleの設定からの連携解除の文言）、Android 14以下の実機、スクリーンリーダー、文字サイズを大きくしたとき、招待URLを開いたときに実行中の画面が外れないこと（`useHoldInviteSwap`。ほかの画面の遅らせる仕組みと同じ配線で、この画面では動かしていない）、Android のApple（Web経由）での本人確認で、Custom Tabから戻るURL（`warikan-seikatsu://auth/apple?...`）を受けたあとも、削除の画面が残って結果を受け取れること（`app/+native-intent.tsx` が、起動中は `null` を返す設計。本物のAppleで確かめるまで未確認。アプリのプロセスが本人確認の最中に終わると、起動時のURLとして届き、ルートから始まるので、削除の画面は失われる）、iOSの `announceForAccessibility` の読み上げ。
